# ADR 0001：单活动 SKU 的库存预占采用条件 UPDATE

- 日期：2026-10-08。
- 状态：**Accepted / Implemented（策略已接受，Phase 6C-5 正式服务层落地并验证）**。
- 确认依据：项目拥有者对“单个商品的库存预占采用条件 UPDATE”明确回复 `ok`，随后要求开始下一片。
- 阶段：Phase 6C-4，Depth / Learning Mode；面试价值是解释并发正确性、选型理由、失败回滚和证据边界。
- 决策基线：`86b1bd8`。Phase 6C-4 只写决定、学习材料和进度；下文第 6C-5 节记录后续正式实现与验证。

## 问题与适用范围

多个顾客竞争同一个活动 SKU。每单购买一件，库存不能超卖；订单、购买资格、库存预占及流水必须共同提交或回滚。
此前默认 NOWAIT 在获取库存行锁发生竞争时立即返回 `stock_busy`；有限重试仍可能以繁忙结束，且增加尝试次数。

本决定只适用于 [create_flash_sale_order()](../../backend/apps/promotions/services.py) 的单 SKU 库存预占步骤。
普通购物车的多 SKU 下单、支付核销、关闭释放及退款逻辑不在本次替换范围内。
Phase 6C-4 时正式 helper 仍是 NOWAIT，条件更新仅在比较测试中选用。
Phase 6C-5 已切换正式 helper；[既有比较测试](../../backend/apps/promotions/tests/test_flash_sale_inventory_comparison.py) 的条件分支直接调用它，NOWAIT 作为显式历史对照保留。

## 接受的设计

在原下单事务中，按唯一 SKU 定位 Inventory，将 `available_stock >= 1` 作为 UPDATE 条件，
同时执行 `available_stock - 1`、`reserved_stock + 1`，然后检查更新行数。

| 库存步骤结果 | 解释与后续行为 |
| --- | --- |
| 更新 1 行 | 本次预占成功；继续读取 Inventory，建立原有 Reservation、Movement，最后由整个事务提交 |
| 更新 0 行 | 没有符合条件的库存行；按 `insufficient_stock / 409` 退出事务，回滚此前订单与资格 |
| SQL 抛出异常 | 不属于 0 行结果；离开业务事务并保持失败可见，不提交部分业务事实 |

Inventory 的 SKU 是 OneToOne，购买数量固定 1，因此合法更新行数是 0 或 1。
0 行也包括对应库存记录不存在，不能仅由行数区分“售罄”和“记录缺失”；本决定沿用现有候选的统一库存不足结果。
1 行只代表库存步骤成功，不代表整张订单已成功提交。

保留已有 User 串行化、地址归属、活动校验、服务端价格、幂等键和购买资格数据库唯一约束。
保留创建路径中 Purchase 先于 Inventory 的相对锁顺序，与支付/关闭路径的相关锁序一致。
原子条件更新负责库存数量边界；资格唯一约束负责限购；幂等键负责同请求重放，三者不能互相替代。
后续写入异常仍必须回滚整个下单事务，不能提前提交库存，也不能在原事务里吞掉数据库错误后继续建单。

## 选择依据与替代方案

已复用的 [Phase 6C-2 正确性证据](../verification/phase-6c2-flash-sale-inventory-comparison.md) 包含：
首单提交后败方更新 0 行并无残留；首单回滚后等候者更新 1 行；同用户不同 Key 仅一单；实写后异常全回滚及原 Key 重放。

已复用的 [Phase 6C-3 成本证据](../verification/phase-6c3-flash-sale-inventory-load.md) 中，
库存 6、24 位顾客、8 worker、最多 3 次总尝试的三轮，两种策略每轮都生成 6 张订单：

| 指标 | NOWAIT 加有限重试 | 条件 UPDATE 候选 |
| --- | --- | --- |
| 每轮调用数 | 52–55 | 24 |
| 全部旅程 p95 范围 | 106.42–121.91 ms | 90.01–94.55 ms |
| 批次连接开放区间合计 | 1.703–1.834 s | 1.016–1.072 s |

这些是每个条件三轮的范围；旅程含重试与退避，连接合计不是 SQL CPU 时间。
库存 24、三次预算时，候选总连接秒与 NOWAIT 有交叠，不能说候选每轮资源成本都更低。
数据来自有限本机服务批次，不支持生产容量、稳定尾延迟、普遍无死锁或所有负载下更快的结论。
上述成本来自 Phase 6C-3，当时尚未正式落地；Phase 6C-5 的行为验证见后节，未重跑该成本矩阵。

最小替代方案是保留 NOWAIT：库存取锁迅速失败，但应用需要决定是否以及如何重试，顾客可能最终得到繁忙。
普通 `SELECT FOR UPDATE` 等待后检查库存也是可行设计；本片未增加第三套实验，其成本不能冒充已实测。
选择条件 UPDATE 是基于单 SKU 数量规则和现有证据的本期取舍，不是认定所有业务都应这样实现。

## 代价与失败边界

UPDATE 仍取得写锁，可能等待；等待时连接、事务及此前取得的用户、地址、资格相关锁仍占用资源。
条件更新成功后仍有一次 Inventory GET，当前成功库存步骤与原方案都是两条 SQL，完整下单远不止一条 SQL。

- 更新 0 行与 1205（锁等待超时）、1213（死锁）必须区分；后两者不能伪装成库存不足。
- 锁等待预算只限制相应数据库等待，不是整个 HTTP 请求截止时间，也不是零等待或无死锁保证。
- MySQL 默认锁等待超时通常只回滚当前语句；应用必须让异常离开外层 `transaction.atomic()`，保障此前订单和资格也回滚。
- 不能在失败的事务里只重跑库存 SQL。若后续允许自动重试，应在原事务结束后以原 Key 重跑完整业务流程，并明确有界预算；本片没有新增自动重试政策。
- 连接中断等错误可能涉及提交结果不确定，不能简单归类为“库存不足”或把所有异常都盲目重试。

Phase 6C-4 将等待政策和错误映射留待正式落地前确认；Phase 6C-5 的确认、实现与新证据见下一节。
原负载矩阵不自动重跑，只有实现改变测量前提或出现新问题时才扩大验证。

技术语义参考：[MySQL 锁定读取](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)、
[事务隔离与 UPDATE](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)、
[InnoDB 错误处理](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html)。

## Phase 6C-5 正式落地（2026-10-08）

拥有者明确选择沿用现有会话上限：本机 50 秒；不新增配置或自动重试，HTTP 接入前再确定顾客等待预算。
正式 helper 仅在库存 UPDATE 的 1205/1213 分支返回现有 `stock_busy / 409` 并保留 cause，其他数据库异常原样上抛。
错误必须退出原下单 atomic，前面的 User/Address 锁与其他 SQL 错误不由该分支统一转换。
公开下单 AST、资格/幂等、价格与相对锁序保持；NOWAIT 函数体迁入测试作为历史对照。

真实隔离 MySQL 1205 验证了超时前已有订单与资格、失败后六类事实全回滚，以及放行后原 Key 重试/重放。
1213/2006 的注入仅证明映射与透传，不是真实死锁或断连实验。
目标 9 项、198 子场景通过；相关回归 183 项、403 子场景通过，7 项显式实验跳过、12 项真实 MQ 未选入。
本轮没有修改生产等待配置、开发数据库、迁移或接口，也没有重新压测；详细证据见 [Phase 6C-5](../verification/phase-6c5-flash-sale-inventory-failures.md)。

## Phase 6D-2：HTTP 会话等待政策（2026-10-08）

拥有者明确选择“临时5秒并恢复原会话值”。只在秒杀HTTP调用原服务前读取/暂设SESSION等待值，
原atomic结束后恢复同一物理连接原值；不修改全局MySQL配置或服务层默认值。
适配拒绝已有外层atomic或关闭autocommit的调用，避免把未完成事务错误当成可安全恢复的状态。

库存步骤仍将1205/1213映射stock_busy；原下单其他SQL的1205/1213在atomic退出后映射checkout_busy，
未知数据库错误传播，没有自动重试。设置失败不下单；恢复失败告警并丢弃连接，保留已提交成功、业务拒绝或原异常。
连接已经更换时，不向新连接写旧值。5秒限制相应行锁等待，不能保证整个HTTP请求5秒内结束。

替代方案是沿用原会话值，免去参数读取与设置成本，但本机50秒的单次行锁等待不适合本入口的当前选择。
暂设政策增加成功路径三条会话SQL及异常清理分支；当前没有生产SLO或吞吐改善结论。
真实隔离库存UPDATE与User FOR UPDATE分别发生1205，两种HTTP繁忙响应、整单无残留、会话恢复和原Key重试/重放通过。
恢复/关闭故障、1213与未知错误测试为注入，不是真实死锁、网络断连或提交不确定恢复实验。
详细目标和相关回归范围见 [等待与恢复记录](../verification/phase-6d2-flash-sale-http-wait.md)。
