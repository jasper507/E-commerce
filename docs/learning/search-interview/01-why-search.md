# 为什么用Elasticsearch，MySQL搜索不够吗？

2026-10-11。当前源码快照：`7ea1963f2a7eec6018852e7d3c17b007d1e6d190`。[搜索总览](../search-current-overview-study-guide.md) · [本轮文档核对](../../verification/search-interview-knowledge-base-publication.md)。

**本项目引入ES的具体价值，是验证另一套文本匹配与排序规则，以及可重建搜索副本的读写边界；现有证据没有证明MySQL搜索已经慢到不能用，也没有证明ES更快。** 面试时需要讲清需求怎样变化、两个方案分别做了什么，以及多一份数据以后付出了什么代价。

当前顾客前端仍使用原MySQL商品列表。独立ES接口已实现并经过隔离验证，但默认关闭、只允许隔离测试来源；不能把这段开发经历说成线上搜索已经切到ES。

## 1. 从顾客的搜索意图说起

顾客想找“无线鼠标”，商品名称可能是“无线鼠标 M1”，描述也可能含“备用无线鼠标”。最初的业务选择是：**名称或者描述包含完整关键词，都算匹配；分类和上架状态仍要同时满足。**

这个规则容易解释，也能直接复用公开商品列表。输入`无线鼠标`可以找到上述商品；输入`鼠标 无线`却找不到`无线鼠标 M1`，因为商品文字没有连续出现整个`鼠标 无线`。这不是接口异常，而是完整包含匹配的能力边界。

后来需要评估的是：顾客把词顺序写反或用空格拆开时，是否仍能找到商品；名称匹配能否影响排序；商品改名以后，第二份搜索资料怎样重建并交给读入口。这里既有搜索体验问题，也有副本一致性问题。

**采用ES不意味着上述体验都会变好。** 当前分析器也有单字和空格边界的漏匹配，下一页会用实测例子解释。不能把“引入了搜索引擎”当作已经满足了全部中文搜索需求。

## 2. 原MySQL搜索怎样形成完整结果

请求为`GET /api/catalog/products/?q=无线鼠标&category=mice&page=1`。这是公开只读目录，游客可访问，无需先登录。

输入校验先去掉关键词首尾空白，最长80字符；未传或空白关键词继续原商品浏览。查询先限制商品上架、分类有效，计算有效SKU最低价及有货提示，再加关键词和可选分类条件，按`name, id`排序，固定每页20条。

关键词条件为“名称包含，或者描述包含”，与其他业务条件取交集。缺货商品和没有SKU的商品仍可被发现；无有效SKU时最低价为null，有货提示为false。这使顾客能看见待补货商品，但浏览结果不能承诺之后下单一定成功。

核心片段来自[商品列表查询](../../../backend/apps/catalog/views.py#L102)：

```python
keyword = query.validated_data["q"]
if keyword:
    # 完整关键词包含匹配；ORM负责转义LIKE通配符，不做分词或相关性排名。
    queryset = queryset.filter(Q(name__icontains=keyword) | Q(description__icontains=keyword))
```

这段不是整条SQL：前面已有当前可见性、SKU摘要、分类与顺序，后面还有分页统计和响应。`icontains`产生包含匹配，参数和LIKE通配符由ORM处理；它没有把关键词拆成词项。实际大小写、字符等价比较还受MySQL排序规则影响，不能只根据Python条件推断全部Unicode行为。

响应`count`是此时完整MySQL过滤结果的数量，`next/previous`是分页链接。它与ES接口的`candidate_count`不同，后者统计的是搜索副本里的候选，详见[候选回读与分页](03-read-path.md)。

## 3. LIMIT20为什么不代表数据库只看20件商品

分页先解决“一次只返回20条”的问题；但在找到这20条之前，数据库仍可能检查大量商品、计算SKU摘要和排序。

Phase 7A在可销毁MySQL中建立5,000件可见商品、2件隐藏商品和10,004个SKU及对应库存记录，捕获完整API的COUNT与结果SQL。`无线鼠标`命中500件，分类限定后命中250件；结果页仍只返回20件。实际计划显示，列表在关键词过滤后的商品上聚合，再排序取20；COUNT也不是不带关联的简单商品计数。

关键词是`LIKE '%关键词%'`，不能把普通名称索引想成一个直接定位任意包含文本的目录。该次计划仍使用分类外键等已有索引定位商品候选，随后进行文本过滤；所以“关键词不能直接按普通前缀查找”也不能说成“整条SQL完全没有用索引”。

| Phase 7A请求 | 匹配总数 / 返回数 | 实际API SQL |
|---|---:|---|
| `q=无线鼠标` | 500 / 20 | COUNT与结果查询，共2条 |
| 不存在的关键词 | 0 / 0 | COUNT，共1条 |
| 关键词加指定分类 | 250 / 20 | COUNT与结果查询，共2条 |

这些计划揭示了工作范围，但每条只观察一次本地合成数据。没有旧MySQL与ES在相同数据、相同语义、相同负载下的时延对照。**SQL数量、分页条数和“用了索引”，都不能单独证明接口性能提升。**

证据见[7A验证记录](../../verification/phase-7a-search-baseline.md)与[完整查询计划](../../verification/phase-7a-search-baseline.json)。这是2026-10-09的历史实测，本轮整理没有重跑。

## 4. ES到底改变了哪一段

Elasticsearch（独立文本搜索服务）在本项目保存可从MySQL重建的商品搜索资料，用分析后的词项寻找候选并计算相关性。它不接管商品交易事实。

相比原列表，ES读路径先对名称和描述做文本分析与候选排序，再由MySQL检查这页候选当前是否可见，生成当前名称、分类、最低价与有货提示。ES只决定“哪些ID先成为候选”，MySQL决定“现在可以返回什么商品事实”。

| 业务问题 | 原MySQL列表 | 当前独立ES入口 |
|---|---|---|
| 关键词怎样匹配 | 名称或描述连续包含完整关键词 | 同一字段满足全部分析词项 |
| 词序与空格 | 属于完整输入的一部分 | 词项匹配允许换序，但空格改变词项 |
| 排序 | 名称升序、同名ID升序 | 相关性降序、同分商品ID升序 |
| 当前价格和库存提示 | 当前MySQL摘要 | ES候选后回读当前MySQL摘要 |
| 计数 | MySQL完整当前匹配数量 | ES候选总数，不能冒充当前可见总数 |
| 新增或改名 | 后续MySQL查询读取当前文字 | 副本不自动更新，可能漏掉或旧词误命中 |
| 服务依赖 | MySQL | MySQL加ES，增加故障和恢复边界 |

业务体验的具体变化已有证据：在7B的固定12件商品数据中，`鼠标 无线`的MySQL匹配为0，ES匹配为6。可是单字`标`的MySQL匹配为6，ES匹配为0。因此可以说“在这些输入上实现了不同检索语义”，不能笼统说“召回率全面提高”。

搜索副本只保存商品标识、名称、描述和分类标识；不保存价格、库存、订单或付款状态。价格变化不需要靠重建ES才能返回当前最低价，库存核销更不会发生在ES。即使结果显示有货，下单仍经过原MySQL事务和库存规则。

## 5. 为什么没有直接替换原搜索框

两种接口已经改变了匹配、排序和分页语义，不能把响应封套换一下就宣称是透明升级。ES接口还需要前端正确呈现短页、空候选页和503；现有前端尚未切到该接口。

当前独立入口默认关闭，而且限制实际测试库、ES测试集群与候选命名。这个选择让原浏览闭环继续可用，同时可以隔离验证文本分析、陈旧候选和切换机制。代价是项目现在还不能通过普通顾客页面演示完整ES搜索体验，这项缺口必须如实说出来。

ES故障时没有静默回退原MySQL搜索：换序输入可能从有结果变成无结果，排序也会改变，数据库还可能突然承接搜索流量。当前明确返回503并保留普通浏览，这是已选业务合同；有提示的降级仍可作为后续方案，而非已实现能力。

## 6. 有哪些有意义的替代

| 选择 | 适合什么需求 | 要接受什么成本 / 当前证据 |
|---|---|---|
| 继续MySQL包含匹配 | 小目录、连续关键词已足够、先完成顾客闭环 | 实现简单，无独立副本；词序、相关性和包含扫描限制仍在 |
| 评估MySQL FULLTEXT | 需要全文检索，但希望继续在一个数据库内管理 | 仍要确定中文词项、查询语义和索引维护；本项目没有实测，不能说已证明不合适 |
| 当前ES派生副本 | 希望单独验证文本分析、排序和重建发布 | 需要第二个服务、同步/重建、陈旧处理及故障政策；现有证据支持局部语义和机制，不支持速度优势 |

有意义的比较必须让需求先站住。例如需求只是“查名称中含完整型号M1”，引入第二个服务的收益可能不足；需求如果明确包括换序词项、相关性或独立搜索演进，才有更充分的比较理由。不是技术名称越多，面试回答就越强。

## 7. 如果重新做，我会怎样选择

**我会保留先做MySQL基线的顺序，但更早把“搜索正确”写成一组顾客输入与预期商品，再决定是否采用ES。** 原先的最小目录能立即服务浏览，且没有副本同步问题，这个选择在学习阶段合理。

会改进的是，在加入分析器前，把连写、空格、换序、单字、型号和跨字段输入放到同一份需求表，明确哪些必须命中、哪些允许不命中。这样不会在发现ES漏掉`无线 鼠标`后才把它称为理所当然，也不会把MySQL与ES不同语义的耗时直接比较。

如果这些输入用MySQL已经满足，我会暂缓ES，把时间用在交易正确性和数据库基础；如果确实需要不同检索语义，就保留“ES找候选、MySQL守当前事实”的边界，再按业务变化频率决定手动重建是否足够。自动同步是候选改进，不是当前成果。

新成本是需求整理和质量对照的时间，以及采用ES后持续承担第二份数据的维护。采用门槛是具体查询例子证明收益、业务能够接受更新延迟和故障提示；性能主张另需同条件完整请求对照。已有7A–7D证据足够解释当前选型与边界，本轮不追加负载实验。
