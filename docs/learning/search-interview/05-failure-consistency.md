# ES故障或数据陈旧怎么办？

2026-10-11整理。源码快照：`7ea1963f2a7eec6018852e7d3c17b007d1e6d190`。[搜索总览](../search-current-overview-study-guide.md) · [本轮文档验证](../../verification/search-interview-knowledge-base-publication.md) · [7C真实验证](../../verification/phase-7c-search-read-api.md) · [手动重建与切换](04-index-switch.md)。

**当前用MySQL确认返回商品的可见性、分类、价格与有货提示；ES坏了则搜索明确503，普通浏览入口仍可独立使用。MySQL回读能过滤陈旧命中，却补不出ES没有召回的商品。** 这页支撑面试解释“副本与事实的分工、故障时业务怎样反馈、为何加入MQ不等于完成可靠同步”；以已有陈旧、离线和来源拒绝证据为边界。

## 本专题前后变化

7B只有隔离搜索原型，旧索引会保留改名前的商品信息。7C增加ES候选ID到MySQL当前商品摘要的只读API，7D增加手动完成候选后切换入口。现在可以守住返回可见性并手动更新候选，但没有自动同步。新搜索默认关闭，只允许实际隔离测试来源；开发与当前独立部署都没有开启，前端搜索仍走旧MySQL商品列表。

## 1. 搜索副本与交易事实各管什么

ES索引保存商品标识、名称、描述和分类，用于找出关键词相关候选并排序。MySQL保存商品、SKU、价格、库存、订单与支付事实；搜索读API用候选ID再查MySQL生成公开摘要。用户真正提交购买时，订单业务仍重新验证商品、SKU、价格和可预占库存，不能信任之前的搜索响应。

例如搜索返回最低价`89.00`、`in_stock=true`，说明摘要读取时某个有效SKU有货，不是承诺顾客选中的SKU一定有库存。下一位顾客可能已占走最后一件；最终下单事务仍可返回无货。最低价也是多个有效SKU的最低值，不一定是用户所选SKU的单价。

浏览、详情缓存、搜索和购买是不同读写路径。Redis详情缓存可以提供旧展示字段，ES可以提供旧候选，二者都不替代MySQL下单规则。搜索恢复可连接，也不等于候选已经更新到最新业务数据。完整闭环见[项目总览](../project-current-overview-study-guide.md)。

## 2. 陈旧候选能修正什么，不能修正什么

历史7C先索引了一批“陈旧键盘”，ES旧词返回5个候选。之后只改测试MySQL：一件商品下架、一个分类隐藏、一件迁分类、一件改名为“新款音箱”并改价为`89.00`、可用库存改为7，再新增“全新麦克风”。没有重建ES。

| 当前变化 | 旧ES会怎样 | MySQL回读后的结果 |
| --- | --- | --- |
| 商品下架或分类隐藏 | 旧候选仍可能命中 | 当前不可见，过滤掉 |
| 商品迁到别的分类 | 旧分类候选仍可能包含它 | 指定旧分类时过滤；不指定分类时显示当前分类 |
| 商品改名、改价和库存 | 旧词仍可能命中 | 返回新名称、89元、有货提示 |
| 顾客搜索改名后的新词 | 旧索引没有新词项 | 回读没有收到该ID，无法把它补出来 |
| 新增商品尚未建索引 | ES没有文档 | 即使MySQL存在，也不能凭回读自动搜到 |

真实结果：旧词5候选、返回3件；指定旧分类4候选、返回2件。改名商品展示新名称、`89.00`和有货，而新词、新分类、新增商品各为0候选。具体响应见[陈旧场景JSON](../../verification/phase-7c-search-read-online-final.json)，实际改变见[测试交错](../../../backend/apps/catalog/tests/test_search_read_api.py#L215)。

Recall（召回：把相关商品找进候选集合）与返回事实是两件事。回读是在已选ID集合内确认当前事实，不重新做关键词匹配。因此顾客搜“陈旧键盘”有时会看到已改名的“新款音箱”。这不够理想，但当前明确允许，以便保留ES相关性、接受副本陈旧边界；如果再套MySQL完整包含匹配，语义会变回原LIKE，也不能找到ES完全没给出的新商品。

## 3. 为什么短页、空页仍可能翻下一页

新接口每次只取20个ES候选，不补拉到20个可见商品，也不统计全部当前可见命中数量。`candidate_count`表示候选总数，`results`表示这一候选页回读后还可展示的商品。

历史测试21个同文案候选：第一页20个，其中1个下架后返回19件；再把前20个都下架，第一页返回空数组，但`candidate_count=21`、`next_candidate_page=2`。第二页仍返回最后1件。**空结果数组不能直接表示全站没有匹配商品，候选导航必须单独看。**

这个合同控制每次候选读取范围，代价是用户可能翻到短空页、候选数字不等于当前可见总数。为凑满页，需要增加多次ES拉取及MySQL回读，并给扫描预算、导航位置和故障明确语义；不能在当前代码里只改`len(results)`就完成。返回事实与分页的详细机制见[MySQL回读问题页](03-read-path.md)。

## 4. 故障为什么返回503，不能假装没搜到

“没有商品符合关键词”是正常搜索结果，200且候选0；“ES没有给出可信结果”是依赖故障，503。把后者返回200空数组会误导顾客认为商品不存在，也掩盖运维问题。当前入口捕获来源拒绝、ES API/传输异常及相关非法结构，统一给出明确不可用提示。

摘录来自[API故障转换](../../../backend/apps/catalog/views.py#L62)：

```python
try:
    ids, total = reader.candidates(data["q"], category, page)
except (SearchReadUnavailable, ApiError, TransportError, ValueError) as exc:
    raise SearchServiceUnavailable() from exc
```

`SearchServiceUnavailable`定义503和“商品搜索暂不可用，请稍后重试；仍可使用普通商品浏览”。候选还没有拿到时就退出，不继续查询当前商品摘要；不是先失败再悄悄改走另一套MySQL搜索。

| 情况 | 当前接口行为 | 业务含义 |
| --- | --- | --- |
| 合法查询，无候选，第一页 | 200，空results | 本次正常查询没有候选 |
| 当前候选全部被过滤 | 200，可能空results且仍有下一候选页 | 本页没有可展示商品，不代表后页没有 |
| 非法参数或候选超过10,000 | 400 | 修正输入或缩小范围 |
| 合法页码超过候选尾 | 404 | 此候选页不存在 |
| 模块关闭、ES不可达、索引缺失或不完整 | 503 | 没有可靠搜索结果，之后可重试 |
| 来源/完成标记或别名结构不符 | 503 | 拒绝把不符合约定的候选当正常数据 |

“HTTP200也可能不可信”还适用于ES本身。[读适配器](../../../backend/apps/catalog/search_read.py#L55)检查`timed_out`、失败分片、总数是否精确、候选数量及ID合法性；不接受部分搜索结果。超时响应、失败分片、近似总数与坏ID的503分支使用替身客户端注入验证，不是实际多节点故障证据。

2026-10-10真实停止隔离ES后的7D离线回归观察：约2.007秒发生`ConnectionTimeout`，新搜索503，仅1条`SELECT DATABASE()`、0条商品摘要SQL；普通MySQL浏览200。[离线原始JSON](../../verification/phase-7d-search-read-offline-regression.json)。客户端零自动重试、每请求超时2秒；在线路径串行info、alias、mapping、search，2秒不是整体HTTP期限，更不是恢复SLA。读端目前每请求新建并关闭客户端，尚无生产连接池、整体依赖期限或搜索容量证据。

## 5. 为什么不自动退回MySQL搜索

旧MySQL搜索按名称或描述包含完整关键词，按名称/ID排序；新ES搜索按分词后的字段匹配和相关性排序。同一个“鼠标 无线”，两者可能给出不同命中与顺序。故障时直接套旧LIKE，会在同一新API下改变语义、候选总数和分页位置，用户可能把“相关性变了”误认为商品变了。

当前选择是明确503，让普通浏览保持独立可用。它保留了失败可见性与契约，但损失故障期间的新搜索可用性。替代方案并非绝对错误：如果业务确实优先保证一种基础搜索，可以单独设计降级模式，向使用者标明结果来源、匹配与排序变化、分页重置规则，并为数据库回退负载加边界。当前没有这些机制，也没有该模式的实测，所以不能写成已存在的自动降级。

## 6. 来源保护为什么要核对实际连接

搜索索引里的`product_id=7`只对其来源库有意义。如果测试索引ID7被拿去查开发库，可能意外显示完全不同的商品。代码同时限定环境、连接配置和实际`SELECT DATABASE()`，还禁止在外层数据库事务内等待ES。核心摘录来自[真实来源检查](../../../backend/apps/catalog/search_prototype.py#L46)：

```python
def require_test_source(db_connection):
    if (
        settings.ENVIRONMENT != "test"
        or db_connection.vendor != "mysql"
        or db_connection.settings_dict["NAME"] != SOURCE_DATABASE
    ):
        raise RuntimeError("Search prototype requires isolated MySQL test_project_one.")
    if not db_connection.get_autocommit() or db_connection.in_atomic_block:
        raise RuntimeError("Do not hold a MySQL transaction while building a search index.")
    with db_connection.cursor() as cursor:
        cursor.execute("SELECT DATABASE()")
        if cursor.fetchone()[0] != SOURCE_DATABASE:
            raise RuntimeError("Search prototype requires the actual isolated MySQL database.")
```

ES地址、集群与版本、精确索引/别名格式以及完成来源元数据也会校验。它们是约定与误接防护，不是安全认证或内容签名。`_meta`只记录`test_project_one`这个库名，不能区分删除后再创建的同名测试库；因此索引与测试库必须同生命周期，结束前精确清理，旧候选不能沿用于下一轮新数据库。

这里还保留了一次实际教训。7B首轮拒绝测试曾临时改真实连接的NAME，再由查询捕获上下文打开了开发连接；恢复NAME没有切换已经打开的连接，pytest后续清理误清开发4张表。问题根因是测试修改了真实连接目标，且只看目标函数SQL漏掉连接初始化和teardown，不能以“商品SQL为0”宣称安全。已经修正为仅替换模块内连接引用的配置替身，正常fixture前后核对实际数据库；授权恢复后139条记录逐字段核验一致。事故事实见[脱敏记录](../../verification/phase-7b-test-isolation-incident.md)，首轮通过结果不能当隔离安全证据，也不能包装成新增系统恢复能力。

本页仅引用事故根因、保护与核验结论，不复制个人行值、凭据、原始日志或恢复候选。本轮知识库整理没有连接开发数据库，也没有重跑这些测试。

## 7. 如果重新做，我会怎样补新鲜度

我会保留MySQL交易事实与ES可重建副本的分工。原选择先用手动重建，是为了以最小代价验证匹配语义、当前事实回读、短页合同和发布结果；它适合学习与隔离演示，但如果真实运营要求改名、新增后及时可搜，长期人工操作不够。

| 重做候选 | 解决的真实缺口 | 新增代价与采用条件 |
| --- | --- | --- |
| 可重复的手动/定时全量重建 | 数据量小、更新少，允许一段陈旧时间 | 要有持久构建记录、来源代次、调查与安全清理；定时任务也会失败，需可见状态 |
| 提交后发布商品变更任务 | 修改后触发索引更新，降低正常路径延迟 | 数据库已提交但任务未发出的窗口仍在；任务可靠性、删除与分类批量变化需要规则 |
| Transactional Outbox（事务发件箱：业务变化与待发布记录同一数据库事务保存） | 当需要可靠捕获每次应同步变更时覆盖漏投 | 新表、扫描发布、消费者幂等、版本顺序、补漏与运维成本；当前未实现 |
| CDC（变更数据捕获：读取数据库日志生成变更流） | 希望覆盖多写入口的变更 | 日志与权限、模式演进、重放及运维更复杂；对当前规模未必划算 |

已有RabbitMQ/Celery支付链路可以提供基础设施参考，但“消息发出”不保证ES已更新。商品连续改价/改名时，旧任务晚到可能覆盖新版本；重复任务、商品删除、分类隐藏、重建与增量交错都要有明确处理规则。需要版本或可重复读取当前事实的策略，以及全量核对路径；不能只加一个`on_commit(...delay...)`就宣称强一致、无漏投或实时同步。

我会先把业务要求说成可检验的目标，例如“普通修改允许多长时间不可搜索；下架必须如何防止展示；故障后可否人工重建”。再选择最小方案，保留当前MySQL可见性回读，并验证连续修改乱序、重复、删除、发布失败与补漏。只有这些缺口成为本期目标，才落地同步；本轮先完成已有知识的解释，不自动扩展实现或实验。

## 8. 面试表述的证据边界

当前能够用历史真实隔离结果说明：陈旧候选被当前规则过滤、价格与库存提示来自MySQL、短空页不补齐、真实ES离线搜索503且旧浏览仍可用、完整来源与别名约束被检查、手动重建可改变新请求候选。7C最终新在线8项包括5项真实ES/MySQL与3项无数据库单元/注入，不能全部称真实依赖故障；7D新增5项的边界见[索引切换页](04-index-switch.md)。

当前不能声称：ES已经比MySQL更快、普通开发或部署启用、自动同步、跨页快照、全量当前可见count、生产故障切换、恢复SLA或个人已独立掌握。性能与生产容量未通过这些证据建立。解释能够覆盖实际正常、陈旧、故障和重建边界就停止整理，把后续学习时间留给项目理解、编码与计算机基础。
