# 中文商品怎样被搜出来，为什么还会漏匹配？

2026-10-11。源码快照：`7ea1963f2a7eec6018852e7d3c17b007d1e6d190`。[搜索总览](../search-current-overview-study-guide.md) · [文档核对记录](../../verification/search-interview-knowledge-base-publication.md)。

**当前ES把名称和描述转换成词项，要求全部查询词项在同一个字段里匹配；它没有要求词序相同，也没有理解中文词义。** 这让部分换序输入可以命中，也使单字或跨空格的输入出现漏匹配。面试需要用实际词项说明原因，而非只说“用了中文分词”。

## 1. 索引保存什么，为什么这些字段足够

Index（搜索索引）是供ES检索的一组商品副本。每份文档来自当前有效商品与有效分类，仅有五个字段：

| 字段 | 用途 | ES类型 |
|---|---|---|
| `product_id` | 把候选交给MySQL，并作为同分排序依据 | long整数 |
| `slug` | 原型结果中识别商品 | keyword完整值 |
| `category_slug` | 分类精确过滤 | keyword完整值 |
| `name` | 名称文本检索 | text，使用catalog_cjk |
| `description` | 描述文本检索 | text，使用catalog_cjk |

Keyword（完整值字段）适合分类标识这样的精确匹配；Text（分析文本字段）先生成词项，再按词项匹配。名称与描述采用同一个分析器，使建索引和查询对文本使用同一套规则。

这里不因缺货或无SKU排除商品：搜索服务的是发现商品，有货与最低价稍后由MySQL生成。**价格和库存不进入索引**，能减少易变化业务字段带来的同步责任；搜索文档本身仍会因名称、描述、分类和可见性变化而陈旧。

Mapping（索引字段规则）设置`dynamic="strict"`，没有声明的字段不能悄悄进入文档。这是约束文档形状，不是业务数据完整性证明。索引使用单分片、零副本，属于本地隔离验证配置，不能说已经具备节点故障切换能力。

字段来源与规则见[公开商品导出](../../../backend/apps/catalog/search_prototype.py#L61)和[索引定义](../../../backend/apps/catalog/search_prototype.py#L77)。

## 2. 无线鼠标怎样变成可查找的词项

Analyzer（文本分析器，把文字转换成检索用词项）在当前索引叫`catalog_cjk`，使用内置CJK且`stopwords=[]`。这避免添加第三方中文插件；它不是基于词典识别“无线”和“鼠标”的中文语义分词器。

Phase 7B实际调用ES `_analyze`得到：

| 输入 | catalog_cjk词项 | 本例说明 |
|---|---|---|
| `无线鼠标` | `无线`、`线鼠`、`鼠标` | 连续中文形成相邻双字项，跨词边界也有`线鼠` |
| `无线 鼠标` | `无线`、`鼠标` | 空格阻断了`线鼠`这项 |
| `标` | `标` | 单字查询不是自动展开到含它的所有双字项 |
| `M1` | `m1` | 此型号例子做了英文大小写归一 |

同一组数据中的standard分析器把`无线鼠标`分成`无`、`线`、`鼠`、`标`。这只是实际词项对照，不代表把分析器切成standard就解决中文搜索：候选、排序和噪声都需要按同一组业务输入重新验证。

可把当前机制理解为：建立索引时先生成词项与商品的关联；查询时再生成查询词项并找关联。ES不是逐件商品重新执行MySQL的完整子串判断。**查询单字`标`时，包含“无线鼠标”的文档并没有因此拥有单独的`标`词项**，所以这组数据没有命中。

## 3. AND和best_fields到底要求什么

核心查询来自[文本与分类条件](../../../backend/apps/catalog/search_prototype.py#L20)：

```python
text_query = {"multi_match": {
    "query": keyword, "fields": ["name^3", "description"],
    "type": "best_fields", "operator": "and", "zero_terms_query": "none",
}} if keyword else {"match_all": {}}
query = {"bool": {"must": [text_query], "filter": []}}
if category:
    query["bool"]["filter"].append({"term": {"category_slug": category}})
```

`multi_match`在多个字段上执行文本查询；这里`best_fields`配合`operator="and"`，意味着名称满足全部分析词项，或者描述满足全部分析词项，才能命中。不能把一半词放在名称、另一半放在描述，就当作已经满足。

例如查询`蓝牙 耳机`：名称为`蓝牙`、描述为`耳机`的商品在该实验中不命中；名称为`蓝牙 耳机`的商品命中。跨字段拼接是另一种业务语义，当前没有采用。

**这里不是match_phrase（要求词项位置与顺序的短语匹配）。** 查询`鼠标 无线`生成`鼠标`和`无线`，这些词项同时出现在商品的名称即可，不必以输入顺序连续出现。这正是它与完整包含匹配的重要区别。

`name^3`为名称匹配增加评分权重；不是“名称命中分数永远是描述的三倍”，也不是名称商品在任意数据中永远排第一。词项频率、字段长度等仍会影响评分。本项目只在等长名称/描述互换的固定对里观察到名称6.5429316、描述5.8075876，不能把这组数字泛化。

分类是`filter`里的精确条件，不负责提高相关性分数。候选按`_score`降序、同分`product_id`升序；这个ID顺序用于确定同分顺序，不表示商品越新越值得展示。

原型允许空词查全部用于实验；独立顾客搜索API要求非空词。因此`match_all`的原型行为不能说成新搜索API也把空关键词当作浏览。

## 4. 同一组商品上的命中与反例

7B用12件人工商品，其中10件构建时可见，按预先指定商品集合核对结果。下表是这组数据的实际结果，数量不代表全站搜索质量指标：

| 输入 | 原MySQL完整包含 | 当前ES词项规则 | 为什么 |
|---|---:|---:|---|
| `无线鼠标` | 5 | 5 | 这五件名称或描述满足完整连写文字和三个词项 |
| `无线 鼠标` | 1 | 6 | MySQL必须包含中间空格；ES只要求无线与鼠标 |
| `鼠标 无线` | 0 | 6 | ES不要求词项按输入顺序相邻 |
| `标` | 6 | 0 | 子串命中不等于索引拥有单字词项 |

还有一个容易误判的反例：查询`无线鼠标`会要求`线鼠`，名称`无线 鼠标`却没有这项，因此未命中；把查询也写成`无线 鼠标`才会命中它。不能只背“ES支持分词”，忽略空格导致的查询差别。

名称命中、描述命中、分类交集、同字段AND、相同文本同分ID顺序和m1型号都保存了独立预期。详见[7B验证记录](../../verification/phase-7b-search-index-prototype.md)及[修正后的在线原始JSON](../../verification/phase-7b-search-index-prototype-online-final.json)。这些是2026-10-10的隔离实测，本轮没有重新调用ES。

## 5. 搜得到之前，还要证明索引真的建完

导出商品后创建随机新候选，不先删除旧成功索引。Build（构建）包含几个不同门槛：Bulk逐项写入成功，refresh让写入可以被搜索看到，count和失败分片核对确认数量，再把来源/完成元数据写成已完成。

当前索引元数据是`search_schema=1`、`source_database=test_project_one`、`build_complete`。开始时为未完成；通过门槛后才改成完成，新请求也会读取此标记。这比仅靠构建器进程内的ready集合更持久，但它不是内容签名，也没有记录同名测试库的数据代次。

关键完成门槛来自[构建结果核对](../../../backend/apps/catalog/search_prototype.py#L129)：

```python
refreshed = self.client.indices.refresh(index=index)
counted = self.client.count(index=index)
if refreshed["_shards"]["failed"] or counted["_shards"]["failed"]:
    raise RuntimeError("Search index validation returned failed shards.")
actual = counted["count"]
if written != len(documents) or actual != len(documents):
    raise RuntimeError("Incomplete search index build.")
self.client.indices.put_mapping(index=index, _meta=build_metadata(True))
self._ready.add(index)
```

前面使用Bulk的逐项错误检查。真实实验注入一份类型错误的文档后，Bulk请求HTTP200，但一项400，合法项仍写入；失败候选只有1份文档，不能进入可查询集合，旧完整索引仍有10份。**HTTP成功只表示收到请求结果，不能等同于所有文档构建完成。**

数量相同也不能证明所有名称、描述与分类正确；原型另用固定商品集合和实际响应核对字段/结果。重建与安全切换的完整过程见[索引重建与发布](04-index-switch.md)。

隔离验证也有必须保留的历史限制：7B首轮测试曾通过临时修改真实连接目标的错误写法误清开发库4表，不能把首轮通过当成隔离安全。后来改为替换模块连接引用的替身，并在明确授权后恢复139条记录、逐字段核对。这里仅引用[公开脱敏事故记录](../../verification/phase-7b-test-isolation-incident.md)，不复制原始行值或恢复材料；恢复事实不能包装成搜索功能的新增能力。

## 6. 为什么这样选，替代方案会改什么

内置CJK的优点是无需安装插件，当前词项生成、命中和反例都能复现；代价是它不理解业务词语，同义词、纠错和中文单字/空格体验尚未解决。

| 候选改变 | 能针对什么问题 | 新成本和范围变化 |
|---|---|---|
| 词典型中文分析器或专门字符切片 | 改进明确业务词与单字输入的匹配 | 插件/词典或更多词项成本，仍需建立质量样本，不能先断言效果 |
| combined_fields等跨字段查询 | 允许名称“蓝牙”加描述“耳机”共同满足 | 改变当前“至少一个字段满足全部词项”的合同，可能多出噪声 |
| match_phrase | 需要把词序和位置作为约束 | 会改变当前换序可命中的体验，不是当前实现 |
| 同义词或纠错 | 顾客使用别名、错别字 | 需要业务词维护、误召回控制和独立证据，当前未实现 |

选择不只看命中条数。把所有商品都召回也能提高“找到”的数量，却可能让顾客翻很多不相关结果。实际需求应同时定义该找到什么、不该找到什么和该优先展示什么。

## 7. 如果重新做，我会先改哪里

**我会先把单字、空格、换序和跨字段反例变成明确的搜索需求，再决定分析器与查询类型。** 原本选内置CJK，是为了先在一个可控原型中验证索引和副本边界，这个顺序仍有价值。

会保留最小搜索文档和MySQL回读价格库存；会改进的是，不把当前分词器当作通用中文搜索默认答案。若业务要求`标`也应找到鼠标，或连写/空格应等价，就用相同人工商品和查询样本比较候选规则，核对漏匹配和误匹配，再决定是否值得付插件、索引空间与查询维护成本。

改变分析器通常需要重建已有索引，不能只修改一个Python查询参数就假装旧词项已经变化。新成本是词项与排序验证、重建发布和历史副本清理；采用门槛是明确重要输入变好且噪声可接受。本轮只解释已观察规则，不自动新增分析器、同义词或搜索质量实验。
