# Phase 4B：让旧请求回填的缓存不再被新请求使用

## 本片前后变化

以下描述 Phase 4B 完成时的变化；后续进度见[学习导航](README.md)。

- **开始前**：提交后删除缓存仍会被旧请求回填，后来的浏览请求可能再次命中旧值。
- **本片改变**：在详情首条 SQL 前捕获随机代号，同一请求始终读写该代；目录保存提交后切换全局代号，旧回填只能进入旧代。
- **完成后与边界**：成功换代后开始的新请求不读旧代，命中仍有上架 SQL；换代失败或提交后崩溃仍可旧读，且改一个商品会让整个目录冷启动，尚无回源保护。

**后续衔接：** [Phase 4D 请求合并](phase-4d-detail-singleflight-study-guide.md)已完成；中间的重复回源测量见[Phase 4C 基线](../verification/phase-4c-cache-bursts.md)。

## 这一步完成什么

本段属于 Track B / Redis 缓存一致性，采用 Depth / Learning Mode。
目标是关闭已观察到的“提交后失效，被慢请求重新填旧值”的读取窗口。
这里使用 Generation（缓存代号：区分修改前后两批缓存）划分 Key，
不修改商品表，不引入锁、Lua 或消息队列。

完成标准是：**目录修改成功提交，并且提交回调成功换代后，才开始的新请求
不会读取旧代详情。** 在途请求可以返回它之前看到的结果，旧副本也可以
物理写入旧代；我们修正的是它对后续请求的影响。

这一步没有保证 MySQL 和 Redis 强一致。Redis 换代失败、提交后进程崩溃等
问题仍需后续可靠失效或持久版本方案解决。

## 从实际业务理解问题

页面展示商品价格和有货提示，帮助顾客选择 SKU；下单时后端仍重新读取
MySQL 的价格、可售状态和库存。因此旧缓存不会授权超卖或决定订单金额，
但会让顾客看到过时的信息，形成“页面报价与结算不同”的体验。

三个具体例子：

1. 正常浏览：首次详情查询未命中，读取 MySQL 并回填；后续请求命中同代。
2. 管理员改价：旧请求之前读到 129 元；改为 159 元并成功换代后，新请求
   读取新代，缺少副本时从 MySQL 获取 159 元。
3. Redis 换代失败：MySQL 已保存 159 元，但代号没变。服务恢复后旧缓存
   仍可能展示 129 元。这是保留的故障边界，不能说成已经解决。

第 2、3 项中下单都继续以 MySQL 为准。缓存的作用是改善浏览读取，
订单、库存和支付的不变量由原事务、约束、行锁及状态规则维持。

## 原方案为什么会失败

| 顺序 | 请求 A：浏览 | 请求 B：管理员修改 |
| --- | --- | --- |
| 1 | 缓存未命中，读到旧值 | |
| 2 | 暂停在回填之前 | 修改 MySQL 并提交 |
| 3 | 仍暂停 | 删除缓存 |
| 4 | 把旧值写回同一个 Key | |
| 5 | 后来的请求命中旧值 | |

`on_commit` 解决的是“事务还没成功就失效”和“回滚仍误失效”的问题。
它不能取消请求 A 已经读到的结果，也不会自动阻止 A 在删除之后回填。

Race Condition（竞态）表示执行先后顺序会改变结果。
分析时把两个请求拆成数据库读取、提交、失效、回填等步骤，比只看一个函数
从上到下运行更容易发现错误。

## 现在怎样运行

代号实际是 32 位随机 UUID 十六进制字符串；下面用 `g1/g2` 简写。

```text
Vue 商品详情页
→ GET /api/catalog/products/{slug}/
→ Django 路由及公开只读 View
→ 先从 Redis 取得代号 g1
→ MySQL 查询 Product + Category，检查商品及分类上架状态
→ GET detail:v2:g1:{product_id}
   ├─ 命中：返回公开 JSON
   └─ 未命中：MySQL 预取 SKU + Inventory
       → 原 Serializer → SET detail:v2:g1:{product_id} + TTL → 返回

管理员保存 Product / Category / SKU
→ MySQL 写入并提交
→ on_commit 把全目录代号切换为新的 g2
→ 后来的请求取得 g2，读取 detail:v2:g2:{product_id}
```

对应旧请求的关键时序：

| 顺序 | 旧请求 A | 修改请求 B | 后来的请求 C |
| --- | --- | --- | --- |
| 1 | 捕获 g1，读取旧值 | | |
| 2 | 暂停 | 提交新值，切换 g2 | |
| 3 | 仍暂停 | | 捕获 g2，从 MySQL 建立新代 |
| 4 | 把旧值写到 g1 的 Key | | |
| 5 | | | 再次读取 g2，旧 g1 不影响结果 |

Logical Invalidation（逻辑失效）表示旧副本可以仍在 Redis，但正常读取
不再选择它；它与立即物理删除不同。旧详情保留原 25–35 秒 TTL，随后自然
过期；代号 Key 不设 TTL，一个命名空间保留一个代号 Key。

**代号必须在任何详情数据库读取之前捕获。** 如果先读取旧 Product，再取得
修改后的 g2，就会把旧 Product 写进新代，重新产生问题。只把版本读取放在
SKU 查询前仍不够。

请求不能在回填时重新取得代号；应始终用请求开始时捕获的那一代。

## 初始化为什么使用 SET NX 和随机值

Redis 的 `SET ... NX` 表示只在 Key 不存在时写入，用于处理两个请求同时
发现代号不存在的情况。代码流程为：GET → 缺失则 SET NX 提议值 → 再 GET
实际获胜的值，而不是各自使用自己的提议。[Redis SET 官方说明](https://redis.io/docs/latest/commands/set/)

代号不能简单地在丢失后重置成 `1`，因为 Redis 中可能仍有 `代1` 的旧详情。
随机新代号避免重建时重新选中旧命名空间；这不等于解决 Redis 恢复旧快照
或 UUID 理论碰撞等所有可能情况。

## 为什么选择这个方案

| 方案 | 能解决什么 | 成本与限制 |
| --- | --- | --- |
| 只删除 + TTL | 实现简单，回滚与普通失效易维护 | 已实际复现旧值回填 |
| 延迟再删一次 | 可能缩短常见回填窗口 | 延迟难覆盖任意慢请求，还需要可靠调度；不能给严格保证 |
| WATCH 条件回填 | 原子判断版本未变后才写入 | 需要监视、事务和失败处理；普通 GET 比版本后 SET 仍有竞态 |
| 全局代号 + 分代 Key（本段） | 成功换代后，新请求不选择旧代 | 目录任意写入使全部详情逻辑失效，多一次 Redis GET，旧副本短期占内存 |
| MySQL 持久版本/每商品版本 | 可进一步细化失效范围或强化故障恢复 | 扩大表结构和所有写路径，分类与 SKU 联动维护更复杂 |

当前项目目录规模小、写入口少。先用全局代号建立正确性证据，避免为了局部
失效就扩大数据库设计。以后如果实际测得改一个商品导致大量热点回源，再
比较每商品/分类版本。现在没有测得这个成本的生产规模，也没有宣称这个
方案在性能上优于其他方案。

## 面试中可能遇到的问题

| 追问 | 回答要点 |
| --- | --- |
| 先更新数据库再删除缓存，就一定一致吗？ | 不一定。旧读可以在删除后回填；给出 A/B 的实际时序。 |
| 为什么不直接更新缓存？ | 完整详情依赖商品、分类、SKU 和库存，写路径拼整份副本更复杂；并发旧写同样要协调。 |
| 你的版本号什么时候读取？ | 任何详情数据库读取之前，并在本请求中固定；读完数据库再取新版本会污染新代。 |
| 旧值最后还是写进 Redis，算解决了吗？ | 本段保证的是后续请求不选择旧代；旧代写入与当次旧响应允许，旧副本靠 TTL 回收。 |
| 为什么不是分布式锁？ | 当前问题可以通过 Key 隔离解决；锁还要处理持有时间、超时、释放和故障，不必先增加这些负担。 |
| 版本 Key 丢了怎么办？ | 用随机 UUID + SET NX 重建，再读获胜者；不能复用可能已有旧副本的初值。 |
| Redis 失效失败怎么办？ | 数据库保存不报错，连接失败回源；恢复后仍可能旧读。TTL 是兜底，本段没有可靠失效补偿。 |
| 这是强一致方案吗？ | 不是。MySQL 提交到 Redis 回调之间有窗口，提交后崩溃或换代失败也未解决。 |
| 改一个商品会怎样影响其他商品？ | 当前全局换代，其他详情也冷启动；之后依据回源量和命中率测量再细化。 |
| 命中几条查询，性能提升多少？ | 命中仍 1 SQL，现在还有代号和详情两次 Redis GET。只能报告实际查询量，没有足够性能实验不能报提升倍数。 |
| 如何保证缓存价格不会造成少收款？ | 下单 Service 重新读 MySQL 价格并生成订单快照，缓存仅供浏览。 |
| 如何证明这不是偶然通过？ | 使用事件同步制造固定旧读窗口；修正前断言失败，修正后允许旧 SET 仍发生但后续读新值。 |
