# 订单列表联合索引：从实验到正式迁移

2026-10-09。基线e85e592；本片源码校验值见[正式查询计划](../verification/phase-3-order-list-index-plans.json)。配套[验证记录](../verification/phase-3-order-list-index.md)。**模型与迁移已完成，实际生效只在隔离测试库验证；开发库尚未应用。**

## 1. 这片补齐了什么闭环

订单读业务仍是“登录 → 查看本人订单 → 翻页 → 进入详情”。上一片已经发现：首页只返回20单，却读取本人5,000单后排序；隔离候选索引可以消除这一步排序。

这片把候选写成项目可维护的结构变更，补齐**证据 → 模型声明 → 数据库迁移 → 回归与真实计划**。你现在能解释的重点是：为什么选这些字段、怎样让其他环境重现索引、怎样确认结构变化没有破坏业务。

## 2. 核心设计：过滤字段在前，排序字段在后

重要代码只需要看Order模型中的这一处：

```python
indexes = (
    models.Index(
        fields=("user", "created_at", "id"),
        name="ordering_order_user_created_id",
    ),
)
```

Composite Index（联合索引）按多个字段顺序组织查找结构。模型里的user在数据库对应user_id；先固定登录用户，再沿created_at、id的顺序读取其最近订单。id负责同一创建时间下的确定顺序。

索引采用和上一片候选相同的升序字段；本轮MySQL实际反向扫描它满足`-created_at, -id`。没有改查询或强制指定索引，是否采用由数据库优化器选择。

它是**普通非唯一索引**。原`(user, creation_scope, idempotency_key)`唯一约束继续负责请求幂等；排序索引与业务唯一规则解决不同问题，不能为了减少索引数量删除原约束。

## 3. 难点一：模型声明、迁移文件和数据库生效是三个状态

Migration（数据库迁移）记录数据库结构怎样从旧版本演进到新版本。只有修改models.py，不会让已经存在的数据库自动多出索引；0005_order_list_index把AddIndex操作记录下来，并依赖0004。

相较于临时手敲CREATE INDEX，模型与迁移一起保存能让新环境重建同一结构，也能追踪正向与反向操作。反向迁移是执行相反的结构操作，不能把它理解成任意DDL失败后都有普通事务回滚保证。

本片在可销毁MySQL测试库里实际执行`0004 → 0005 → 0004 → 0005`。每一步核对预存订单、地址、明细和接口响应完全不变，并保留原幂等唯一约束；finally恢复0005。检查的不只是迁移文件能否导入。

开发库没有执行migrate，因此当前本地演示接口不能据本片直接宣称已采用新索引。以后应用到已有数据的库时，要先确认目标库、现有索引和迁移影响；本片没有测量大表建索引耗时或期间的锁等待。

## 4. 难点二：正式索引生效后，哪些成本还在

正式0005创建的索引在本轮真实MySQL计划中被采用。本人/他人各5,000单，每单一个地址、两条明细；首页和第201页的结果仍完整属于本人。

| 实际步骤 | 首页 | 第201页（OFFSET 4,000） |
|---|---:|---:|
| 订单索引步骤输出 | 20行，反向扫描 | 4,020行，反向扫描 |
| 订单排序Sort | 无 | 无 |
| 地址索引查找loops | 20次 | 4,020次 |
| COUNT覆盖索引步骤输出 | 5,000行 | 5,000行 |
| 返回订单 / 明细 | 20 / 40 | 20 / 40 |

COUNT聚合最终输出1行，仍需统计5,000笔本人订单；OFFSET仍经过被跳过的结果。items查询还有自己的40行排序，因此只能说**消除了订单排序**，不能说所有查询都没有排序。

本片是迁移与路径验收，每页只做一次计划观察，不重复上一片五轮计时，也不报告新的性能提升比例。上一片的耗时仍是历史本机合成结果，不能包装成上线收益。

## 5. 为什么这次只落地索引，以及一个容易漏掉的证据问题

保留分页、快照和查询代码，只正式表达已有证据支持的索引，能控制改动并清楚解释收益来源。代价是额外存储和订单写入时的索引维护，本片没有量化；COUNT、深OFFSET、页码漂移和大订单items仍有成本。

游标分页可以针对深页继续评估，但会改变任意跳页与接口；先取ID再联表可能减少深页地址查找，但会增加查询阶段；摘要响应与缓存又涉及展示或失效规则。它们本片没有实现或实测，当前没有必要一起改。

另一个真实难点在实验本身：测试库默认会应用最新迁移。正式索引加入后，旧“无索引基线”实验已经不能直接沿用，否则会把带索引状态当成原基线，再建立重复候选。

本片按索引的**列顺序**识别`user_id, created_at, id`并明确拒绝这种错误基线，不只判断名字。迁移到0004时允许旧基线检查，恢复0005后检查应拒绝；历史实验要在e85e592的隔离版本复现，旧原始记录保留。
