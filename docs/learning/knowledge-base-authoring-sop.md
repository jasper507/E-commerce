# Project One 知识库写作规范：面试优先，业务与证据贯通

2026-10-08，项目拥有者明确要求以后知识库采用此方式。本规范用于学习资料，不新增业务架构或技术采用决定。

2026-10-11补充：每个业务专题以完整业务流程为主线，重要步骤配适合的流程/时序/状态图，并附有解释价值的核心代码；正文允许详细，但把篇幅集中在关键规则与难点上。每篇增加“如果重新做”一节，说明真实限制、原选择理由、具体改变、新成本和所需证据；独立项目复盘页作为汇总。此项明确配图要求适用于已授权整理的知识库资料，覆盖下文默认无图在这些资料中的限制。历史切片与原证据保留日期，模块总览讲当前状态，不把重做候选写成已实现，不新增末尾测验。

### 本轮重构的最高优先级：帮助拥有者准备项目面试

拥有者再次明确“面试优先级最高”，并批准重构项目入口、支付与Redis。此要求覆盖这些知识库资料中将“简短”或“通常1–2处代码”当作深度上限的解释；保留历史切片的原记录，不统一改写所有旧指南。

完成标准是读者能独立解释：具体问题是什么、当前机制怎样运行、为何选择它、并发或失败时发生什么、替代办法有什么代价、真实证据支持到哪里，以及重新做会如何改变。**提到名词、列齐章节或增加字数，都不能代替讲透问题。** 不能只给供背诵的结论而省略推导，也不能为了面试好听夸大生产能力、强一致、无死锁或自动恢复。

- **项目入口讲全局。** 串起身份、购物车、快照金额、建单预占、付款核销、关闭与履约；解释MySQL、Redis、Lua、MQ、ES的责任，以及三条主线的失败、选择、证据和代价。普通支持模块提供准确入口，不在总览复制所有正文。
- **模块总览建立地图，问题页讲透机制。** 页面按业务问题组织；支付保留已有问题节点，Redis可将现有长文分为问题页。历史切片作为演进证据，不要求按阶段编号背诵。
- **关键失败要有具体过程。** 例如响应丢失后重放、两个不同事件竞争同一订单、旧请求跨过失效再回填、T1已提交但Worker消失。标明谁取什么锁、检查哪个状态、何时提交或回滚；关键过程缺失时应补深。
- **代码按解释需要选择。** 保留取锁、终态门槛、事务、原意图复用与预算等真正支撑设计的片段。通常少量即可，必要时超过1–2处；不通过加代码清单制造完整感。摘录外的前置条件、后续提交及异常边界必须交代，不能只用几个字段加减证明并发正确。
- **每个业务专题有重做选择。** 从已观察痛点或明确业务需求出发，说明为何原方案当时合理、保留什么、候选改变什么、新增成本和采用条件。已存在的恢复命令不能写成未来才新增；计划不能写成已经实现。
- **图服务理解。** 复用适用的原生画板，配等价文字与本地可编辑来源。新图须在授权范围内，遵守渲染、远端读回与实际预览要求；不把数量作为质量指标。
- **面试优先不代替技术真实性。** 自己的方案推论、公开岗位要求和候选人一手面经分别标明；未经查证不称必考、统计频率或录用保证。AI整理完成不等于拥有者独立掌握，不自动追加末尾题目和参考答案。
- **更新有范围与停止条件。** 同步已变化的当前总览及相关子页，保留历史日期；先使用足够支持解释的已有证据。文档重构不自动触发业务实验、部署启用或新增实现，避免挤占算法、语言、数据库、网络与操作系统基础学习。

## 每个切片固定交付两份材料

同日拥有者进一步要求：每完成一个切片，都同时交付验证记录和学习指南，并相互链接。指南讲清本part的业务闭环、重点难点、少量关键机制/代码、设计与替代方案、证据边界、缺口和下一步；不能只列文件和测试数量。

2026-10-08的精简要求保留为普通切片指南默认：不放图、不做源码文件/函数导览、不追加末尾自检和参考答案；通常只挑1–2处重要代码，常规接线与框架样板只简述，不逐行讲解。完整性以关键问题是否讲清为准，不以章节、字数或代码数量为准。**对已按2026-10-11新要求授权整理的知识库，以上“无图”与1–2处惯例不作为限制；遵循面试所需深度，仍不做无关代码导览或自动末尾练习。**

2026-10-10阅读改进：正式指南开头统一增加“本片前后变化”，用“开始前 → 本片改变 → 完成后与边界”说明演进；纯实验/选型片明确只增加证据或决定，不能写成实现已经改变。综合专题用“本专题前后变化”。链接[学习导航](README.md)与真实后续片，正文保留阶段日期；旧下一步已完成时新增衔接说明，不把历史证据改写为本轮实测。新指南继续精简；维护旧文档时不因排版自动删掉原材料。

仅补文时复用该片已有验证记录，注明本轮静态检查与历史实测来源；不为归档自动重跑应用或外部实验。源码核对、图渲染与视觉检查属于文档检查，不能当作功能/性能测试。最终答复提供两份材料入口，个人理解仍需独立验收。

## 从读者要解释的问题开始

正文先讲具体业务场景和用户经历，再解释为什么选择一种方案。技术名词、代码清单和阶段编号不能代替设计理由。每次整理先说明能独立掌握的工程能力、可回答的面试追问及最小可信证据；不声称必考、频率或录用保证。

每个问题页按下面的逻辑组织，可以按实际需要合并短节：

1. **业务场景与前后值**：谁遇到什么条件？使用本项目订单、活动价、库存与状态举例。
2. **必须守住的规则**：不超卖、不重复效果、金额可信、旧订单不污染新订单等。
3. **为什么采用当前方案**：原方案有什么限制，本方案具体改变哪一步。
4. **替代方案与取舍**：比较一个有意义的选择；区分实际对照与未实测候选。
5. **关键业务流程**：说明与难点有关的提交、取锁、等待、重放和失败；需要时以具体值、两执行者交错或状态变化详细推导。常规接线不展开，已授权知识库配适用图并保留等价文字。
6. **收益与代价**：优先比较相同业务产出；说明重试、等待、连接、依赖和恢复成本。不能把拒绝更快等同于购买更快。
7. **真实核心代码**：核对文件、行号与源码快照；按必要解释选择数量，并交代省略的前后条件。代码支持业务解释，不逐行重复样板。
8. **证据与边界**：记录日期、环境、输入、终值、实际故障/注入及原始材料。历史测试不得当作本轮运行。
9. **重做、缺口与演进**：每个专题说明真实痛点、原选择理由、会改与会保留的地方、新增代价和采用门槛；未来方案标计划/候选。明确停止条件，不自动添加题目、口述模板或参考答案。个人理解可在互动中另行验收。

## 图与章节怎样配合

普通切片学习指南默认不放图。下列适用于用户明确要求图的资料及本轮已授权知识库重构；根据问题选择适用图，不以每节必须一张图作为门槛。

- 一张时序图只解释一个业务问题；优先中文参与者和动作，必要状态保留源码名称。
- 明确本次是默认同步、可选异步、历史对照还是拟议方案，不在一条线上混为当前实现。
- 用箭头顺序说明提交点和失败效果，显示重放跳过哪些步骤。避免把MQ接收/ACK当付款成功。
- 图可以是飞书原生可编辑画板，保留本地Mermaid、PNG、转换结果和实际远端预览。
- 先渲染和查看本地图，再写入远端；写入后读回正文与画板并查看实际预览。空画板不算完成。
- 不把大量表格、代码、日志塞进图；详细证据链接到仓库验证记录。

## 归档、验证和维护

- 项目资料在现有电商项目Wiki按业务模块组织。支付、Redis、秒杀与并发、未来商品搜索分别维护，跨模块用链接复用。
- 已有文章保留原链接和资源；新增材料优先新节点，导航只做最小更新。飞书目标与写入范围遵守用户授权。
- 记录创建时间、适用版本、真实代码提交与证据来源。代码链接优先固定Git提交，避免主分支后续变化使摘录失真。
- 当前总览、问题解释与历史验证记录分层维护。明确“已实现”“该环境启用”“该场景实测”三者；源码存在不代表开发库已迁移，隔离测试通过不代表独立部署开启中间件。更新最新部署或认证证据时，只补实际通过的范围，不把HTTP验收扩大成浏览器UI或交易验收。
- 重构保留既有有效节点、原链接和画板。需要替换正文时先读取完整当前内容，核对可保留资源，再读回正文、代码、链接及图；局部失败先确认已写内容，不盲目追加导致重复。新增问题页与导航必须限定用户授权的模块。
- 本地草稿、发布候选、远端响应/读回和检查记录一起保存；不得将OAuth凭据、Token、密码或真实个人信息放进项目。
- 文档/图检查通过不等于应用测试通过；为归档不自动运行数据库实验、引入依赖或改实现。
- 仅在规则变化或新风险影响结论时补实验。已足够支持目标解释就停止，保留算法与计算机基础学习时间。
