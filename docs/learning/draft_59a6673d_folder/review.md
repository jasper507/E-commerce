## 业务起点：两个人想买最后一只鼠标

普通SKU价129.00元，活动价89.00元，活动购买数量固定1。可售库存只有1件，两位顾客几乎同时点击购买。页面显示有货只是读取时的提示；最终谁买到，必须在后端交易时决定。系统要同时守住三件事：总预占不能超过库存，同一用户不能同时占多个购买名额，同一次请求重试不能建立第二张订单。

Idempotency（幂等）识别同一次请求；购买资格识别同一顾客是否还能买；库存条件更新识别还有没有商品。三个规则分别保护不同业务边界。禁用按钮只改善操作体验，不能替代后端规则。

## 从点击到付款：哪些事实一起改变

![秒杀与库存并发的飞书实际画板](C:/project-one-ecommerce/docs/learning/draft_59a6673d_folder/remote/board-00-preview.jpg)

| 业务时刻 | 订单 / 购买资格 | 库存available / reserved | 必须保持 |
| --- | --- | --- | --- |
| 点击前 | 无本次订单 | 1 / 0 | 前端提示不等于购买承诺 |
| 新单事务提交 | PENDING_PAYMENT / HELD | 0 / 1 | 订单、快照、资格、预占、RESERVE流水一起提交 |
| 原Key重复提交 | 返回原订单与当前状态 | 保持0 / 1 | 同参数200；异参数409，不再次预占 |
| 可信支付成功 | PAID / CONSUMED | 0 / 0 | 核销原reserved；不再减available，COMMIT一次 |
| 真正未付关闭 | CANCELED或EXPIRED / RELEASED | 1 / 0 | 先确认无未确认支付，再释放库存和名额 |
| 已付取消 | CANCELED / CONSUMED | 恢复available | 模拟退款与库存恢复，但成功限购资格不返还 |

Transaction（事务）把一组数据库修改当作一起成功或一起回滚的操作。下单时，服务端取本人地址、当前活动价和数量1，保存历史快照；库存UPDATE完成后仍要写Reservation和流水。任何后续异常都应退出事务，不能只留下库存扣减。支付再把原预占核销，不重新做一套下单逻辑。

## 这一版为什么选择MySQL条件UPDATE

业务要求是单SKU、数量1、集中竞争最后一件。正式代码用available>=1作为UPDATE条件，在数据库内同时可售减1、预占加1，避免应用用旧库存值覆盖新值。UPDATE仍取得写锁，可能等待，更新1行只代表库存步骤成功，整单还须提交。

我们没有只凭术语选型：先保留NOWAIT快速拒绝基线，再把条件UPDATE放进相同完整事务，验证首单提交、回滚、限购和异常无残留，最后比较有限批次下的重试与连接成本。紧张库存的同产出条件下，条件UPDATE用较少调用达到同样6张订单，支持本期选择；不代表所有负载都更快。

# 01 重复下单：幂等与限购为什么分开

同一个购买意图重试，找回原订单；换一个请求编号，也不能绕过活动限购。这两件事分别由幂等和购买资格保护，库存条件更新负责第三件事：不卖出没有的货。

适用读者：理解普通下单、正在学习并发的项目拥有者。读完应能回答“客户连续点击两次，为什么不生成两张单”“换 Key 为什么仍被拒绝”。证据来自本项目隔离 MySQL 与 HTTP 验证；不代表生产容量或真实支付。

电商项目；秒杀总览；下一篇：02 抢最后一件：为什么选择条件 UPDATE。

## 同一个点击，可能到达服务器两次

顾客抢活动商品，价格 89 元，地址 A。第一次请求已经提交，但响应丢失，浏览器不知道是否成交。若重新创建订单，就可能重复占库存、占资格；若一律报“已经买过”，顾客又找不到刚才那张订单。

Idempotency（幂等：重复执行同一意图，不额外产生一份业务效果）用来解决这个不确定结果。浏览器把购买意图保存为 K1，恢复时继续提交 K1 和原参数。服务器返回原订单 O1 的当前事实，HTTP 200；第一次新建返回 201。重放不是重新参加一次活动，也不保证响应正文逐字不变。

![01 重复下单：幂等与限购为什么分开的飞书实际画板](C:/project-one-ecommerce/docs/learning/draft_59a6673d_folder/remote/board-01-preview.jpg)

图中先查原订单，再考虑新建资格。旧 K1 始终关联 O1；资格释放后，只有新的 K2 才可能创建 O2。

## 三层保护对应三条业务规则

| 保护层 | 业务问题 | 当前规则 |
| --- | --- | --- |
| 请求幂等 | 是不是同一次购买的重试？ | 同用户、秒杀 scope、同 Key；参数摘要相同才返回原单 |
| 活动限购 | 换 Key 后能否再占一份资格？ | 同顾客、同活动项，最多一份 HELD 或 CONSUMED |
| 库存原子更新 | 不同顾客还能否抢到最后一件？ | MySQL 条件 UPDATE 只允许可售库存大于等于 1 时预占 |

scope 是请求所属业务范围。普通购物车与秒杀的 Key 分开保存，同样的字符串不会误命中另一种下单。Fingerprint（请求摘要：把决定购买意图的参数压成一个可比较的值）包含活动项 ID 与地址 ID。

```python
existing = Order.objects.filter(
    user=locked_user,
    creation_scope=Order.CreationScope.FLASH_SALE,
    idempotency_key=idempotency_key,
).first()
if existing is not None:
    if existing.request_fingerprint != fingerprint:
        raise OrderRuleError("idempotency_conflict", "该幂等键已用于不同请求。", 409)
    return _order_with_details(existing.pk), False
```

源码：锁用户、比较摘要、重放原单。K1 从地址 A 改成地址 B，返回 409，不能把同一个意图偷偷改成另一张订单。

## 为什么重放要排在活动检查之前

O1 已经成交后，活动可能结束、商品可能改价或下架，地址也可能删除。重试要读取已经提交的订单和快照，所以先识别旧 Key；只有没有原单的新意图，才重新检查本人地址、活动时间、商品可购买性和资格。

例如 O1 创建时是 89 元，后来活动价改为 99 元：K1 找回的仍是原订单快照；K2 是新的购买，必须按当前规则检查。接口仍校验登录和输入格式，重放优先不意味着绕过认证。

## 限购不能只依赖浏览器或 Key

浏览器禁用按钮只能减少误点击，顾客还能刷新、打开第二个标签页或直接发送请求。只按 Key 去重也无效，因为 K1 与 K2 是两个编号。当前购买记录与具体订单一对一关联，保留三种状态：

| 状态 | 业务含义 | 是否阻止新 Key |
| --- | --- | --- |
| HELD / marker=1 | 订单待付，资格已占用 | 是 |
| CONSUMED / marker=1 | 已成功购买 | 是；已付取消也不返还资格 |
| RELEASED / marker=NULL | 真正未付订单已经合法关闭 | 否；新 Key 可重新申请，仍检查活动和库存 |

数据库联合唯一约束为 customer、flash_sale_item、blocking_marker：marker=1 的阻挡记录最多一条；MySQL 允许多个 NULL，已释放历史可以继续保留。状态与 marker 还有一致性约束，防止把 HELD 错标为 NULL。购买记录及数据库约束。

同一用户的新建请求先取得 User 行锁，使竞争请求按顺序检查；数据库唯一约束再作为后备保护。代价是该用户的相关操作会等待，不能称为零锁或无竞争。库存、订单、资格和流水仍须同事务提交，不能只创建资格就宣称下单成功。

## 为什么选当前方案，证据到哪里为止

“每个顾客永久只有一条活动记录”比较简单，却不适合关闭后重购并保留历史；“每单一条资格 + 阻挡唯一约束”多了一份状态管理，但能明确区分 O1 与 O2，旧订单事件不会误改新订单资格。单靠 Redis 标记还要额外解决它与 MySQL 订单提交的一致性；当前基线暂不引入。

2026-10-07 的 6A 隔离 MySQL 验证：同顾客、不同 Key 的两连接竞购，只有一单及一份预占；同 Key 重放、异参冲突和唯一约束也经过检查。2026-10-08 的 HTTP 验证覆盖 201/200、异参 409、活动结束后旧 Key 重放。属于历史验收，本次归档未重跑。

6A MySQL 证据与边界；HTTP 合同证据。测试不能据此证明生产防刷、跨设备意图自动合并或全部死锁不存在。

## 业务问题：看到一件，不代表两个人都能买到

活动价 89 元，同一活动 SKU 只剩一件。A、B 分别点击购买，业务规则是最多一张订单提交，失败者不能留下订单、购买资格或库存预占。SKU 是具体商品规格；Inventory 与 SKU 一对一，每单固定购买一件。

错误的“先读取 1，再各自在 Python 判断，再写回 0”会让两个人都通过检查。历史 Phase 3 在隔离 MySQL 中固定这一交错，实际出现两订单、两预占，而库存表仍为 0/1：旧快照覆盖不能代表实际销售数量。这是普通结账的最小错误示范，不是当前秒杀实现，也不是高并发容量测试。错误基线证据

## 可选方法：正确性之外，还要决定顾客等待方式

| 方法 | 业务行为 | 取舍 |
| --- | --- | --- |
| NOWAIT 行锁，历史策略 | 先锁库存；别人持锁时立即返回 stock_busy。即使对方随后回滚，本次也已退出。 | 快速释放本请求资源，但顾客或应用要决定是否重试；繁忙不等于售罄。 |
| 条件 UPDATE，当前策略 | 数据库同时判断库存至少一件并增减库存；竞争时可能等待，取得锁后按当时库存得到 0 或 1 行。 | 让一次正在进行的请求有机会完成；等待占用连接和先前取得的锁，可能超时或死锁。 |
| 普通 SELECT FOR UPDATE | 等待取得行锁，再读取、判断并更新库存。 | 也是可行方案，步骤更显式；本期没有第三套完整事务负载实测，不能给它编造性能排名。 |

Row Lock（行锁）让同一库存记录的竞争写入按顺序执行。条件 UPDATE 仍会取写锁，并不是“没有锁”；本期适合数量固定为一件的单 SKU，不因此替换普通多 SKU 购物车、支付核销或取消释放。

## 请求怎样运行：把条件放进数据库，整单仍共同提交

下单事务先处理用户、地址、活动规则、订单与购买资格，再执行库存步骤。A 更新一行后仍未提交，B 的 UPDATE 可以等待。A 提交，B 看见可售为 0，更新零行并整单回滚；A 回滚，库存恢复为 1，B 可以更新一行，再完成自己的订单。图中省略普通字段写入，但取锁与提交仍属于完整下单事务。

![02 抢最后一件：为什么选择条件 UPDATE的飞书实际画板](C:/project-one-ecommerce/docs/learning/draft_59a6673d_folder/remote/board-02-preview.jpg)

```python
updated = Inventory.objects.filter(sku=sku, available_stock__gte=1).update(
    available_stock=F("available_stock") - 1,
    reserved_stock=F("reserved_stock") + 1,
)
# ……已知锁错误处理见下一页……
if updated != 1:
    raise OrderRuleError("insufficient_stock", "活动商品库存不足。", 409)
return Inventory.objects.get(sku=sku)
```

F expression（字段表达式）让 MySQL 用数据库中的值加减，不把 Python 的旧值写回。初始 available/reserved 为 1/0，成功预占后是 0/1；支付成功才核销 reserved。更新一行只表示库存步骤成功，后面预占或流水失败，整个事务仍须回滚。

更新零行表示没有匹配的库存行，也包括库存记录不存在；沿用当前统一库存不足响应。SQL 抛异常与零行不同。幂等键保护同一请求重放、购买资格约束保护每人限购、条件更新保护数量边界，三者不能互相替代。核心源码；完整下单事务

## 显著提升在哪里：用相同产出比较请求成本

## 业务场景：锁等不到时，不能留下半张待付订单

顾客用原 Key 买一件活动价 89 元的商品。程序已经写入订单、商品快照、地址快照和购买资格，但库存正被另一事务锁住。若等待失败后只说“库存繁忙”却提交前面的写入，顾客会留下没有库存预占的订单，甚至限购资格被占住，下一次也买不了。

因此，整个下单服务用 transaction.atomic（事务：一组数据库修改共同提交或回滚）。订单、快照、资格、库存、预占和流水必须一起成功。失败异常必须退出原事务；不要在失败事务中吞错后继续写，也不要只重跑扣库存 SQL。下单事务入口

## 先分清：库存不足、锁竞争和未知数据库故障

| 结果 | 业务含义 | 当前处理 |
| --- | --- | --- |
| UPDATE 返回 0 行 | 没有满足库存至少一件的记录；也包括记录缺失。 | 409 / insufficient_stock，整单回滚。 |
| 1205 锁等待超时；1213 死锁 | 本次没完成正常库存判断，不等于售罄。 | 库存 UPDATE 处为 stock_busy；其他下单 SQL 在事务退出后为 checkout_busy，均 409。 |
| 其他数据库错误，例如 2006 | 连接等故障，不能假装成库存不足。 | 原错误上抛，保留可调查原因；不能盲目重试或声称提交结果确定。 |

Deadlock（死锁）是事务相互等待对方持有的锁。固定取锁顺序能减少风险，不保证永远没有死锁。本项目不把所有 DatabaseError 都变成“繁忙”。

```python
except DatabaseError as exc:
    if not exc.args or exc.args[0] not in (1205, 1213):
        raise

if updated != 1:
    raise OrderRuleError("insufficient_stock", "活动商品库存不足。", 409)
```

from exc 保留原异常作为原因。MySQL 锁等待超时默认可能只回滚当前语句；应用仍要让异常离开整个 atomic，才能撤销前面的订单和资格。错误映射源码；失败合同与设计依据

## 为什么等待 5 秒：只给当前入口临时缩短等待

当前环境原会话值是 50 秒，单个库存热点长时间等待不适合这一顾客入口。选择不是修改全局 MySQL，也不是永久改变连接，而是在 HTTP 适配层读原值、暂设 SESSION 为 5 秒，再执行完整下单，事务结束后恢复同一物理连接原值。

Session（会话）是当前数据库连接的参数范围；Django 可能复用连接，不恢复就会影响后续请求。原值也可能是 17 秒，必须恢复实际读到的 17，不能写死 50。

![03 下单失败：为什么整单回滚与等待 5 秒的飞书实际画板](C:/project-one-ecommerce/docs/learning/draft_59a6673d_folder/remote/board-03-preview.jpg)

```python
with connection.cursor() as cursor:
    cursor.execute("SELECT @@SESSION.innodb_lock_wait_timeout")
    original_wait = cursor.fetchone()[0]
    original_connection = connection.connection
    cursor.execute("SET SESSION innodb_lock_wait_timeout = %s", (5,))

# try 中调用完整 atomic 服务；finally 在该服务退出后执行。
if connection.connection is original_connection:
    try:
        with connection.cursor() as cursor:
            cursor.execute("SET SESSION innodb_lock_wait_timeout = %s", (original_wait,))
    except Exception as error:
        _log_cleanup_error("restore", error)
        _discard_connection()
```

节选将常量值展开为 5 并省略业务调用，完整控制结构见 HTTP 适配源码。顺序是“事务外设值 → 完整下单提交或回滚 → finally 清理”。拒绝已有外层事务或关闭 autocommit 的调用，避免尚未结束业务事务就恢复参数。

读值或设置失败，不调用下单服务，丢弃连接并传播错误。恢复失败，安全告警并丢弃连接；不能让清理错误覆盖已经提交的成功、业务拒绝或原异常。若物理连接已经更换，不把旧值写到新连接。

5 秒是相应 InnoDB 行锁等待预算，不是整个 HTTP 请求截止时间。多个语句可分别等待，还存在认证、SQL 执行和网络耗时；等待时也占着连接与先前已取得的业务锁。

## 替代方案与代价：等待不是免费，重试不是只扣一次库存

沿用原会话值最简单，免去三条会话 SQL，但当前环境可能单次等 50 秒；改成永久或全局 5 秒会扩大到其他入口；NOWAIT 快速拒绝则把继续购买的决策移到顾客或应用。临时会话方案把影响范围限制在本入口，代价是读取、设置、恢复与清理分支，没有生产吞吐改善证明。

正式路径没有自动重试。顾客收到已知繁忙后，用原 Key 重跑完整请求：如果前次已回滚，可以重新建单；如果已有同 Key 的提交事实，就返回原订单。响应丢失时也应查原意图，不生成新 Key 猜测失败。只重跑库存 SQL 会遗漏活动、资格及幂等检查，也可能基于失败事务继续工作。

付款成功要同时确认订单、核销库存并消费资格；真正未付关闭要同时释放库存与资格。MQ 把支付通知的接收与处理分开，MySQL 仍决定交易事实。秒杀建单目前是同步 MySQL 事务，未实施“抢购请求入队后异步建单”。

## 业务先决定资格何时消费和返还

例子从库存 5/0 开始，两个数字分别是 available（可售）和 reserved（预占）。顾客下单一件后库存 4/1，订单待付，资格 HELD。支付失败与订单关闭是两种不同事件：一次付款失败，顾客仍可以在原订单上尝试付款，不能立刻把库存与资格返还给别人。

| 业务结果 | 订单 / 资格 | 库存与后续购买 |
| --- | --- | --- |
| 正常付款成功 | PAID / CONSUMED | 4/1→4/0；不再减可售；禁止新 Key 重购 |
| 真正未付取消或到期 | CANCELED 或 EXPIRED / RELEASED | 4/1→5/0；允许新 Key 重新申请 |
| Attempt 仍 CREATED/PENDING/UNKNOWN | 付款尚未确认；暂缓关闭 | 不释放，先查询原付款结果 |
| 已付、未发货取消 | CANCELED / CONSUMED | 恢复库存、模拟退款；成功购买资格不返还 |

UNKNOWN 是结果未知，不是付款失败。没有确认就释放，可能先允许第二张订单，再收到第一张付款成功，造成两份交易争夺一份资源。

## 哪些修改必须一起提交

Transaction（事务：一组数据库修改一起成功或一起回滚）保护跨表一致。成功通知处理中，锁序为 Event → Order → Attempt → Purchase → Reservation → Inventory；真正未付关闭从 Order 开始核对 Attempt，再处理 Purchase 和库存。不是所有入口都要先锁 Event。

```python
purchase = lock_flash_sale_purchase(
    order, expected_status=FlashSalePurchase.Status.HELD
)
_commit_inventory(order)
# 同事务保存 Attempt SUCCEEDED、Order PAID
transition_flash_sale_purchase(
    purchase, target_status=FlashSalePurchase.Status.CONSUMED
)
# 同事务保存 Event 处理结果
```

节选中的注释概括了省略的保存语句。完整成功分支与按原订单取锁与资格转换。资格更新异常时，已执行的库存、订单修改也回滚，不能留下 PAID / HELD 的半完成事实。

替代方案是业务提交后再补写资格：锁少一点，却增加失败窗口和补偿责任。当前把它们放在一个 MySQL 事务内，多持有一把本单资格锁，换取直接可验证的一致性。

## 为什么业务需要 MQ

同步基线在 HTTP 请求里保存通知并立即处理。库存锁竞争或处理异常会拖住这次请求；进程在入箱后中断，顾客还得等网关重发或人工恢复。我们的目标是先可靠保存收到的通知，再让后台独立完成校验和业务事务。

Message Queue（消息队列，简称 MQ：在接收方与处理方之间传递待处理工作的通道）在本项目由 RabbitMQ 保存任务消息，Celery Worker（后台执行进程）读取内部 Event ID，调用已有处理入口。业务规则没有搬成第二套，消息也不包含可信付款金额或库存决策。

![04 从付款到关闭：资格生命周期与 MQ 的业务价值的飞书实际画板](C:/project-one-ecommerce/docs/learning/draft_59a6673d_folder/remote/board-04-preview.jpg)

图里的四个边界要分开：Inbox 提交 → 发布 ID → Worker 业务提交 → 消费确认。调用网关和等待 Broker 都在数据库事务外，不能带着订单或库存锁等待网络。

异步 Webhook 的 202 表示原文已入箱；不是付款成功，也不是消息一定已可靠发布。ACK（消息消费确认：告诉队列本次投递已被确认）同样不能单独证明订单已付，须查 MySQL 的业务终态。

| 方案 | 业务收益 | 付出的代价 |
| --- | --- | --- |
| 同步 + 人工或定时 Inbox 扫描 | 系统简单，复用一个处理器 | 请求与业务处理耦合；及时性或轮询成本要权衡 |
| 持久 Inbox + MQ 后台处理 | 接收和处理分开，独立任务执行；可安排到期重试 | 增加 Broker/Worker、重复投递、漏投和中断恢复责任 |

当前默认仍同步，异步是本地开发/测试可选路径，真实 RabbitMQ 与 Worker 已有验证。尚不能声称 MQ 提高了秒杀吞吐，或天然保证“业务效果恰好一次”。秒杀库存竞争仍由 MySQL 解决。入箱后选择同步/异步；事务外发布 ID。

## 重复、暂时失败和进程中断怎样收尾

重复消息可再次到达，Event 领取资格与锁内终态判断挡住重复业务效果；不同事件指向同一成功 Attempt，也不能重复核销。MySQL 保存累计处理预算：总共 3 次包含首次，允许的暂时失败分别等待 5 秒、10 秒；未知错误、库存/资格不一致阻断调查，次数耗尽停止。Celery 不另设一份业务重试预算。

提交 Inbox 后进程可能还没发布就中断，或 Broker 不可用。人工补投重新发送原 ID，允许重复，不能把 published 当成 paid。Worker 领取 PROCESSING 后硬中断，还需要持久租约：默认 60 秒，到期只是检查资格的条件，不是死亡证明。人工恢复锁内核对状态、次数版本和截止，拿不到业务锁就跳过；修复后再补投或同步处理，预算不清零。尚无无人值守恢复时限承诺。

2026-10-05 的真实 C4 验证分别中断在领取提交后、业务未提交、业务提交后 ACK 前及退款提交后：恢复最终只核销一次或只退款一次。C3 真实停 Broker 验证提交后漏投的人工补发。这里只概括业务价值；具体命令、MQ 配置与原始过程沿用已有支付与 MQ 知识库。

## 旧订单迟到成功，不能碰新订单资格

O1 真正未付关闭，资格 RELEASED 后，顾客可用 K2 创建 O2，资格 HELD。此时 O1 收到可信成功通知，系统保持 O1 关闭、只为 O1 模拟退款，不走正常库存核销，也不按“顾客当前活动资格”去改 O2。购买记录必须按 order 定位，这是保留每单历史的业务理由。

### 业务问题：顾客以为失败，但订单可能已成立

顾客抢最后一件商品，活动价 89 元、普通价 129 元。服务器完成建单，库存从“可售 1 / 预占 0”变成“可售 0 / 预占 1”，响应却没被页面确认。如果此时自动换新 Key 再下单，后端会把它当作另一笔购买，无法用它确认刚才那张订单。限购能挡住部分新购买，却不能代替找回原结果。

Purchase Intent（购买意图）是“谁用哪个 Key，购买哪个活动项，配送到哪个地址”的固定记录；Idempotency-Key（幂等键）让后端识别同一次业务请求的重放。示例用 K1 缩写真实 UUID Key，保存内容为 {userId:1, key:K1, itemId:711, addressId:1}，不是只保存一个 Key。

### 为什么先保存完整意图，再发请求

前端先冻结四字段，并成功写入 sessionStorage（同标签页会话存储，刷新后仍可读取），随后才 POST。存储失败直接停止，没有“先靠内存继续发”的后备路径；否则刷新后丢失 Key，就破坏了本页承诺。

```typescript
try {
  saveFlashSaleIntent(original)
} catch {
  storageError.value = '浏览器无法保存购买信息，因此尚未发送下单请求。请启用会话存储后刷新。'
  return
}
intent.value = original
await submitIntent()
```

来源：冻结、保存和发送顺序；读取校验与存储。

替代方案是在内存里仅保存 Key，代码更短，但刷新就丢失，而且活动项或地址变化后难以恢复原参数。当前方案多了恢复、身份核对和错误状态，换来同标签页刷新后的原请求确认；不承诺跨设备、跨标签页或关闭标签页后的恢复。

### 完整时序：重放读取原事实，不再预占

![05 响应丢失：为什么保留原购买意图的飞书实际画板](C:/project-one-ecommerce/docs/learning/draft_59a6673d_folder/remote/board-05-preview.jpg)

图中先完成数据库事务提交，再出现受控响应丢失；刷新读取原四字段，顾客主动确认。没有自动重试或自动创建新 Key。每次发送前调用 /api/auth/me/ 核对当前身份；用户 ID 只是前端恢复检查，服务器仍以 Session（服务端登录会话）识别用户，并通过 CSRF 校验防止别的网站冒用浏览器发起写请求。

为什么列表已经无货仍能确认？后端锁当前用户后，先查同用户、秒杀 scope、原 Key 的已提交订单；同摘要直接返回原订单，再向后才是新购买的本人地址、活动和库存检查。因此活动结束、列表消失、地址不再显示或当前售罄，都不应由页面挡住原意图确认。原订单已保存成交价和地址快照，不依赖地址簿重新创建它。

```python
if existing is not None:
    if existing.request_fingerprint != fingerprint:
        raise OrderRuleError("idempotency_conflict", "该幂等键已用于不同请求。", 409)
    return _order_with_details(existing.pk), False
```

来源：先查旧 Key，再检查新购买地址。False 表示不是本次新建，HTTP 返回 200；首次创建为 201。重放返回订单当前状态，付款后可以是 PAID，不要求整份 JSON 与第一次逐字相同。

### 页面怎样区分“未确认”和“明确拒绝”

| 结果 | 业务解释与页面行为 |
| --- | --- |
| 200 / 201 且订单结构有效 | 确认订单，展示服务端状态，保留原意图；主动“开始新购买”才清理。 |
| 网络、5xx、解析失败、异常成功结构 | 结果待确认，保留原 Key 和参数，不擅自认为没建单。 |
| 403 或 stock_busy / checkout_busy | 保留原意图；403 可能是登录或安全校验问题，不能直接等同未登录。 |
| 同 Key 改地址，409 冲突 | 这是不同请求，不会修改原订单；保留原意图，先核对订单。 |
| 明确业务 code + 404 / 409 拒绝 | 进入“本次购买未成功”，例如地址不存在、活动关闭、库存不足；仍须主动开始新购买。 |

不是所有 409 都允许开始新购买，繁忙与幂等冲突被单独保留。失败分类与Session/CSRF 请求及成功结构校验共同决定结果，不能只看 HTTP 数字。

### 已有证据证明到哪一步

Phase 6E 历史浏览器验收先用 route.fetch 真正发送请求并取得上游 201，随后 route.abort 丢弃客户端响应。刷新后原四字段不变，页面虽显示无货，原 Key 真正返回 200 和同一 public_id；同 Key 刻意改地址真正返回 409，数据库事实不变。后续 Mock 支付让订单 PAID，资格 CONSUMED，库存从 0/1 变为 0/0，RESERVE 与 COMMIT 各一条。

这是真实建单之后的受控客户端丢响应，不是切断真实网络，也没有证明数据库提交结果未知时的恢复。503、畸形 200、有效 Session 下 403 为客户端响应注入；存储失败注入观察到下单 POST 为 0。历史构建和目标/回归已通过，本次知识库整理没有重新运行这些检查。记录：浏览器事实与注入边界；历史串行检查。

## 怎样解释显著提升，而不夸大

业务产出相同才能有意义地谈成本。在库存6、24位顾客、8worker、NOWAIT最多3次总尝试的三轮里，两种策略每轮都建6单；条件UPDATE每轮24次调用，对照52–55次。这支持当前条件下减少繁忙重试的结论。旅程p95和连接区间也较低，但不能把范围的端点随意配对成固定提升百分比。

库存充足且只有一次尝试时，NOWAIT更快返回的多数是拒绝；不能只看全结果延迟就说顾客更快买到了。库存充足、三次预算下连接总秒有交叠，不能说条件更新每轮都更省资源。当前方案减少重复调用的同时，仍可能等待并占住连接、事务及此前的锁。

## Redis Lua：先明确希望改变哪个业务问题

Lua脚本可以原子组合Redis内部的多个操作。若下一步目标是减少进入MySQL的无效或超能力请求，可比较可关闭的原子准入与当前MySQL路径；它只是前置保护，MySQL仍核验库存、资格和订单。若选择Redis库存预扣，则还要定义MySQL建单失败补偿、重复补偿、Redis已执行但响应丢失、取消返还与重建对账。

已有MySQL防超卖证据，所以不能用‘当前没有Lua就不正确’作为引入理由。已有订单的原Key重放也不能被新的售罄或准入标记挡住。原子性范围只有Redis，不跨MySQL。先取得明确数据库成本基线，再用同业务产出与失败终值对照；没有收益或失败边界未闭合，就不进入正式路径。

Redis官方：Lua原子执行与阻塞边界

## ES：作为独立商品搜索故事评估

Elasticsearch（ES）服务全文检索与相关性排序，适合回答‘用户怎样找到想买的商品’。当前顾客列表仅分类筛选，尚无关键词搜索基线；先确定具体查询与预期结果，再比较最小MySQL搜索和ES。不能用新增服务数量证明秒杀更强。

若实际采用ES，要将商品索引视为可重建副本：定义改名/下架同步、漏同步修复、重复或乱序更新、服务故障以及从MySQL重建。即便ES写入成功，搜索可见也可能等refresh；下单价格、库存与权限仍以MySQL为准。最小查询集效果与这些一致性证据足够后停止，不扩成通用搜索平台。
