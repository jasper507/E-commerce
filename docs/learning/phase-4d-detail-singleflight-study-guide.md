# Phase 4D 学习：从重复回源到请求合并

本步完成的是“让同一份公开详情的并发加载共享一次结果”。它属于缓存技术
主线，服务于浏览商品。分代处理旧请求回填到哪一代；合并处理有多少请求
同时加载这一代。两者分别解决一致性边界与重复工作。

## 先理解正常业务链

```text
用户打开商品详情 → GET /api/catalog/products/{slug}/
→ Django URL → 公开接口权限
→ 捕获 Redis 代号 G1
→ 每个请求各自检查 MySQL 商品与分类上架状态（1 SQL）
→ 初查 G1 的详情缓存
   ├─ 命中：返回公开 JSON
   └─ 未命中：寻找本进程内 G1 + 商品的进行中加载
       ├─ 第一个请求：再查一次同代 Redis
       │   └─ 仍为空：查 SKU/库存（1 SQL）→ 序列化 → 尽力回填
       │             → 通知等待者 → 清理登记 → 返回
       └─ 其他请求：最多等待 200ms
           ├─ 成功：共享公开结果 → 返回
           ├─ 失败：独立复查缓存/查数据库 → 返回或保留自己的查询异常
           └─ 超时：独立复查缓存/查数据库；原加载者继续运行
```

商品下架时，这次请求的 MySQL 检查先返回 404，不参加详情合并。浏览价格
和有货提示仍可能陈旧，下单服务始终重读真实 MySQL 价格和库存。

## 用具体值理解

10 人同时查看鼠标，价格 129.00。未合并时，本轮测到 9 人重复加载 SKU，
加上 10 次上架检查，共 19 SQL。合并后，一个人加载、其他人共享结果，
共 10 + 1 = 11 SQL。不是“10 请求只查一次数据库”。

如果加载者查数据库失败：该请求保留原异常；其他人得到失败通知，自己
复查/加载。下一个请求也可以成为加载者。不能把失败记录永久留在登记里。

如果加载者很慢：B 等待超过 200ms，B 独立查询，但不能删掉 A 的登记。
否则 C 到来就会建立另一份正在进行的加载，进一步增加竞争。超时限制的是
B 等结果的时间，不是 A 的工作时间，也不是 B 的完整响应时间。

管理员改价切到 G2 时，G2 请求不得加入 G1 的加载。旧请求允许返回旧值，
旧结果只能回填 G1；后来请求取得 G2 下的详情。不能为了合并率省略代号。

## 关键代码如何运行

先读 `views.py` 的 retrieve 和 load_detail，再读 `cache.py` 的
ProductDetailCache.get_or_load，最后读 SingleFlight.run。

- `load` 是一个尚未执行的函数；`lambda: self.load_detail(product)` 把
  “如何加载当前商品”交给合并器，只有需要数据库结果时才调用。
- Lock（线程锁）让“检查有没有登记并新建登记”作为一个连续操作执行，
  防止两个人同时认为自己是第一个。数据库和 Redis 调用不能放在这把锁里。
- Future（未来结果）让其他线程等待加载完成。它保存成功 payload 或失败
  标记；失败标记不包含另一个请求的数据库异常对象。
- `finally` 无论成功还是抛错都执行，负责清理进行中记录。身份检查保证
  只删除自己登记的那份 Future。
- 普通 dict 去掉 Serializer 隐含引用；每个请求创建自己的 Response。
  此机制只用于公开只读数据，不能直接复用于用户私有或事务内结果。

## 方案比较与工程能力

| 方案 | 收益 | 代价/边界 |
|---|---|---|
| 不合并 | 流程简单，请求各自独立 | 热点冷启动重复读数据库 |
| 本轮进程内合并 | 不增加服务，同进程重复加载减少 | 跨进程不合并；等待、失败需处理 |
| Redis 租约锁 | 多进程可以协调 | 过期、所有权、释放、Redis 故障更复杂 |

这段训练你区分“结果正确”和“少做重复工作”，设计线程协调和异常清理，
保留可复现基线，并按实测数据说明收益。不要把减少 SQL 偷换成提高多少 QPS。

## 面试追问与个人验收

| 追问 | 你应解释的关键点 |
|---|---|
| 为什么合并 Key 要包括代号？ | G2 不能等待/使用 G1 的结果。 |
| 为什么还要查两次 Redis？ | 注册前上一轮可能已经回填并清理；二次检查避免接力回源。 |
| 为什么不用一把全局锁包住查询？ | 不同商品也会被串行阻塞；锁只保护登记操作。 |
| 加载失败后其他请求会怎样？ | 通知失败、清理，等待者独立复查/回源；不保证数据库持续故障时成功。 |
| 等待超时能否清掉旧加载者？ | 不能；旧加载仍在，清理会允许更多加载者同时出现。 |
| 200ms 能保证接口响应上限吗？ | 不能；之后回源、原查询及其他请求步骤不受这个等待预算限制。 |
| 多个 Gunicorn worker 呢？ | 各有自己的登记，同商品仍可能每个进程加载一次。 |
| Redis 挂了是不是也保护数据库？ | 本轮没有；初次不可用仍独立回源，整体限并发另行设计。 |
| 怎么证明有效？ | 基线9/10/7次详情加载，合并1/1/1；受控4请求5 SQL；异常/超时/换代测试。 |

请先关闭参考，用自己的话回答三个问题：为什么仍有 11 SQL？为什么 G1
与 G2 必须分开？为什么等待超时不能取消加载者？

练习：在纸上画出 A 加载、B 超时回源、C 加入 A、A 完成的顺序，指出每一步
登记是否存在；再解释共享用户私有数据时，Key 至少还需要考虑哪些权限因素。
