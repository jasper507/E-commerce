**MySQL事务负责订单、购买资格与库存正确；Lua在启用时限制进入订单处理的尝试。原Key重放在MySQL事务内先认原订单，但启用Lua后的HTTP入口先申请预算，因此原Key确认也可能先429/503。** 两个检查的位置与责任不同，不能只背“先幂等，再校验库存”就省略外层准入。

这份当前总览替旧入口补齐6F之后的状态，服务于独立讲清完整请求、失败责任、取舍和真实证据。原六页的历史代码、实验日期和画板保留；新Lua问题页配启用后的请求图，本轮没有重新运行服务实验。

## 2. 启用Lua后，一次购买怎样运行

顾客发送已保存的活动项、本人地址与Key，后端先确定Session身份、CSRF及参数/Key格式。准入预算只控制格式有效的秒杀尝试，尚未查询MySQL来确认活动项是否存在。

1. 独立Redis执行短Lua脚本，对全入口共享Key同时读取、检查、计数和设置期限。首次SET保存1并带PX，后续INCR不续期。
2. 预算满返回429；Redis错误或返回无法解释返回503。两种情况都不进入后面的会话等待适配和订单事务，但Session认证仍可能有SQL。
3. 明确放行后，HTTP适配才在事务外查询原等待值、临时设5秒，再进入MySQL业务事务。
4. 事务锁User，先按用户/秒杀scope/Key识别旧订单；原参数200同单，异参数409。新单才继续查本人地址、活动与可售状态，检查购买资格，创建订单与快照、Purchase，执行库存条件UPDATE并写预占/流水。
5. 整单提交或回滚，HTTP适配恢复原物理连接会话值；恢复失败丢弃连接而不掩盖业务结果，随后才返回HTTP响应。

Lua关闭时第1–2步直接跳过，原MySQL事务与响应规则保持。当前总览原交易画板继续解释这一默认路径；启用准入后的完整时序见[07问题页](flash-sale-interview/07-lua-admission.md)及[图源](assets/flash-sale-lua-2026-10-11/lua-sequence/diagram.mmd)。

预算4且库存24时，该窗口最多4次获得进入事务的许可，并不保证成交4单：仍可能活动关闭、地址错误、限购或库存不足。Lua不扣库存，后续业务失败不退预算，也不把预算当正在执行事务的并发槽。

## 3. 为什么原Key确认也可能等待

第一次下单已经提交，浏览器却没收到响应；此时应保持原意图确认原单。启用准入后，确认请求仍先申请同一共享预算：满额429，Redis无法确认503；不能据此判断旧单不存在，也不能换新Key再买。

恢复放行后，MySQL幂等分支仍先于新单的活动/库存检查，所以当前售罄、活动结束或地址簿变化不让已存在的原订单变成新单。**售罄检查与前置准入是不同边界：前者不会阻止事务内已命中的原单，后者可以暂时阻止请求进入事务。**

这项选择减少所有被拒请求的订单处理成本，代价是旧单确认的可用性下降。先查MySQL、让旧单绕过准入是有意义的替代，会保留确认查询压力；当前没有采用。前端429/503保留原意图已静态核对，6F没有补跑浏览器端到端，也没有Retry-After倒计时。

## 4. 两种未知结果，恢复责任不同

| 未知发生在哪里 | 可能已经发生什么 | 当前处理 |
|---|---|---|
| Redis EVAL执行后响应丢失 | 已消耗预算，尚未进入本次MySQL下单 | 503，不自动重试脚本、不退未知预算，恢复后仍确认原意图 |
| MySQL已提交后HTTP响应丢失 | 已有订单、资格和库存预占 | 保留原四字段，恢复后用同Key确认原单，不重复预占 |

Lua原子性只覆盖Redis内部操作，不跨MySQL；Redis脚本错误也不自动回滚已发生写入。固定窗口到期、Key丢失或跨窗口重叠并不取消MySQL订单。实际下单、付款核销和关闭释放仍以MySQL事实为准。[支付总览](payment-current-overview-study-guide.md)

## 5. 新增证据支持到哪里

2026-10-09的[6F验证](../verification/phase-6f-flash-sale-admission.md)真实观察到：24个独立Redis客户端竞争4个预算，4放行、20拒绝；8线程处理24顾客的APIClient对照中，关闭/开启准入分别24/4次实际订单事务及建单，20个429在固定认证、既有连接的统计范围内各0下单SQL。

两组完成订单数不同，因此不能把批次耗时或SQL480→80解释为相同业务产出下的购买提速/吞吐提升。真实EVAL后主动抛超时的注入支持未知时不重试、不建单；不等于真实丢包或主从故障。最终53 passed/325 subtests包含原目标和相关回归，属于历史实测，这轮只读整理。

原6A–6E记录与六张旧图保留，当前补充6F。驱逐/重启/主从切换、Cluster、多进程、公平性、生产容量及6F浏览器链路没有新增证据，先停止扩大实验。

## 6. 如果重新做，我会保留什么、改什么

我会保留MySQL作为订单/库存/资格事实来源，并把入口保护和库存正确性分开。会更早定义旧单确认的可用性要求、共享预算对象和依赖故障政策，先解释业务代价，再决定放在哪里。

如果业务明确要求旧单确认不随下单准入阻塞，会比较受保护的独立确认入口或先查原单的成本；如果需要平滑突发，再比较滑动窗口/令牌桶；如果需要严格在途数，必须新增领取、释放、崩溃回收与租约。它们都不是当前计数改名，也未实现。

采用门槛是具体压力或体验缺口、可核对的不变量和最小充分证据。当前固定预算20次/1000ms只是默认练习配置，不直接变成生产容量。这个专题整理到能独立解释一条放行、一条429/503与一次原Key恢复即可收束。
