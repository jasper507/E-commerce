## 1. 面试收益与本片停止条件

本片练习回答：为什么这样预占库存、并发时为什么不超卖、失败怎样回滚，以及为什么选择它。
停止条件是保存有依据的策略决定，讲清 0/1 行与数据库异常的区别，明确下一片的最小落地边界。
不增加压测组合，不把方案名称或实验数量当成面试价值。

本轮项目拥有者已经确认采用条件 UPDATE，并正确预测：
库存 1，A 已预占但未提交；A 提交后，B 等待结束，更新 0 行并返回库存不足。
这个预测有“没有先发生超时或其他错误”的前提，也不能替代对整个模块的独立理解验收。

## 2. 规则怎样进入数据库

库存表保存可售 available 与已预占 reserved。购买一件意味着把一件从可售转为预占。
普通“Python 先读 1，再写 0”可能使用过时值；条件 UPDATE 让数据库在修改时同时判断是否足够。
下面是既有测试候选的库存步骤，不是本片新增的业务实现：

```python
updated = Inventory.objects.filter(sku=sku, available_stock__gte=1).update(
    available_stock=F("available_stock") - 1,
    reserved_stock=F("reserved_stock") + 1,
)
```

`F()` 表达式让计算在数据库内使用字段值执行，避免先把数量读到 Python 再写回。
`available_stock__gte=1` 表示可售至少有一件。条件和数量变化在同一条 UPDATE 中完成。
这条 UPDATE 仍取得数据库写锁，没有另设 version 字段，也不应直接说它是无锁方案。

## 3. 两位顾客如何争最后一件

初始库存为 available=1、reserved=0，A/B 是不同顾客。B 已走到相同库存 UPDATE。

| 时刻 | A | B |
| --- | --- | --- |
| A 先预占 | 写成 0/1，持锁，事务未结束 | 开始竞争同一库存行 |
| 等待中 | 后续订单事实尚未提交 | 库存步骤可能等待，不直接返回 NOWAIT 繁忙 |
| A 最后提交 | 一张订单和预占事实生效 | 条件已不满足，更新 0 行；本次业务事务回滚 |
| 如果 A 最后回滚 | A 的订单与预占撤销，库存恢复 1/0 | 在正常放行情况下更新 1 行，原请求继续下单 |

两条结尾是不同分支，不是同一轮同时发生。
提交/回滚放行与 0/1 行已有 [Phase 6C-2 真实证据](../verification/phase-6c2-flash-sale-inventory-comparison.md)，本片未重跑。
真实错误先出现时，上表不能保证正常结束；那属于失败处理边界。

## 4. 一条 UPDATE 解决不了所有规则

| 要保证的规则 | 项目中承担它的机制 |
| --- | --- |
| 可售库存不能减成负数 | 条件 UPDATE 与库存数量约束 |
| 同一顾客不能同时占两个活动名额 | 用户串行化与购买资格唯一约束 |
| 同一个 Key 重放返回同一张订单 | scope 内幂等键、参数指纹与已有订单查询 |
| 任一步失败，不留下半张订单 | 订单、资格、预占、流水共用下单事务 |
| 旧订单事件不能改新订单名额 | 按原 Order 关联原 Purchase 转换资格 |

实际服务流程仍是：用户串行化 → 幂等重放检查 → 地址归属与活动检查 →
订单/快照/明细/购买资格 → 库存步骤 → Reservation/Movement → 整体提交。
当前直接从 Python 服务进入实验；HTTP 和页面入口尚待后续切片接入。

影响行数为 1，只说明当前库存步骤预占成功。
如果随后写流水失败，异常离开外层事务，库存仍须恢复，订单与资格也须撤销。
影响行数为 0，是“没有符合条件的库存行”；也可能库存记录根本不存在，现有候选统一返回库存不足。

## 5. 为什么现在选择它，以及代价是什么

最小替代方案是保留 NOWAIT，库存锁忙时立即失败，由应用决定是否重试。
条件 UPDATE 让当前请求在正常放行后继续依据数据库状态判断，适合本期单 SKU、数量固定 1 的规则。
普通等待式 FOR UPDATE 也可行；本片不为凑更多方案而新做一组实验。

本机库存 6、每人最多三次的三轮中，两种策略都建成 6 单：候选每轮 24 次调用，NOWAIT 52–55 次。
候选旅程 p95 90.01–94.55 ms，NOWAIT 106.42–121.91 ms；连接区间合计分别 1.016–1.072、1.703–1.834 秒。
相同产出下，这组证据支持本期选择；数据见 [Phase 6C-3](../verification/phase-6c3-flash-sale-inventory-load.md)。

代价是等待期间仍占用连接、事务及此前获取的相关锁；候选不是无锁，也不是无死锁保证。
候选 UPDATE 后还有 GET，成功库存步骤仍有两条 SQL，不要说整个下单只发一次 SQL。
有限批次数据不能推断生产容量；其他条件下总连接秒范围有交叠，不是候选总能消耗更少资源。

## 6. 超时为何需要回滚整个业务

1205 是 Lock Wait Timeout（锁等待超时）；1213 是 Deadlock（事务形成循环等待，数据库需中止其中一个）。
它们是 SQL 错误，不是“成功执行且更新 0 行”，不能返回库存不足来掩盖。

MySQL 默认锁等待超时通常只回滚等待失败的语句；死锁则会回滚受害事务。
我们的业务需要让失败异常离开外层 atomic，回滚之前创建的订单和购买资格。
不能只依赖“有一条 SQL 没成功”就认为之前所有记录自动撤销。
官方说明见 [InnoDB 错误处理](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html)。

具体等待预算、错误映射和自动重试政策下一片确认并实现。
锁等待超时不是整个 HTTP 请求截止时间；数据库/网络故障也不能都当作可盲目重试的库存竞争。
本片没有新增全局数据库配置、状态码、自动重试或超时测试。

## 7. 面试表达与独立练习

下面是回答骨架，需要你用自己的话解释，不代表已经掌握：

> 我把秒杀库存预占放在完整下单事务里，用唯一 SKU 和库存至少一件作为条件，
> 在数据库内同时减少可售、增加预占，再根据影响行数决定继续或回滚。
> 更新一行后还要完成订单关联事实；失败时整体撤销。限购与幂等由各自约束保证。
> 我对比过 NOWAIT 与条件更新的完整事务，在同产出的小批次中观察到条件更新减少尝试成本。
> 它仍可能等待锁、占用连接，需要定义超时失败。我的证据来自隔离 MySQL 的本机实验，不能代表生产容量。

独立练习：不看代码，解释 A 回滚后 B 为什么可能成功，以及“更新 1 行后流水失败”为什么订单仍不能成立。
再指出库存数量、购买资格与请求 Key 分别解决什么问题。
