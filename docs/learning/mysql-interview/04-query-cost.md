# 返回20笔订单，为什么数据库仍可能做很多工作？

面试中比“我用了预加载和索引”更有价值的是：能从真实请求解释每条SQL的职责，再用计划区分返回数量与实际工作量。这个项目先做分页，再观察完整查询，最后正式落地一个索引；没有把SQL条数少直接当成性能好。

返回[MySQL与订单查询总览](../mysql-current-overview-study-guide.md)。当前代码核对基于`886600018badf0d157a6cd6d7164a308c4bd1c2b`；本页实测数字来自2026-10-09[真实查询基线](../../verification/phase-3-order-query-baseline.md)及其[原始JSON](../../verification/phase-3-order-query-baseline-data.json)。本轮仅整理，见[发布验证](../../verification/mysql-interview-knowledge-base-publication.md)。

## 先还原这条读取业务流

顾客登录后打开`GET /api/orders/?page=1`。HTTP入口先处理Session身份与权限，再把`request.user`交给本人订单查询。分页器统计本人总数，取排序后的20笔订单；地址快照跟随订单联表读取，商品明细通过本页订单ID批量加载。Serializer把这些对象转换成JSON字段，Renderer再编码成字节，浏览器收到结果。

## 为什么用JOIN加载地址，用Prefetch加载明细？

ORM（对象关系映射）让Python对象操作对应数据库查询；QuerySet通常是惰性的，构造查询不等于已经取得结果，物化时才取数据并创建对象。核心查询见[views.py第147行](../../../backend/apps/ordering/views.py#L147)：

```python
    return (
        Order.objects.filter(user=user)
        .select_related("address_snapshot")
        .prefetch_related("items")
        .order_by("-created_at", "-id")
    )
```

`select_related`借助SQL JOIN取单值关联；`prefetch_related`执行额外批量查询，再在Python中把多值关系挂回对应对象。这是Django两种不同的关联读取机制，不是两个“缓存开关”。[Django 5.2官方QuerySet说明](https://docs.djangoproject.com/en/5.2/ref/models/querysets/#select-related)

假设一页20单，逐单取地址和items，读取次数可能随订单数增长。N+1 Query（N+1查询）就是先查一批主体，再为每个主体另外查关联的模式。当前不是在循环里分别发20次items查询，而是对本页的20个订单ID一次预加载；同一非空页的查询数量不随20条缩成1条而增长。

把订单和所有明细直接做一个大JOIN是另一种方案，但一个订单有多条items会产生多行，直接在连接结果上LIMIT20不等于20笔订单，还可能重复订单字段或截断某单明细。可以用更复杂的分阶段查询处理，但不必为了把3条SQL改成2条牺牲明确的订单分页语义。

响应会访问关联，因此必须确认序列化没有追加SQL。真实的[Serializer关联声明，第137行](../../../backend/apps/ordering/serializers.py#L137)是：

```python
    address = AddressSnapshotSerializer(
        source="address_snapshot",
        read_only=True,
    )
    items = OrderItemSerializer(many=True, read_only=True)
```

它输出下单时已保存的快照，不去读取顾客现在的地址或商品当前价格。实验检查`OrderSerializer.data`阶段没有新增SQL，因此3条数据SQL包含了页面要求的完整地址与明细。若后来新增序列化字段而引入关联读取，需要重新看它是否落在预加载范围，不能机械继承原查询预算。

## 真实基线为什么准备本人和他人各5,000单？

只准备20单很难区分“能返回20单”和“为这20单扫了很多历史记录”。2026-10-09实验在可销毁`test_project_one`中合成本人5,000、他人5,000单，共10,000地址、20,000明细；每单两种SKU、总额2.00。这是读取夹具，不是线上用户规模，也不是通过10,000次真实库存与支付流程生成的业务流量。

创建时间明确更新为固定起点加`(id*37)%503`秒，既有相同时间，也有时间和ID顺序不一致。期望结果从预存ID和时间公式算出，不用被测ORDER BY生成答案；否则排序代码与断言可能共享同一个错误。

比较三种形状：旧式全量数组、当前首页20单、第201页20单。旧全量用相同本人查询和Serializer重建过去的路径；当前API没有开放一个`all`参数。每种先热身、再测五次，形状轮转，先原索引阶段后候选阶段；没有清冷缓存、并发压测或随机交替索引阶段。

计时也拆开：**ORM物化**包含执行查询、结果获取和对象构造；**序列化**转换成响应字段；**JSON渲染**编码成UTF-8字节。驱动execute周围的时间不是纯MySQL服务器时间，EXPLAIN ANALYZE另行执行并有测量开销，不能把它当普通接口延迟。

| 原索引阶段，五次中位数 | 全量本人5,000单 | 首页20单 | 第201页20单 |
|---|---:|---:|---:|
| ORM物化 | 469.68ms | 8.79ms | 12.89ms |
| 序列化 | 199.94ms | 1.45ms | 1.45ms |
| JSON渲染 | 41.45ms | 0.16ms | 0.17ms |
| 单次三阶段和的中位数 | 711.57ms | 10.38ms | 14.52ms |
| 响应字节 | 4,005,001 | 16,108 | 16,146 |
| 订单数据SQL数 | 2 | 3 | 3 |

三阶段和是在每次相加后再取中位数，不能直接把三个阶段中位数相加来复算它。这里不含Session SQL、真实HTTP服务器、网络传输或浏览器，也不支持吞吐、p95或生产容量结论。

这组数据说明两个容易混淆的事实：分页虽然多了COUNT、由2条变3条，但返回与Python处理范围大幅缩小；索引优化主要针对数据库路径，不能自动消除全量5,000单的序列化与JSON成本。每单固定两条items只是实验前提，不能证明20笔任意真实订单都有16KB上限。

## LIMIT20为什么仍出现5,000行？

先看实际已有索引，而不是看到慢就直接加新索引。基线阶段Order已有主键、public_id唯一索引、`(user_id, creation_scope, idempotency_key)`幂等唯一索引；地址有order_id唯一索引，items有order_id外键索引。所谓“原基线”是**没有匹配当前时间排序的列表索引**，不是整张表没有索引。

原索引可以用最左边的`user_id`找到本人5,000单，但后面的scope/key没有按订单创建时间组织。首页实际路径是从幂等索引得到5,000笔本人订单，按`created_at DESC, id DESC`做Sort，再取20笔，地址查找20次。数据库返回20笔，不意味着可以在没有排序支持时只找20笔就知道哪20笔最新。

EXPLAIN（执行计划）描述优化器计划怎样查，里面rows是估计；EXPLAIN ANALYZE实际执行并记录节点结果。这次原计划估计4,968，实际索引节点输出5,000。树中父子节点不能相加作“总共扫描多少行”；地址节点的rows与loops也要一起理解。[MySQL官方EXPLAIN说明](https://dev.mysql.com/doc/refman/8.4/en/explain.html)

`filesort`表示需要额外排序，不自动等于磁盘排序；本次没有落盘证据。另一个容易忽略的对照是全量items：原计划沿主键实际读20,000行，过滤后输出本人10,000条；分页items才按本页order_id范围读取40条。只看最终返回量或SQL条数，会漏掉这些路径差异。

## 深页与COUNT为什么需要单独解释？

第201页的OFFSET是`(201-1)*20=4,000`。原路径从5,000订单排序输出前4,020，再经过地址查找4,020次，最后跳过4,000返回20。候选排序索引避免订单Sort，仍需沿顺序经过4,020笔，并在当前完整联表路径里查4,020次地址；它没有直接跳到第4,001笔。

COUNT最后输出一个数字，却仍从覆盖索引读本人5,000笔再聚合。Covering Index（覆盖索引）表示该步骤需要的信息能从索引拿到，不必取完整订单字段；它不代表不需要统计所有匹配记录。索引、分页、总数和深翻页各自减少不同工作，不能用“有索引”盖过剩余成本。

还有一致性边界：COUNT和列表分别查询，默认没有把这几个查询包成共享快照的只读事务。翻页期间或两条查询之间新增/删除订单，count和本页位置可能变化。当前应用接受普通订单列表的这一边界，没有承诺冻结历史，也没有为了读列表引入锁住用户或订单的交易事务。

## 如果重新做，我怎样判断下一个优化？

我会从接口第一版同时定义业务规则与测量范围：本人过滤、排序、完整快照、固定页长，以及完整HTTP和订单数据阶段的区别。发现成本后，先捕获应用实际SQL、参数、已有索引和估计/实际计划，用相同数据分别测对象构造、序列化和字节大小。

当前首页主要缺口是排序读取路径，所以随后只落地[联合索引](05-composite-index.md)。若将来用户真的频繁深翻页，再评估游标分页；若地址JOIN的深页工作显著，再比较先取本页ID后联表，但要计入额外查询与一致性窗口；若items变大，再考虑列表摘要。缓存列表则另有失效和归属隔离问题，不是零代价的替代。

停止条件是能解释“哪一步工作减少、响应和权限是否保留、哪些成本还在”。现有实验1项、相关16项与9子场景通过；临时候选被删除、测试库销毁，应用模型在该基线片没有改变。当前正式索引是下一片的结果，本页保留原阶段；不要在最新模型上重跑旧基线，把已经有索引的结构冒充原结构。没有必要为同一个面试结论反复增加负载矩阵。
