## 1. 这片形成的业务闭环

之前的 MySQL 秒杀事务已经负责不超卖、一人一单和请求幂等，但每个合法 HTTP 请求都会进入订单处理；库存正确不代表数据库能承受任意数量的尝试。

本片增加“登录与安全校验 → 输入校验 → Redis 申请尝试名额 → MySQL 下单 → 保存订单结果”。没有名额时返回429；Redis无法确认名额时返回503。只有明确放行才进入原订单处理，订单与库存仍以MySQL为准。

你需要掌握的重点是：**正确性和负载保护分别由什么机制负责；为什么计数判断需要原子执行；故障时保护数据库要付出什么可用性代价。** 最小证据是并发名额不超限，以及被拒请求确实没有进入订单事务。

名额不是库存或购买资格。例如测试允许4次尝试、库存有24件：该窗口内最多4次获准进入MySQL，仍可能因为地址、活动状态或库存规则失败。正常下单后继续复用既有Mock支付与库存核销；Lua不参与支付事实。

## 2. 难点一：共享计数必须同时判断、更新和设置期限

Fixed Window（固定时长窗口）是在一段固定持续时间内限制尝试数量。本项目从第一个请求开始计时，不按自然整秒切段；TTL（过期时间）到达后，下一次请求建立新窗口。

全部秒杀下单请求共享一个固定Redis Key。这样控制的是入口总量，不会因为每个用户或活动各有额度而累加放大总量；也不需要先查MySQL确认活动，再决定使用哪个Key。

首次建立窗口的关键代码是：

```lua
if not raw then
    redis.call('SET', KEYS[1], '1', 'PX', window_ms)
    return {1, 1, window_ms}
end
```

`raw`是读取到的当前计数；没有Key时用一次SET同时保存计数1与毫秒期限，避免“已计数、还没设置过期就中断”留下永久计数。后续合法计数的放行分支是：

```lua
if current >= limit then
    return {0, current, ttl}
end

current = redis.call('INCR', KEYS[1])
return {1, current, ttl}
```

这两段在同一个Lua脚本中执行。客户端分别GET、判断、INCR时，两个请求可能同时看到剩余1个名额并都放行；脚本执行期间其他命令不能插入这些步骤，因此共享额度判断与更新不会交错。见[Redis官方脚本说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)。

后续INCR保留原期限，满额拒绝既不递增也不续期，否则持续流量可能把窗口一直推迟。原子执行也不能理解成“脚本任何报错都会像数据库事务一样撤销此前写入”。脚本先验证参数、计数和期限，再做短而明确的写入；无期限、非法计数或错误类型均拒绝，不擅自重置额度。

额度统计的是**进入订单处理的尝试**。业务校验失败仍消耗一次名额，不退还；否则大量无效地址等请求也能反复进入MySQL。Redis暂时丢失Key会重新开启预算，但不能改变MySQL中已经存在的订单和库存。

## 3. 难点二：放在事务前，故障策略才真正保护数据库

准入发生在Session登录、CSRF和参数/Key格式校验之后，原HTTP下单适配器之前。适配器会查询并临时调整数据库会话锁等待时间，然后进入订单事务；拒绝发生在它之前，才能连这些SQL和用户行锁也一起避开。

前端仍保留用户、活动项、地址与Idempotency-Key组成的原购买意图。Idempotency（幂等）在这里指原请求重试可以确认同一订单，不重复产生库存效果。拥有者确认的政策是：

| 当前结果 | 用户怎样继续 | MySQL订单处理 |
|---|---|---|
| 明确放行 | 创建订单201，或确认旧单200；异参原Key仍409 | 执行既有业务规则 |
| 窗口满额429 | 等窗口恢复，再用原Key和原参数确认 | 不进入 |
| Redis无法确认503 | 保留原购买意图，恢复后用原Key重试 | 不进入 |

**已提交订单的原Key确认也先申请名额。** 满额时先429，恢复后同参200、异参409。优点是所有被拒请求都避开订单处理；代价是旧订单确认也可能暂时等待。先查MySQL、让旧单确认绕过准入是另一种可行政策，但会保留查询压力，本片没有采用。

Fail Closed（无法确认就拒绝继续）与商品缓存故障后回源MySQL的策略不同：缓存回源为了继续提供读取，准入则承担下单保护；Redis故障后直接放行会让保护失效。当前选择503，接受秒杀入口暂时不可用。

Redis连接与读响应各设0.1秒超时，客户端自动重试次数为0。它们不是整个HTTP请求的总期限。脚本可能已消耗名额，但响应超时：此时返回503，不重试脚本、不退还未知名额、不进入MySQL，等恢复后仍重试原购买。

## 4. 为什么选择这层方案，以及代价

共享Redis能让多个应用进程看到同一个额度；进程内计数简单，但每个进程各自放行，无法保证入口总预算。Lua把判断和计数合成一次短操作，现阶段直接EVAL发送固定脚本，省去脚本缓存丢失时的加载分支；代价是每次传输脚本文本。EVALSHA缓存执行可后续按真实开销评估，本片未做比较。

固定窗口简单、只有一个计数Key；窗口末尾与下一窗口开头可连续放行两批请求，因此不能宣称流量已经平滑。滑动窗口或令牌桶能改变突发行为，但有额外状态和规则，本片没有实现或实测。

这也不是严格并发上限：窗口统计“进入过多少次”，不记录事务是否完成；上一窗口仍未结束的事务可与下一窗口重叠。严格并发槽需要领取、释放、超时与崩溃回收，不是把当前计数改个名字即可。

全局预算有热点Key、用户争抢与公平性代价，不能代替反机器人或每用户防刷。默认20次/1000毫秒只是本地实验配置，不是测出的安全容量。Redis库存预扣会新增双存储对账和补偿问题，本片继续由MySQL条件UPDATE保证库存正确。

## 5. 已验证的收益与证据边界

当前最终回归为**53项通过、325个子场景通过，61.45秒**。此前目标验证14项通过；首轮测试夹具错误导致失败，修正过程与原始失败日志保留在验证记录中，不把首轮记成成功。

真实Redis验证：24个独立客户端同时申请，额度4，实际4个放行、20个拒绝；计数保持4并有期限。拒绝不续期、期限到达后新建窗口、损坏状态503均通过。

真实MySQL/Redis对照：8个工作线程处理24名合成顾客，初始库存24、每单89元，窗口10秒，比较结果如下：

| 观测 | MySQL基线 | 启用准入 |
|---|---:|---:|
| 进入订单事务 / 创建订单 | 24 / 24 | 4 / 4 |
| 429拒绝 | 0 | 20 |
| 请求期间SQL总数 | 480 | 80 |
| 最终可售 / 预占库存 | 0 / 24 | 20 / 4 |

20个429请求各为0条SQL，证明固定身份后的订单处理压力被截住；实验绕过Session认证，不表示真实登录请求完全不访问数据库。两组完成的订单数量不同，因此不能用其耗时宣称购买更快、吞吐提升或生产容量。

连接失败使用真实非监听端口，本机实际得到TimeoutError；“脚本已执行、响应丢失”使用真实EVAL后抛超时的注入，证明不自动重试且不进入MySQL，后者不能包装成真实网络延迟测量。原Key被429/503拦住后恢复确认、异参409、无重复订单和库存效果也通过。前端429/503保留意图依据本轮静态核对，未新增真实浏览器端到端验收。
