# 商品搜索基线：先明确查询语义，再判断搜索引擎的价值

2026-10-09。配套[验证记录](../verification/phase-7a-search-baseline.md)。本片增加MySQL关键词搜索并记录完整查询计划；Elasticsearch已确认后续加入，本片尚未接入。

## 1. 这片形成了什么业务闭环

之前顾客只能浏览目录和选择分类；现在可以输入关键词，找到名称或描述中包含它的公开商品，再进入详情、购物车及既有下单支付流程。搜索改变的是发现商品这一步，订单、价格与库存事实仍由MySQL负责。

这片要练会的是：**把搜索需求说成明确规则，读懂真实请求的SQL，并区分查询语义不足与已测出的性能问题。** 它支撑你解释“为什么准备加ES、普通索引能解决什么、分页为什么仍可能处理很多数据”。

最小证据是搜索结果符合独立预期、没有泄露下架内容，以及真实API的COUNT与列表SQL执行计划。达到这些证据后先收束，不把查询基线扩成大量压测。

顾客输入“无线鼠标”：名称是“无线鼠标 M1”的商品会命中；名称是“桌面配件”、描述包含“备用无线鼠标”的商品也会命中。选择“鼠标”分类后，其他分类的命中商品会被排除。

## 2. 难点一：搜索规则必须明确，不能悄悄改变目录

本片采用**完整关键词包含匹配**：去掉首尾空白后，整个关键词出现在名称或描述任一字段即可。没有关键词或只有空白时，仍是原来的商品浏览。

关键词最长80字符；超长或包含空字符返回400，在商品SQL之前拒绝。这个长度限制约束输入，不保证查询只扫描少量商品，也不构成入口限流。

关键过滤代码如下，前面已经建立公开商品查询并应用分类条件：

```python
keyword = query.validated_data["q"]
if keyword:
    # 完整关键词包含匹配；ORM负责转义LIKE通配符，不做分词或相关性排名。
    queryset = queryset.filter(Q(name__icontains=keyword) | Q(description__icontains=keyword))
```

`OR`表示名称、描述命中一个即可；它与已有的商品有效、分类有效、所选分类条件取`AND`，即这些条件必须同时满足。不能让描述命中绕过可见性，也不能为了搜索只显示有货商品。

ORM（对象关系映射，把查询表达式转成SQL）负责参数化和LIKE字符转义；用户输入`%`、`_`或反斜线时按普通文字匹配，不把它们当“匹配所有商品”的规则。

结果继续按名称、内部ID排序，固定每页20条。同名时ID决定先后；最低价只考虑有效SKU，有货提示也只考虑有效SKU，无规格或缺货商品仍可展示。提示有货不等于下单时一定有库存。

这不是分词搜索。“鼠标 无线”不会自动拆成两个词、改变词序后找到“无线鼠标”；结果也没有“名称命中比描述命中更相关”的排名。英文小写`m1`命中`M1`已验证，实际文本比较仍受数据库排序规则影响。

前端把关键词、分类、页码保存到URL；换关键词或分类回到第一页，翻页保留关键词，进入详情后返回仍可恢复条件。新请求取消旧请求，防止旧结果覆盖新搜索。

## 3. 难点二：每页20条，不代表数据库只处理20条

非空首页实际有两条SQL：一条计算总数，一条取列表。零匹配时只有总数SQL，分页器直接返回空列表。

列表不仅查Product，还关联分类与SKU，聚合有效SKU最低价，并用`EXISTS`判断是否有可售库存。`EXISTS`在这里表示“只要找到一个符合条件的库存即可”，用于浏览摘要。

本次关键词有500个命中商品；执行计划显示列表先聚合这些命中商品，再从500个结果中排序取20条。增加分类后则聚合250个命中商品，再排序取20条。`LIMIT 20`限制返回量，并没有让前面的筛选与聚合只处理20个商品。

COUNT也不是简单的`Product.objects.count()`：实际SQL关联分类、左关联SKU、按商品分组，再统计分组结果。它还保留库存EXISTS表达式；分类场景的实际计划明确记录该相关子查询执行250次，不能把“总数查询”直接理解成廉价计数。

全局关键词和无匹配场景均先通过分类外键索引查找商品，再检查名称或描述。Product步骤显示`rows=2500, loops=2`；这是每次循环的平均值并经过显示舍入，不能把相乘结果当成精确读取5000行的证据。

分类场景缩小了候选范围，Product步骤实际为`rows=2501, loops=1`，筛选后留下250个可见命中商品。无匹配虽然返回0条，仍要检查候选商品；结果少不等于查找成本低。

这里已经使用分类外键索引，因此不能说“整个查询没用索引”。真正的限制是`LIKE '%关键词%'`不能靠名称的普通B树索引直接定位关键词范围：B树按字段顺序组织数据，开头不确定时无法像前缀查询那样确定连续范围。见[MySQL 8.4范围优化说明](https://dev.mysql.com/doc/refman/8.4/en/range-optimization.html)。本片没有新增名称索引或测试索引候选。

## 4. 为什么先做MySQL基线，以及其他方案的取舍

直接在现有目录查询上增加过滤，能够保留权限、价格、库存提示和分页规则，不引入第二份商品数据及同步故障。先得到这套准确行为，后续才有参照判断搜索引擎改变了什么。

代价是包含匹配缺少分词、相关性排名，完整请求仍有COUNT、联表、聚合和排序成本。现有5000条合成商品的单次计划中出现毫秒级耗时，**不足以认定它是慢SQL，更不能推算生产容量或ES会快多少**。

MySQL FULLTEXT（数据库全文检索能力）是有意义的候选：可以评估文本检索与分词规则，同时减少引入独立服务的运维范围。本片没有建立全文索引、配置分词器或进行同需求对照，不能宣称它已经被证明不适合。

ES可以作为独立搜索查询副本来评估，但会增加服务、映射、同步、陈旧结果和恢复成本。是否真正改善中文查询与排序，要靠后续具体查询和真实集成证明，不能仅凭技术名称下结论。

## 5. 已验证什么，证据到哪里为止

目标验证为**9项通过，12.84秒**，包括关键词规则与显式查询基线；相关回归为**24项通过、6个子场景通过、1项默认跳过，10.99秒**。跳过的是需要明确开启的查询实验，不是一次失败。

本次使用可销毁MySQL 8.4.10测试库，建立5000个可见商品、2个隐藏商品，以及10004个SKU与10004条库存；每个商品都包含有效及隐藏SKU。预期结果由合成数据的编号规则决定，没有用相同ORM过滤计算答案。

| 请求 | 命中数量 | 实际SQL数量 |
|---|---:|---:|
| 关键词“无线鼠标” | 500 | 2 |
| 不存在的关键词 | 0 | 1 |
| “无线鼠标”＋指定分类 | 250 | 2 |

三种请求均核对数量、首屏完整摘要及分页状态，并保存实际SQL、参数、表索引、列排序规则、估计计划和实际执行计划；每条SQL只观察一次，不是时延对比实验。详见[原始证据](../verification/phase-7a-search-baseline.json)。

前端构建通过，关键词URL与取消旧请求仅做本轮静态核对，尚未进行真实浏览器运行验收。开发库、库存与支付核心、Redis准入及依赖未修改；没有ES服务或索引同步验证。

## 6. 剩余缺口与下一片

当前还没有分词、相关性排名、搜索副本同步与重建、陈旧或下架结果处理、ES故障政策，也没有真实网络搜索验收。分页期间目录变化仍可能影响前后页；固定排序不等于跨请求一致快照。

**下一片只做ES可重建索引原型**：确定最小商品搜索文档与中文查询规则，从隔离MySQL数据构建查询副本，再用具体关键词验证命中和排序。派生索引意味着它可以由MySQL事实重建，不成为价格、订单或库存的最终依据。

先证明文档、查询与重建机制能解释业务需求，再决定API接入、增量同步和故障恢复切片；不一次生成整个ES模块，也不把本指南或通过测试当作个人已经独立掌握。
