## 1. 这片在项目中完成了什么

上一片已经完成“登录 → 查看本人订单 → 翻页 → 进入详情”。这片补齐它的工程判断闭环：**捕获实际查询 → 看数据库怎样执行 → 拆开不同成本 → 在隔离库验证候选 → 明确下一步**。

它支持你讲清“怎样定位慢SQL、为什么这样设计联合索引、为什么有索引后深分页仍有成本”。没有增加购买功能，也没有把本机合成实验说成生产慢SQL事故。

实验使用本人5,000单、他人5,000单，每单一个地址和两条明细；包含相同创建时间和时间顺序不等于ID顺序的数据。比较旧式全量读取、当前首页、第201页；每种形状热身一次、采样五次，临时索引前后返回内容完全一致。

## 2. 重点一：SQL少，不等于工作少

当前非空分页有三条订单数据SQL：COUNT本人订单总数；读取订单并联表取地址；批量读取本页items。旧式全量读取只有两条，没有COUNT，却需要构造5,000笔订单及10,000条明细。

分页收益首先来自**少返回、少构造、少转换**，不能写成“SQL数量减少”。本轮基线中：

| 查询形状 | 返回订单/明细 | ORM物化中位数 | 序列化中位数 | JSON字节 |
|---|---:|---:|---:|---:|
| 旧式全量 | 5,000 / 10,000 | 469.68ms | 199.94ms | 4,005,001 |
| 当前首页 | 20 / 40 | 8.79ms | 1.45ms | 16,108 |
| 当前第201页 | 20 / 40 | 12.89ms | 1.45ms | 16,146 |

全量items计划沿主键读取20,000条明细，再过滤输出本人10,000条；本轮分页items则按order_id范围读取40条。返回量与数据库工作量必须分开看，不能只统计SQL条数。

ORM物化指执行查询、获取结果并构造成Django对象；序列化指把对象转换成响应字段。JSON渲染另测，全量中位数41.45ms，首页0.16ms。以上不包括真实网络传输、Session认证、浏览器或并发等待，不能叫完整HTTP延迟。

每页仍有完整items；本实验固定每单两条明细，**没有证明20笔订单的响应字节有硬上限**。

## 3. 难点一：已有索引支持过滤，却没有支持当前排序

Index（索引）可以理解为按指定字段排列的查找结构。Composite Index（联合索引）按多个字段顺序组织，字段顺序会影响它支持什么查法。

本项目实际已有`(user_id, creation_scope, idempotency_key)`唯一索引，用来保证不同下单入口的请求幂等。它能按最左边的user_id找到本人订单，但后面的字段没有按created_at排列。

当前查询的关键条件如下；为讲清目的省略字段和地址JOIN，完整SQL保存在原始记录：

```sql
WHERE ordering_order.user_id = 1
ORDER BY ordering_order.created_at DESC, ordering_order.id DESC
LIMIT 20
```

EXPLAIN（执行计划）说明数据库打算如何查；EXPLAIN ANALYZE会实际执行并记录各步骤。在本轮首页计划中，原索引查到5,000笔本人订单，再做Sort，最后只输出20笔。计划中的估计4,968行和实际5,000行不同，**不能把估计当实际读取量**。[MySQL官方说明](https://dev.mysql.com/doc/refman/8.4/en/explain.html)

因此，“用上索引”还不够；要看这个索引减少了哪一步。`filesort`表示额外排序，不自动代表发生磁盘排序；items查询也有自己的40行排序，应与订单排序区分。[MySQL排序说明](https://dev.mysql.com/doc/refman/8.4/en/order-by-optimization.html)

## 4. 难点二：联合索引改善首页，不能消除COUNT和OFFSET

本片只在可销毁测试库里试建这一处候选：

```sql
CREATE INDEX `experiment_order_user_created_id`
ON ordering_order (user_id, created_at, id)
```

理由与查询相对应：先按user_id定位本人范围，再沿created_at、id的顺序取最近订单；最后的id让相同时间也有确定顺序。升序索引在本次计划中采用反向扫描满足两个DESC，没有使用强制索引提示。[联合索引的最左前缀](https://dev.mysql.com/doc/refman/8.4/en/multiple-column-indexes.html)、[索引与排序](https://dev.mysql.com/doc/refman/8.4/en/order-by-optimization.html)

| 实际步骤 | 原索引 | 临时联合索引 |
|---|---:|---:|
| 首页订单索引步骤输出 | 5,000行，随后排序 | 20行，没有订单Sort |
| 第201页订单索引步骤输出 | 5,000行，随后排序 | 4,020行，没有订单Sort |
| 第201页地址索引查找次数 | 4,020次 | 4,020次 |
| COUNT覆盖索引步骤输出 | 5,000行 | 5,000行 |

覆盖索引指这一步能直接从索引获取所需信息，COUNT不用取完整订单字段，但仍要统计本人可见的5,000笔。不要把COUNT聚合最终输出的1行误认为只读1笔订单。

OFFSET（跳过前面的结果位置）在第201页是4,000。即使顺序已有索引支持，本轮完整联表查询仍经过4,020笔及地址查找才返回20笔；它不是直接跳到第4,001笔。本轮本地三个阶段之和的中位数：首页10.38→7.42ms，深页14.52→13.55ms，深页收益较小。

删掉候选索引后，首页重新出现5,000行读取与排序。数据SQL、响应字节和内容哈希在候选前后相同，支持“变化来自索引路径”，但阶段先后与缓存状态仍会影响耗时，不能推广为固定提升比例。

## 5. 为什么先做这个对照，其他方案有什么取舍

先保留本人过滤、快照字段、页码契约和业务查询，只改变隔离库索引，才能解释哪个变化减少了数据库工作。正式增加索引还会占空间，并增加订单写入及相关字段更新时的维护工作；本片没有量化这些代价。

| 后续选择 | 能解决什么 / 代价 |
|---|---|
| 正式落地这个联合索引 | 已有首页排序路径证据；需要模型迁移、相关回归和安全应用流程，仍保留COUNT/深OFFSET |
| 游标分页 | 以最后一笔时间和ID继续查询，值得在深页需求出现时评估；改变接口和任意跳页体验，本片未实现或实测 |
| 先取本页ID，再取地址与明细 | 可能减少深页中被跳过订单的地址查找；多一个查询阶段及一致性边界，本片未实测 |
| 列表改成摘要或缓存列表 | 摘要可能减少大订单items，缓存可能减少重复读取；分别涉及展示契约或失效正确性，不能代替排序问题的解释 |

现在没有证据要求同时实施全部方案，也没有需要扩大为微服务或压测矩阵。

## 6. 已解决的缺口、仍未解决的缺口和下一步

已补齐完整实际SQL、三个关联表的已有索引、估计与实际计划、首页/深页/全量成本和JSON大小；实验逐次核对本人归属、排序、金额、地址与明细，当前API的SQL和响应字节也与分段测量一致。候选索引已删除，测试库已销毁；正式应用仍沿用原索引。

尚未验证生产流量、冷缓存、并发容量、真实网络、写入成本与索引空间；页码在新增订单时漂移、COUNT与列表不共享快照、大订单items成本仍存在。已有分页浏览器证据仍是模拟响应，不被本片升级为真实端到端。

**下一片建议只正式落地这一个订单列表联合索引**：用模型迁移表达，复核本人过滤/排序/快照与相关订单回归，验证迁移后的查询路径；不同时换游标、摘要或缓存。达到这些证据就收束订单查询方向，再进入已经确认的Lua原子准入。开发库迁移仍须单独说明并确认；本指南完成不等于你已能独立讲述。
