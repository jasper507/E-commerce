# Phase 4E 学习：回源成功不等于数据库受到保护

本步服务于浏览商品和 Redis 故障主线。用户已经选择：回源名额满员时立即
返回 503。你需要理解的是为什么接受“部分浏览请求失败”，以及保护的范围。

- **开始前**：请求合并不能限制 Redis 连接失败后的集中回源，历史基线 10 请求全部成功、20 SQL。

## 先复述请求合并的四个问题

**1. Key 为什么包括代号？** A 加载 G1 的 129 元，管理员改价后切到 G2。
如果只按商品合并，G2 请求可能加入 A 并拿到旧结果。G1/G2 必须是不同任务。

**2. 为什么不能持有全局锁查询数据库？** 鼠标加载慢时，会连键盘等不同
商品也挡住。锁只保证检查/创建登记不被打断，同一 Key 共用结果，不同 Key
可以并行；Redis/SQL 和等待都在锁外。

**3. 等待者超时为何不能删除加载者？** B 等不到 A 不代表 A 停止。删除
登记后 C 会再建一份加载；A 的查询仍在运行。B 可以独立复查/回源，但不能
替 A 删除登记或取消工作。

**4. 为何还要保护故障回源？** 各进程合并表不共享；Redis 代号不可用时
不能安全选取缓存代，现有代码绕过合并。请求从 Redis 转到 MySQL，可能
把压力集中到数据库。能返回正确结果，不意味着大量请求下仍然安全。

## 通行证如何运行

BoundedSemaphore（有固定名额的信号量）像一个只有两张通行证的入口：

```text
读取 Redis 代号失败 → 尝试拿通行证
├─ A 取得第1张：查上架状态 → 查 SKU/库存 → 返回 → 归还
├─ B 取得第2张：查上架状态 → 查 SKU/库存 → 返回 → 归还
└─ C 到来时已满：直接503，不进入这些数据库查询
```

本实验用 Event 保持 A/B 正在加载，让另外 8 个请求都遇到满员。实测
2 个 200、8 个 503、4 SQL。自然调度时如果 A 已完成并归还，C 就可以
进入，因此不能把“总是拒绝80%请求”当成规则。

`acquire(blocking=False)` 是尝试立即拿名额，失败就返回，不排队。
`finally: release()` 保证成功、404 或异常退出都归还。内层发现同一个
请求已经取得名额时直接继续，否则一个请求会占两张甚至自己把自己拒绝。

## 放在哪里决定能保护什么

先看 views.retrieve：缓存对象先捕获代号，再进入 fallback_scope，之后
才 get_object。初次代号读取失败，可在所有商品 SQL 之前拒绝。

如果代号成功、详情 GET 才失败，Product/Category SQL 已经发生。此时
只能限制 SKU/库存加载；测试明确记录 503 仍有 1 SQL。不要只背“拒绝零SQL”。

再看 cache.get_or_load：成功的缓存与请求合并沿用原流程；缓存关闭或
事务内是主动绕过，不是依赖故障，不能随意新增拒绝。非法代号不能安全
选择缓存代，所以进入降级保护。回填失败时数据已读取，仍返回成功结果。

## 面试要区分的四种机制

| 机制 | 回答的问题 |
|---|---|
| Singleflight，请求合并 | 同一代同商品能否共享一次正在进行的加载？ |
| Semaphore，并发名额 | 当前同时允许多少个受保护回源请求？ |
| Rate limiting，限速 | 一段时间内允许多少请求进入？ |
| Circuit breaker，熔断 | 依赖连续失败后，是否暂时停止尝试它？ |

名额是同时进行的工作数，不是每秒次数。故障下每个请求仍先尝试 Redis，
所以本轮没有实现熔断；它也不控制 MySQL 的持久连接总数。

503 表示暂时没有处理能力；404 表示商品不存在；429 通常表达调用者超过
配额。本段不是用户违规，不能用404隐藏繁忙，也不能把失败返回伪装成空商品。
