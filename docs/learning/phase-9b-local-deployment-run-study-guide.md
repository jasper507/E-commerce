## 1. 这片形成了什么闭环

本片形成“源码打包 → 独立数据库初始化 → 后端运行 → 统一入口响应”的部署闭环。它解决的是业务代码怎样离开开发启动方式，经同一个HTTP入口稳定找到前端、Django与数据库。

这是Supporting/Pair工作，支撑独立定位镜像、进程、网络、数据库和静态资源问题。可解释的证据是实际镜像构建、迁移结果、服务健康与HTTP响应；无需在面试现场展示本机，也不能只凭Docker技术名词声称部署完成。

读网页时：浏览器请求`http://127.0.0.1:8080/products` → Nginx返回Vue构建文件 → 浏览器运行JavaScript后才会继续发商品API请求。

读API时：请求`/api/catalog/products/` → Nginx转发到web → Gunicorn运行Django → Django查询`db:3306`中的独立库 → JSON经过Nginx返回。健康接口也实际验证了数据库连接；它不替代全部业务功能验证。

本轮先确认API和HTML响应，再用独立浏览器会话确认Vue实际显示空商品页、发出两个API请求，且深路由刷新仍正常；只验证公开读取，没有提交登录或交易。

## 2. 重点一：镜像构建成功不等于应用运行成功

Image（镜像）是程序和依赖的打包结果，Container（容器）才是运行实例。前端用Node构建成文件，运行时由Nginx提供；后端镜像安装部署依赖，启动后才由Gunicorn的2个工作进程运行Django。

这轮web与nginx两个Linux镜像构建成功，随后db、web、nginx均达到健康状态。这是两个不同阶段：镜像能构建仍可能遇到数据库认证、入口端口或后端运行错误，所以必须继续检查运行与HTTP结果。

后端实际进程用户UID为10001，应用不以root身份运行。但非root运行只是一项权限边界，不代表公网环境安全配置全部完成。

替代方案是在宿主Linux直接安装Python、Node、MySQL与Nginx，少一层容器网络，便于直接观察进程。当前容器方案把依赖和部署过程集中在镜像与Compose中，更易重复构建；代价是需要理解构建缓存、容器网络和卷，故障排查也多了一层。

## 3. 重点二：初始化是明确执行，不隐藏在每次启动里

迁移用于建立或变更数据库表结构；静态收集用于把Django和Admin资源集中到共享卷。关键管理命令分别运行：

```powershell
docker compose --env-file docker/deployment/.env -f compose.deployment-local.yaml -p project-one-deployment-local run --rm --no-deps web python manage.py migrate --noinput
docker compose --env-file docker/deployment/.env -f compose.deployment-local.yaml -p project-one-deployment-local run --rm --no-deps web python manage.py collectstatic --noinput
```

本轮36项迁移全部成功，收集154个静态文件。一次性命令完成后容器移除，独立数据库与静态卷保留，随后再启动长期运行的web和nginx。

这样做可以先看清初始化结果，失败时停止，不让多个web进程在重启时各自尝试迁移。代价是更新时必须记得执行必要管理步骤；命令存在不能保证所有未来迁移都兼容旧代码或不损失数据。

Vue构建文件在nginx镜像里，Admin静态文件来自共享`django_static`卷，Nginx只读提供。两者来源不同，因此网页能返回不能证明Admin样式已准备好；本轮另查了Admin登录页与CSS，均返回200。

## 4. 难点：连接的是哪一套库与入口

Compose项目固定为`project-one-deployment-local`，使用独立环境文件、数据库与卷。实际查询确认当前库为`project_one_deployment_local`，不是开发库；容器之间使用`db:3306`连接。

容器内的`127.0.0.1`指这个容器本身，不是Windows或另一个MySQL容器。新数据库没有主机端口，不能拿原开发库的`127.0.0.1:3307`来连接它。独立卷增加磁盘占用，但降低首次部署试错影响既有数据的风险。

入口只绑定`127.0.0.1:8080`，全程使用同一个主机地址，避免localhost与127.0.0.1之间的Cookie差异。Nginx保留Host中的8080，并为Vue深路由返回前端入口；API和静态资源错误仍返回各自的404，不能全部伪装成前端HTML。

随机独立凭据保存于Git忽略的`docker/deployment/.env`，没有公开真实值。原Compose、根环境文件、原开发容器与数据不在本片改动范围；用户既有文档修改也保留。

当前仍为`development`、`DEBUG=false`、本机HTTP。缓存、Lua、MQ和ES显式关闭；这些模块已有工程证据，不表示已经随这套部署启用。

## 6. 还有什么缺口，下一片怎样收束

尚未验收真实Session（登录会话）与CSRF（防止其他网站借用登录身份发请求）、账号与交易流程；中间件启用、公网HTTPS、重启后持久性、备份恢复与更新演练也未完成。

应用代码已经打进镜像，修改源码后需要重新构建并重建运行容器，不是刷新网页就能更新后端。停机默认保留命名卷，不自动删卷；迁移回退也不等于恢复已经改变的业务数据。完整命令与首次错误定位沿用[9A指南](phase-9a-local-deployment-study-guide.md)，这里不重复操作清单。

本片停止于基础链真实运行：镜像、初始化、服务健康、公开HTTP与浏览器空页已经形成最小证据，不为收片自动打开所有依赖。

下一片建议只确认一个独立学习账号，再验证同一入口的Session登录和CSRF成功/拒绝边界，回答“加了Nginx以后登录身份怎样保持”。商品与交易演示不是本轮收尾要求，不自动补数据。随后整理更新、停机、备份及公网部署流程；各中间件是否实际启用另行按收益决定。
