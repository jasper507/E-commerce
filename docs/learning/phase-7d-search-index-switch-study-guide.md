# 搜索索引手动切换：先建好，再确认读入口去了哪里

2026-10-10。[学习导航](README.md) · [验证记录](../verification/phase-7d-search-index-switch.md) · [前片：搜索读入口](phase-7c-search-read-api-study-guide.md)。本片已在真实隔离ES/MySQL中验证，个人独立理解仍待验收。

## 本片前后变化

- **开始前：** 搜索API只能配置一个精确测试索引；重建得到新索引后，读取入口不会自行跟着换。
- **本片改变：** 增加手动发布入口和Alias（固定读取名称），完成新候选后一次提交旧关系移除与新关系建立，并回读确认实际目标。
- **完成后与边界：** 成功切换、构建失败旧入口保留、在途旧读与更新后响应丢失分类已验证。仍默认关闭、仅隔离测试，没有自动同步或生产零停机承诺。

## 1. 这片解决哪个业务问题

商品改名或新增后，原搜索副本会旧。前片已经能从MySQL重建新候选，这片补上“重建成功 → 换读入口 → 顾客新请求看到新候选”的工程闭环；构建失败不先破坏旧入口。

本片以Supporting/Pair完成接线，发布结果不确定与在途请求边界属于Depth。能解释“依赖请求超时后究竟成功没有、为何不直接重试、旧索引何时不能删”，比仅说明使用了ES更有工程价值。最小证据是一次正常切换、一次构建失败、一次在途旧读和一次更新后响应丢失，不扩展整套同步系统。

这里只切搜索候选来源。价格、有货提示和当前可见性仍从MySQL读取，交易接口、原商品浏览和前端不改；最终候选数量与短空页规则沿用7C。

## 2. 重点一：完成候选与改变入口是两个阶段

发布前先核对真实测试来源、操作者所属构建会话和实际别名目标。首次发布期望目标为None；后续期望旧目标必须属于同一原型会话的完成集合，且实际别名仍指向它。重建前、发布前都检查，发现不符就拒绝写入。

新候选依次通过Bulk逐项写入、refresh、实际文档数核对和完成来源标记，才允许发布。构建异常时**尚未提交切换请求**，所以原入口保留；发布结果未确认则不能套用这个结论。

最重要的发布代码是一次提交两项关系变更，省略前置检查与结果处理：

```python
actions = []
if expected_index is not None:
    actions.append({"remove": {
        "index": expected_index, "alias": self.alias, "must_exist": True,
    }})
actions.append({"add": {"index": index, "alias": self.alias}})
response = dict(self.prototype.client.indices.update_aliases(
    actions=actions, master_timeout="2s", timeout="2s",
))
```

别名关系在一次请求中变更，旧索引本体保留。`must_exist`要求预期旧关系存在，使缺失旧关系时整组变更失败；但前置核对不是多操作者锁或数据库式比较交换，本片要求单操作者。[官方alias语义](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/indices-aliases.html)

## 3. 难点一：收到什么响应，不等于最终是什么状态

更新得到HTTP200也要查看`acknowledged`、`errors`和逐项结果，形成`response_ok`。响应丢失或确认超时则可能已经切换，不能用“报错”推断入口还在旧索引。无论正常响应还是捕获到更新异常，都再次精确读取别名：

```python
current = resolve_read_alias(self.prototype.client, self.alias, missing_ok=True)
state = "switched" if current == index else "unchanged" if current == expected_index else "unknown"
```

| 回读状态 | 可以说什么 |
|---|---|
| `switched` | 本次回读确认指向新候选，即使更新响应曾丢失 |
| `unchanged` | 本次回读确认仍为预期旧目标；首次发布时也可能仍无别名 |
| `unknown` | 回读失败或目标不同，无法确认预期结果 |

例如ES已完成更新，客户端随后抛超时：回读新目标可报告`switched`；回读也失败，只能报告`unknown`。**未知不是“确定没切”，也不是“确定已切”。**

发布器不会因未知结果自动重发、反向切回或删除任何候选，需先人工核对实际指针。否则一个已经成功的切换可能被误撤销，或仍被读取的索引被误删。本片没有把未知恢复包装成全自动工具。

## 4. 难点二：切换后仍有请求在读旧索引

读API每个请求只解析一次别名，确认唯一目标与完成元数据后，搜索这个精确索引。请求A先解析到旧索引I1；操作者切换到I2；A继续查询I1，之后的新请求B解析到I2。保留I1使这个交错有明确的读取对象，不能刚切换就立即删除它。

别名含过滤器、routing（搜索分片路由）或多个目标会被拒绝并返回503。原因是解析后按精确索引查询会绕过别名附带规则；本片只接受自己建立的单目标空配置，不能悄悄忽略那些规则。

旧请求拿到旧候选后，商品摘要仍读取当前MySQL。它可能不再展示已下架商品，也可能返回改价后的金额；这不是ES与MySQL共同快照，更不是多次翻页的PIT。切换后相关性与候选位置可能改变，跨页重复或遗漏的边界仍在。

## 5. 为什么选择别名，有什么代价

手动改精确索引配置并重启也是可行方案，机制简单，但多个运行实例的配置切换时点可能不同。别名把入口集中到ES；读端同时保留7C的精确索引方式，`ALIAS`与`INDEX`必须只配置一个。

代价是每次别名读取多一个GET请求，以及保留新旧索引的空间与人工清理成本。重建仍全量物化MySQL文档到应用内存，再写新候选；不是流式增量同步，也没有证明性能提升。各请求超时和客户端等待会累加，配置2秒不代表整体发布或搜索只需2秒。

发布器只认可同一builder会话的完成集合；另一个进程没有旧ready集合，不能直接继续发布。本片提供隔离控制对象，没有独立管理命令或开发运行入口，这一限制不能被别名已持久化掩盖。

所有操作仍限定同一实际`test_project_one`生命周期、本机9201、指定集群与版本；不改变真实连接的NAME来伪装来源，不持有外层数据库事务等待ES。元数据仍不带测试数据代次，销毁重建测试库后旧索引与别名必须作废；单会话完成集合不能替代生产数据身份绑定。

## 6. 证据、缺口与停止条件

本片5项真实集成与旧读接口/原型回归合计18项通过；独立离线回归1项，原目录24项和6个子场景通过。新词候选0→2，真实Bulk失败alias更新0次；在途旧读完成后新请求读新索引。两轮真实POST后注入响应丢失/回读失败，正确区分switched/unknown，各只提交1次。它们不是实际网络丢包或多节点故障；ack=False、逐action失败与unchanged分支仅静态核对。开发30表比对未变，21个候选和5个别名清理完毕；详细输入、响应与检查见[验证记录](../verification/phase-7d-search-index-switch.md)。

仍缺多操作者协调、数据代次绑定、跨页快照、自动同步、未知结果恢复工具、旧索引自动回收与生产入口。构建完成后源数据也可能继续变化，切换不能保证索引永远新鲜。

证据足以支持“建好才发布、失败怎样分类、在途请求读什么”就收片。下一步先整理个人理解，再评估部署、真实前后端演示与项目收尾还缺哪项最小证据；不因还有上述缺口就自动扩展同步或MQ功能。
