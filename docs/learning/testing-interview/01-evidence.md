# 01 测试通过能证明什么：业务终值、验证层级与性能边界

2026-10-12，源码快照`407066c61b6fed59a172320e997e66fa637fc9eb`。[专题总览](../testing-current-overview-study-guide.md) · [并发与故障](02-concurrency.md) · [本轮核验](../../verification/testing-evidence-knowledge-base-publication.md)。以下是历史实测与当前源码核对，本轮不执行应用测试。

**测试证明的是指定输入、环境和交错下的断言，不是“以后任何情况都正确”。** 项目面试里最值得解释的是Oracle（判断结果正确与否的标准）：业务最终应是什么，哪些副作用不能发生。

## 本专题前后变化：从“passed”走到“守住了什么”

189元订单已经预占一件商品，库存从20/0变为19/1。付款通知和到期关闭发生竞争。只看“支付入口没报错”会遗漏：订单是否被错误关闭、预占是否提前释放、核销是否重复、是否创建第二次付款或退款。

正确行为来自已确认规则：活跃Attempt尚未明确失败，不能仅因预占到期就强行关闭；可信成功最终进入PAID；预占最多核销一次。测试需要跨多个表核对同一笔业务事实。

5D测试在两个执行者结束后重新从数据库读取Order、Attempt、Event、Reservation与Movement，再判断完整结果。它没有只断言一个接口状态。

## 一段核心断言为什么比“200”有解释力

来自[真实终值核对](https://github.com/jasper507/E-commerce/blob/407066c61b6fed59a172320e997e66fa637fc9eb/backend/apps/ordering/tests/test_payment_expiration_concurrency.py#L168)：

```python
    assert result == {
        "order": "PAID", "payment": "SUCCEEDED", "event": "PROCESSED", "event_attempt_count": 1,
        "reservation": "COMMITTED", "inventory": [19, 0], "reserve_count": 1, "commit_count": 1,
        "release_count": 0, "restore_count": 0, "refund_count": 0, "attempt_count": 1,
        "amount": "189.00", "currency": "CNY",
    }
```

代码前面已经`refresh_from_db()`并按这张订单的预占关系统计流水。`19/0`表示可用库存仍19，预占已归零；`COMMIT1`说明这件商品核销一次；`RELEASE0`排除到期路径错误释放；`attempt_count=1`排除重新发起付款。随后还重放原成功事件与到期操作，再核对终值不变。

这支持5D所选两种锁顺序、三种活跃Attempt状态下的结果。它不能独自说明所有多订单死锁排列、真实资金到账或网络吞吐。期望字典来自业务规则；如果规则变化，必须先讨论正确行为，再改断言，不能为了让实现通过而直接改期望。

## 用什么验证层级，取决于你要声称什么

| 方式 | 适合支持的结论 | 本项目中需要额外说明的边界 |
| --- | --- | --- |
| 纯规则测试、Mock或异常注入 | 金额/状态/分类规则、指定异常分支、回滚和错误映射 | 不证明真实依赖产生该故障、网络断连或进程重投 |
| 隔离真实MySQL | SQL、事务、约束、锁竞争及持久终值 | 需实际控制和观察竞争；APIClient不等于真实HTTP部署 |
| 隔离真实Redis/RabbitMQ/ES | Lua原子调用、故障连接、Broker重投、索引切换等指定语义 | 实验配置、进程数、故障窗口与合成数据仍有限 |
| 真实HTTP客户端经8080入口 | Nginx代理、Django接口、Session/CSRF往返 | 不证明浏览器Cookie策略、页面JavaScript或登录UI |
| 浏览器执行页面 | 页面状态、路由、资源加载及实际发请求 | 若响应被拦截替换，必须标模拟；仍需后端终值证明业务效果 |
| 文档/静态检查 | 摘录、链接、配置语法、图文和回读一致 | 不替代任何业务运行结果 |

不同方式是针对不同问题的工具，没有一条简单排名可以替代目标判断。替身测试更便宜、可稳定触发罕见分支；真实集成能揭示替身没有模拟的连接、锁或进程行为。关键语义选真实依赖，日常纯规则保留便宜的反馈，两者配合而不是相互冒充。

## 三组容易说错的本项目证据

**订单分页与索引。** [分页片](../../verification/phase-3-order-list-pagination.md)先把每次返回条数固定20，页面检查用模拟响应；它不宣称SQL变快。后续[查询基线](../../verification/phase-3-order-query-baseline.md)与[正式索引](../../verification/phase-3-order-list-index.md)观察完整SQL及执行计划，首页排序消失，COUNT仍读本人5000单，OFFSET4000仍经过4020条订单/地址查找。不能把“返回20条”改说成数据库全程只读20行。

**Lua准入。** [6F](../../verification/phase-6f-flash-sale-admission.md)用8线程处理24个APIClient请求，真实订单事务24→4，20个429在固定认证后没有下单SQL。这支持所选输入下保护下单事务；不等于24个网络请求同时到达、整个Session HTTP零SQL或生产容量提高了固定倍数。

**部署与身份。** [9B](../../verification/phase-9b-local-deployment-run.md)真实浏览器显示新库空商品页并刷新深路由；[9C](../../verification/phase-9c-session-csrf-operations.md)补15项HTTP客户端身份检查。后者没有做浏览器登录UI或完整交易验收；四开关关闭时不能用隔离MQ测试替部署启用证据。

性能说法还需要明确相同业务产出。4J冷波SKU查询6→2伴随4个503，后续仍要加载这4个商品；快拒绝不等于每位顾客更快拿到商品。SQL数、返回字节、接口时延、成功吞吐、并发占用与生产容量各是不同指标。测试执行耗时不能冒充接口性能。

## 通过、跳过、失败与历史结果怎样保留

`passed`只表示本次被执行且断言通过；`skipped`表示该组没有执行。项目的真实MQ/ES/部分数据库诊断实验要求显式配置，普通回归跳过它们是已知边界，不能算新增通过。显式配置后依赖不可达而失败，也不能临时改成跳过来制造绿色结果。

4J保留目标断言失败再改实现；7B首轮原输出虽有通过项，却因隔离事故不能用来支持安全性。保留原日期、代码版本、环境、输入、注入点、原始输出和终值，后来新增证据再补链接，不篡改旧记录让历史看似一直正确。

## 如果重新做，我会改证据呈现方式

保留各层测试，把每个关键结论绑定一张简短证据卡：业务判据、实际路径、输入规模、故障位置、持久终值、原始来源和明确限制。它能避免只记“几十项通过”，也能防止旧实验混成当前部署状态。

候选成本是材料需要随规则维护，人工填写仍可能遗漏，自动采集也要谨防敏感数据和把任务数当业务数。先统一一条支付与一条缓存证据的字段就足够；当前专题只整理已有资料，没有新增采集平台或覆盖率指标。没有实际覆盖率报告就不报覆盖率，没有生产负载就不报生产容量。
