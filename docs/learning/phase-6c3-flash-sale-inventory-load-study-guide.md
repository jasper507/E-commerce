# Phase 6C-3：同条件有限负载下的库存策略成本

日期：2026-10-08。Depth / Learning Mode；继续加强“库存并发与秒杀正确性”主线。
代码基线为 `3f3afbc`，承接 [Phase 6C-2](phase-6c2-flash-sale-inventory-comparison-study-guide.md)。
本片比较完整秒杀下单事务的成功结果、重试、延迟与应用侧连接占用，正式默认仍是 NOWAIT。

学习者已正确指出：购买旅程的延迟应看“首次请求到最终结果总耗时”。

## 本片前后变化

- **开始前：** 两种库存步骤的受控正确性已验证，但“快速拒绝”与“等待后成功”怎样影响购买结果、重试和连接占用，仍缺同条件数据。

## 1. 为什么不能只比较一次调用有多快

假设两种办法都收到 24 位顾客的请求：一种迅速拒绝了很多请求，另一种让更多顾客等到订单成功。
前者的平均响应可能较短，却未必给顾客带来更好的购买结果。
因此，延迟必须和成功、繁忙、库存不足数量一起看；重试也必须计入顾客最终等待的时间。

NOWAIT 在库存行被占用时返回 `stock_busy`，失败请求的订单和资格随事务回滚。
条件 UPDATE 候选仍需要写锁，可能在当前请求中等待，然后依据实际更新行数继续或回滚。
两者沿用相同的 [create_flash_sale_order()](../../backend/apps/promotions/services.py)，
只在实验中替换库存预占函数，不复制整套订单规则。

当前候选成功路径是 UPDATE 后 GET；默认成功路径是 SELECT FOR UPDATE NOWAIT 后 UPDATE。
两者的库存步骤都执行两条 SQL，不能预先认为候选节省了一次数据库往返。

本片最小设计是“相同完整业务流程、相同输入规模，改变库存步骤和有界重试规则”。
另一种办法是直接发 HTTP 持续压测，但它还会引入网络、认证、服务器线程与连接池限制；
当前先隔离业务事务的成本，HTTP 和持续容量实验留到有明确需求时再做。

## 2. 实验输入与必须守住的业务事实

Finite Closed Batch（有限封闭批次）指一次提交固定数量的任务，全部结束后停止，不持续补充新流量。
本片每批 24 位不同顾客、8 个 worker（实际执行任务的工作线程）、一个共享热点 SKU。

| 条件 | 固定安排 | 要观察的问题 |
| --- | --- | --- |
| 库存充足 | 初始可售 24、预占 0 | 繁忙拒绝与重试是否让库存未卖满 |
| 请求多于库存 | 初始可售 6、预占 0 | 成功、繁忙与库存不足怎样分布 |
| 单次尝试 | 每位顾客最多调用 1 次 | 快速拒绝本身的结果和成本 |
| 忙时有限重试 | 最多 3 次总尝试；间隔 5、10 ms | 多争取成功的代价是多少 |

两种策略 × 两种库存 × 两种重试规则 × 三次重复，共 24 个测量批次。
每种策略另做一次无竞争预热，共两次；预热不计入测量样本。
每批新建活动、SKU、库存、顾客、地址和购物车，避免前一批成功资格或库存影响下一批。
执行顺序轮换，避免某种策略总是先跑；实验不人为延长持锁时间。

Test Oracle（判断结果是否正确的规则）先于性能结果确定：

- 成功订单数不超过初始库存；可售库存 = 初始库存 − 成功数，预占库存 = 成功数。
- Order、OrderItem、AddressSnapshot、FlashSalePurchase、InventoryReservation、InventoryMovement 六类事实数量都等于成功数，关联正确。
- 每张订单买一件，活动价和地址快照正确；成功资格为 `HELD/1`，预占及 RESERVE 流水各一次。
- 被拒绝的顾客没有残留订单、Key 映射、资格、预占或流水；普通商品价与购物车保持原样。

NOWAIT 的有限重试可能用完，因此“库存充足”不等于必须卖完 24 件。
正确性规则检查已经提交的事实是否一致，成功率另作为策略成本观察。

## 3. 一位顾客怎样完成一次购买旅程

Job / Journey（购买旅程）是同一顾客从首次调用到最终结果的一组尝试。
Retry（重试）是失败后再次调用同一业务请求；这里保留原 Key、活动商品和地址。

```text
共同 t0：24 个任务进入实验队列
→ worker 取到顾客任务，开始购买旅程
→ 调用完整 create_flash_sale_order()
   ├─ created：成功结束
   ├─ insufficient_stock / 限购等业务拒绝：结束，不重试
   └─ stock_busy：单次规则直接结束；重试规则尚有预算则等待 5/10 ms 再试
→ 达到终值；最多 3 次总尝试
```

Backoff（退避）是在两次尝试间先等一小段时间，避免刚被拒绝就立即争同一把锁。
固定 5/10 ms 只用于本次可复现比较，并未增加正式重试配置或承诺这是最佳间隔。
重试只能覆盖 `stock_busy`，不能把所有错误都改成“再试一次”。

真实数据库错误如 1205（锁等待超时）、1213（死锁）保留原错误，并将该批次标为无效。
无效批次和原始数据仍须保存，不能悄悄删除后只展示好看的结果。
本片没有实现这些错误的正式自动重试，也不能用“未观察到死锁”证明普遍无死锁。

## 4. 三种延迟分别回答什么

Latency（延迟）是从指定起点到终点经过的时间；不先写清起终点，数字就无法比较。
顾客模型和数据库连接预先准备，服务计时直接包住完整下单函数，不额外夹入 fixture 的用户查询。

| 指标 | 起点 → 终点 | 含义 |
| --- | --- | --- |
| Attempt latency | 一次完整下单调用开始 → 返回或抛错 | 本次业务调用用多久，包含其提交或回滚 |
| Journey latency | worker 开始该任务 → 顾客终值 | 所有尝试及退避的总时间，符合已确认的“首次请求到最终结果” |
| Harness queue time | 共同 t0 → worker 开始任务 | 因实验只有 8 个 worker 而排队的时间 |
| Batch end-to-end latency | 共同 t0 → 该顾客终值 | 本实验的排队加购买旅程时间 |

Harness（实验执行器）排队是本次线程安排造成的等待，不能称为真实 HTTP 服务器排队。
End-to-end 在本表只覆盖这个实验批次，没有前端、HTTP、认证或支付。

Percentile（分位数）描述有多少样本在某个延迟以内，例如 p95 表示约 95% 的样本不超过该值。
本片使用 nearest-rank（排序后向上取对应名次）：`ceil(p × n)`。
24 个旅程时，p95 取第 23 个，p99 取第 24 个，也就是最大值；小样本不能稳定估计尾部延迟。
每项结果必须写样本数，保留每批原始值，不能平均三批的 p95 再冒充合并样本的 p95。

延迟旁必须展示成功、繁忙与库存不足数量。全结果延迟较短，可能只是更快地拒绝了顾客。
成功结果的延迟可另看，但两种策略成功的顾客数量不同，也不能单独拿它决定赢家。

Throughput（单位时间完成量）在这里有两个明确口径：
批次终值数 / 批次墙钟时间，以及成功订单数 / 同一批次墙钟时间。
墙钟时间从共同 t0 到最后一个任务终值，不含建数、连接准备和收尾检查。
前者会计入拒绝，后者才反映本批次每秒实际建成多少订单；两者都不是生产持续容量。

## 5. 怎样理解连接占用

8 个 worker 先打开真实 MySQL 连接并记录 CONNECTION_ID（数据库分配给会话的编号）。
计时开始前，只读应用账号可见的 PROCESSLIST，核对本批次的 8 个连接；
测量期间不逐条拦截 SQL 或反复采样服务器，避免观察器额外改变负载。

连接建立时间单独保存，不混进业务延迟。
Connection holding time（连接保持时间）是连接处于打开状态的时间：
将每个 worker 的打开至关闭区间截取到“共同 t0 至最后一个终值”，再相加，得到 connection-seconds。
它包括调用、数据库等待、退避和空闲，并不等于数据库一直执行查询。

Service-active time（业务调用活跃时间）累计真正位于下单函数内的时间，包含 Python 执行及数据库等待。
它不是数据库 CPU 时间，也不是精确锁等待时间；本片没有采集这些指标。
重试退避时连接仍打开，所以退避即使不执行 SQL，也会占着实验会话。

峰值连接 8 主要是我们预先固定了 8 个 worker 的结果。
不能仅凭它说某种策略更节省资源；还要结合连接保持时间、调用活跃时间、成功数和重试数。
每批线程全部结束、连接关闭后才核对业务终值，并开始下一批，避免跨批次污染。

## 6. 先预测，再核对实测

小预测：NOWAIT 的全结果 p95 较低，但有多位顾客最终 `stock_busy`；
条件 UPDATE 的 p95 较高，却让更多顾客成功。仅凭 p95 能决定哪种更好吗？
请同时说出至少一个顾客结果指标和一个资源成本指标。

### 本轮实测：2026-10-08

真实隔离MySQL8.4.10运行：目标 `1 passed in 23.58s`，包括2次预热和24轮测量；576旅程、767调用、250订单，全部业务校验通过。0无效批次/0意外错误/0观察到的锁超时或死锁，不能据此证明普遍无死锁。

- 库存24、只尝试一次：NOWAIT三轮创建3/3/4单，剩余20–21人返回繁忙；候选每轮创建24单。NOWAIT全结果延迟低，也可能意味着更快拒绝。
- 库存24、最多三次：NOWAIT调用60/57/58次，创建11/10/10单；候选每轮24次调用创建24单。候选每批连接开放1.709–2.002秒，NOWAIT1.889–1.932秒，总资源并非每轮都更低，需要与产出一起看。
- 库存6、最多三次：两种策略都创建6单。NOWAIT52–55次调用，候选24次；旅程p95约106–122ms与90–95ms，批次连接开放约1.70–1.83秒与1.02–1.07秒。相同产出下，这组候选实测成本更低。

每项范围来自3轮实际值，不平均分位数。每轮旅程n24，p99是最大观察值；queue/E2E和所有原值另存，不能称生产尾延迟。候选仍需结合真实故障/超时与部署请求负载再确认选型，正式默认保留NOWAIT。

模块回归 `29 passed, 1 skipped, 260 subtests passed in 36.58s`；跳过项就是默认关闭的负载实验。后检临时库已清理，开发schema前后26，check/迁移漂移检查通过；没有改业务代码、依赖、配置、接口或开发数据。
