## 问题是什么

Cache Penetration（缓存穿透：不存在的数据没有被缓存，请求反复查询
数据库）在当前商品详情里表现为重复访问不存在的slug，例如
`/api/catalog/products/missing-mouse/`。

```text
第一次请求 → Redis代号正常 → MySQL没找到商品 → 404
第二次请求 → Redis代号正常 → MySQL又查一遍 → 404
……
```

真实基线：同一不存在地址6次请求、6SQL；不同不存在地址6次、6SQL；
全部404。Redis正常、熔断Closed。这属于正常“不存在”的业务结果，
不能把404算Redis网络失败，也不能靠熔断消除它。

已有商品暖缓存6请求同样6SQL，原因是每请求保留上架检查。它是正确性
边界，本步不追求让所有详情零SQL。

## 候选怎样运行

Negative Cache（负缓存：把不存在结果短时间记住）是最小候选。首次
查库确认不存在，保存5秒的标记；同代同slug后续命中则直接404。

```text
首次 → 负标记没有 → 查MySQL确认不存在 → 写短标记 → 404
后来 → 负标记存在 → 404，跳过MySQL
过期 → 再查MySQL
```

只记真正不存在的Product；已有但下架的Product/Category不记，仍每次
查MySQL。否则重新上架时可能被旧404标记挡住，会扩大可见性规则。

正常save新建商品会尝试换代：成功后新请求拿新代号，不选旧代负标记。
绕过save的bulk_create或直接SQL可能不换代，可能暂时404；TTL从回填
开始，旧在途请求也可能晚写，所以不能说创建后严格最多5秒。

## 为什么选小方案

保持每次查库最简单，也没有负记录导致的新可见性窗口；缺点是重复
查库。短负缓存减少同一缺失地址的重复SQL，代价是健康商品请求新增
一个Redis GET、额外短期Key以及需要解释的可见性窗口。

如果每次请求换随机地址，每个地址的第一次仍要查询；不能把本段说成
防住所有恶意穿透。当前也不合并缺失地址首次并发，不加新框架或依赖。

## 2026-09-30 学习结论

你给出的首个测试预期是“同一不存在地址短时间内只查一次商品 SQL”。
原实现实测 6 次请求、6 SQL，所以红灯不是测试写错，而是确实没有跨
请求记住“不存在”。接入 Redis 短标记后，目标测试与目录回归通过：
同地址顺序 6 次只有第一次查商品 SQL，6 次仍全部 404。

一句面试回答可从你自己的解释继续：两个 HTTP 请求互不共享上次的
MySQL 查询结果；我先用真实隔离 MySQL/Redis 复现重复缺失地址的 6 SQL，
再按 slug 将“真正不存在”短存 5 秒，复测为 1 SQL。已有但下架的商品
仍查数据库并返回 404，正常商品仍做上架检查。代价是健康请求多一次
Redis GET，并且随机地址与首轮并发请求不能靠这个小方案全部解决。

为什么正常 save 提交后的新请求能看到商品？如果改用 bulk_create，
这个结论还有没有保证？验证细节见[Phase 4H 记录](../verification/phase-4h-cache-penetration.md)。
