# 订单列表 HTTP 压测工具与执行准备

配套[验证记录](../verification/order-list-load-tooling.md)。本轮属于 Supporting 工具实现，服务于“订单列表为什么变慢、怎样判断负载拐点”的面试解释；还没有测出项目容量。

## 要回答的业务问题

“我的订单”按本人过滤，再按创建时间和 ID 倒序返回一页。此前已完成分页和联合索引的 SQL 对照；现在需要观察真实 Session 登录之后，多人持续请求这一接口时的吞吐、尾延迟和错误，而不仅是一条 SQL 的执行时间。

数据量和访问负载必须分开。默认计划是10,000笔合成订单、20个账号，每个账号500单；分别模拟1、5、10、20个闭环用户。以后可另开100,000或1,000,000单的数据集，再采用相同负载梯度。百万订单还会产生百万地址快照和两百万商品明细，不是“数据库总共百万行”，也不是百万并发用户。

每个账号的Session独立。先取CSRF Cookie、按真实登录接口建立Session，所有用户就绪后暖机，再开始测量订单GET。每个用户请求后固定等待100毫秒，这是闭环用户行为；20用户最多只能提供约200RPS，实际还要扣除请求耗时，不能将观察到的吞吐当作服务器上限。登录会写Session和last_login，不能把整个流程称为完全只读；正式负载任务只读取订单。

## 为什么选择这个方案

Locust用Python描述HTTP用户行为，能直接处理本项目的Cookie、CSRF和分页JSON，见[官方场景说明](https://docs.locust.io/en/stable/writing-a-locustfile.html)。本工具固定[Locust2.46.7](https://pypi.org/project/locust/2.46.7/)。相比继续放大旧服务层线程实验，它覆盖实际HTTP、认证、Gunicorn和MySQL；代价是压测端自身也消耗资源，需要排除客户端饱和。JMeter同样可用，本轮选择Locust是为了复用Python能力，不代表Java工具只能测Java。

目标是独立MySQL库、专用用户、Compose网络与命名卷，HTTP只映射本机18080。入口还要求本轮令牌和数据集标识。根开发.env不进入镜像，普通开发设置、原部署配置和交易逻辑均不修改。真实造数/启动必须由--execute显式执行，并经过用户对具体规模的确认。

造数每批500单，同时创建地址及两条商品快照，单批事务；不构造百万对象大列表，不用整表UPDATE。创建时间故意包含相同值，预期页由独立的编号规则计算，再比对响应UUID、顺序、数量和账号标记。它是读取性能夹具，没有执行库存预占或支付，不能当作百万真实交易。

同一运行目录若出现过完整或失败的造数标记，拒绝续跑。失败现场保留，换新的命名空间；不自动清库、删卷或假装恢复成功。

## 怎样计量和判断

每档分开用户启动、暖机、稳态和有界收尾。响应时间来自Locust的请求计时；p95表示这一档95%的样本不超过该耗时，按原始样本计算，不平均多档p95。

延迟和失败率保留所有在稳态窗口中发起的请求，包括窗口结束后才完成的慢请求。吞吐只统计这些请求中在窗口内完成的数量，再除以窗口时长；晚完成数量另列。原生Locust CSV还包含登录/暖机等，不能直接把其总计当作本工具的稳态结论。

固定数据量、页码、索引模式及资源后，若相邻有效档位的用户数至少增加50%、成功RPS增长不超过10%、p95至少增加50%，报告“拐点候选区间”。这是一条预先声明的筛查规则，不是数学证明；需要在相邻档位重复，并结合应用/数据库资源判断。没有出现时报告未找到，不能预设“达到几百万就一定出现拐点”。

报告要求目标、压测端资源样本；客户端CPU连续3次采样达到85%、容器OOM/退出/重启、宿主可用内存采样低于1GiB、响应正确性出错、延迟或失败越过停止阈值，都会停止后续升档。缺少资源证据的档位不用于容量结论。2个sync worker、同宿主争用或客户端限制，都可能先成为瓶颈，不能直接归因MySQL。

默认每档暖机10秒、测量30秒，p95上限2秒、失败率上限1%，至少100个测量样本；超过阈值的结果仍保存。最多200个模拟用户、300万订单是工具参数上限，不是已经验证可承受的规模。

## 可审阅的运行方案

在仓库根目录，以下命令只创建本地计划与忽略提交的随机凭据，不连接数据库：

```powershell
.\.venv\Scripts\python.exe scripts/order_load.py plan --run sample10k --orders 10000 --accounts 20 --users 1,5,10,20
```

先看artifacts/order-load/sample10k/plan.json。不加--execute时，prepare/run只展示计划。获得对启动服务和写测试库的确认后再执行。至多1万订单、20用户、每档测量不超过30秒的小规模短测，准备前要求主机至少3GiB可用内存；目标服务已启动后，运行前要求2GiB，避免重复预留已占用的目标内存。更大或更长计划仍要求5GiB。Docker总内存始终至少5GiB，磁盘须满足预留门槛。运行时资源记录包含宿主可用内存，低于1GiB停止后续负载。

```powershell
.\.venv\Scripts\python.exe scripts/order_load.py prepare --run sample10k --execute
.\.venv\Scripts\python.exe scripts/order_load.py run --run sample10k --execute
```

prepare会下载/构建独立镜像、创建卷和数据库、迁移、造数并启动2-worker应用；准备前要求相关源码已审阅提交，记录实际提交与每个运行独有的镜像ID。run先核对运行镜像，再逐档执行并保存请求JSONL、Locust CSV、容器资源和最终report.json。stop --run sample10k --execute只停止该实验命名空间并保留卷，不删除开发环境或任何卷。不要公开生成的.env。

首页和深页要另建运行：例如每人5,000单才有第201页。比较索引时，用新运行选择--index-mode without_read_index，只在新实验库移除这一条普通读取索引；默认indexed。已有幂等唯一约束保留，不会把删除索引操作写入业务迁移。

## 当前证据与停止边界

10月16日先完成离线规则/保护/统计测试，以及真实Locust对假HTTP的流程自测；这些只验证工具。10月17日经拥有者授权，已构建独立镜像、迁移MySQL并生成1万订单，真实运行Django/Session/CSRF/Locust四档测试，详见验证记录及其原始证据。

首轮9,929个测量请求全部成功；1/5/10/20用户的成功RPS约9/46/92/184，p95约10/11/10/12毫秒。Docker口径的三容器采样合计峰值约761MiB，宿主可用内存最低约2.70GiB，未触发保护停止。收尾有一次窗口外资源采样失败，稳态数据完整。本轮没有找到拐点，也没有测试无索引、深页或百万数据。

这轮支持独立说明真实HTTP登录、固定数据与分页、暖机与测量、p95和RPS口径；尚不能说明服务器上限或索引收益。下一步先理解为什么100毫秒等待会限制请求供给，再根据资源选择索引、页码或数据量其中一个变量做对照，不自动扩量或增加其它接口。
