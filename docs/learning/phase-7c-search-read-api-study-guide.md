# 商品搜索读入口：ES给候选，MySQL确认当前事实

## 本片前后变化

- **开始前：** ES只能在隔离原型内查询；公开商品列表仍使用MySQL完整包含匹配。
- **本片改变：** 增加独立的`GET /api/catalog/search/`读入口，将ES当前候选页交给MySQL检查并生成现有商品摘要。
- **完成后与边界：** 独立接口已在真实隔离ES/MySQL中通过验证，默认关闭，只允许测试来源。前端与原商品列表不切换，没有自动同步或性能提升结论。

## 1. 这片形成什么业务闭环

顾客输入关键词与可选分类 → ES按相关性给出一页候选商品ID → MySQL排除当前不可见商品并读取价格、有货提示 → 返回商品摘要，继续使用已有详情与购买流程。

这片闭合的是搜索读路径，尚未闭合真实前端搜索体验。它支撑你解释“搜索副本为什么会旧、当前事实怎样守住、分页数字为什么不能混用、搜索故障怎样处理”；最小证据是真实ES/MySQL中的陈旧候选、分页及故障场景，而不是添加依赖数量。

`q`去掉两端空格后不能为空，最多80字符；`page`默认1，范围1～500；可选`category`最多80字符，空值不筛分类。参数非法返回400。

## 2. 重点一：搜索命中不是商品当前事实

ES仍保存名称、描述、分类及商品标识，不保存价格库存。它先按相关性降序、同分按商品ID升序取20个候选，MySQL再检查商品与分类都有效；指定分类时，还检查当前分类归属。

最重要的代码是这段候选回读，省略ES请求与响应封套：

```python
queryset = public_product_summaries().filter(pk__in=ids)
if category:
    queryset = queryset.filter(category__slug=category)
current = {product.pk: product for product in queryset}
products = [current[product_id] for product_id in ids if product_id in current]
```

`public_product_summaries()`包含当前可见性过滤、有效SKU最低价与当前库存有货判断。SQL的`IN`不保留ES顺序，因此最后按候选ID重新组装；被过滤的ID直接跳过，不能随意改成名称排序。

例如ES给出商品A、B、C；B已经下架，C改价。返回A和C，C价格来自当前MySQL，不展示B。`in_stock`只是读取时的浏览提示，下单仍重新校验权威库存，不保证点击购买时一定有货。

**回读能纠正可见性和摘要，不能修复所有搜索陈旧问题。** 商品改名后，旧文字仍可能让它命中；新建或刚改成匹配文字的商品也可能漏掉。本片不再次做MySQL `LIKE`，否则就把ES文本语义偷偷改回完整包含匹配；根本修复要靠后续同步或重建。

## 3. 难点一：分页数的是候选，不是最终可见结果

响应保留旧商品摘要字段：`slug`、`name`、`category`、`lowest_price`、`in_stock`。外层采用独立搜索契约：

| 字段 | 含义 |
|---|---|
| `candidate_count` | ES本次查询的精确候选总数，包含可能陈旧的候选 |
| `next_candidate_page` | 下一候选页的整数页码，没有则null |
| `previous_candidate_page` | 上一候选页的整数页码，没有则null |
| `results` | 当前候选页经过MySQL检查后的商品摘要 |

例如候选总数25，第二页取得5个候选，其中2个已隐藏：返回3个结果，`candidate_count`仍为25，下一页null、上一页1。不要把25宣传成“当前可售商品总数”，也不要因为少于20条就判断候选已结束。

本片**短页、空页都不补拉**。一个有效候选页即使全部被过滤，也正常返回200空结果，并按候选位置保留翻页信息；没有任何命中时，第一页也是200。超出候选尾的后续页返回404。

超过10,000个候选返回400，要求缩小关键词或分类；不继续提供深页。候选页采用位置偏移，没有PIT（固定搜索快照），配置切到新索引或索引数据变化可能改变相关性与位置；同分ID排序不等于跨页一致快照。[官方分页说明](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/paginate-search-results.html)

有意义的替代方案是：回读全部候选、过滤后再分页，得到精确可见总数并尽量满页。它需要读取远多于20个商品、维护全量顺序，扩大数据库与应用内存工作。本片选择明确的候选分页，而不是用含糊的`count`掩盖这种代价。

## 4. 难点二：搜索失败不能伪装成空结果

ES无法连接、索引缺失、构建未完成、来源不符，或返回超时/失败分片等不完整结果，都返回503。有效参数下默认关闭也返回503；200空结果仅表示可确认的无命中或候选被当前规则过滤。

这里不自动回退MySQL搜索。两种搜索语义和排序不同，故障时静默切换会改变结果，并可能把流量集中到数据库。代价是搜索暂不可用；普通商品浏览仍保留，后续前端需要明确提示顾客，而不是把503显示成“没有商品”。

每次请求新建并关闭ES客户端，依次检查集群信息、索引元数据和执行搜索，各调用配置2秒请求超时、零自动重试。**这不是总接口2秒期限**，多次网络等待和数据库工作可能累加。

非空候选回读通常包含一次实际数据库来源检查、一次当前摘要查询；摘要只按这页少量ID读取，没有额外全量候选回读。这个结构不能代替实测耗时，也没有证明搜索比原列表更快。

## 5. 为什么现在严格限定隔离来源

本入口只允许`ENVIRONMENT=test`、真实MySQL `test_project_one`，且不能持有外层数据库事务等待ES。ES地址固定为本机9201，检查集群名与8.19系列版本；配置只能指向精确随机测试索引，不能是通配符、别名或开发索引。

构建器新增`_meta`（索引来源与完成标记）：先标未完成，逐项写入、刷新、数量核对成功后才标完成。读入口只接收精确匹配的完成标记，本身不写ES。这让一个新请求也能判断索引是否来自已完成构建，而非依赖构建器内存集合；它不是签名或逐字段完整性证明。[官方元数据说明](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/mapping-meta-field.html)

**标记只记录库名，没有记录测试数据代次。** 销毁再创建同名测试库后，旧索引里的ID可能指向另一批商品；标记无法识别这种混用。因此索引与测试库必须属于同一夹具生命周期，数据库重建后旧索引作废并重新构建。当前保护不是生产身份绑定或自动发现机制。

原公开列表与前端、开发数据库和索引、模型迁移、alias切换、MQ同步均不在本片范围。价格库存仍由MySQL保存事实，这不是把电商交易迁到ES。

## 6. 证据边界、缺口与下一步

新接口在线8项通过（5项真实ES/MySQL、3项单元/注入），停服务后真实离线1项通过；共享原型另5项回归通过，原目录24项及6个子场景通过。正常搜索2条SQL，离线503只有1条来源检查、0商品摘要SQL，旧浏览200；修正过晚读取统计的首轮日志后已补跑，最终JSON为准。开发30表只读摘要相同，测试库和独立ES已清理。Django检查0问题、无迁移漂移、pip check通过，完整记录与边界见[验证记录](../verification/phase-7c-search-read-api.md)。

验收只需覆盖候选顺序、当前隐藏/分类/价格变化、短空页与候选尾、超量限制、构建/来源拒绝及真实ES离线503。足以讲清“搜索副本与事实怎样配合、分页及故障有什么代价”就收片，不扩大搜索质量或性能矩阵。

仍未解决索引自动新鲜度、数据库代次绑定、跨页快照、生产连接池与依赖总期限、真实前端入口和上线配置。下一片建议先处理手动重建与安全读入口切换：变更后构建新候选，成功才换读入口，失败保留旧索引；在隔离环境证明这一成功/失败边界即停止。开发数据建索引与启用需要单独确认，不直接扩大为自动同步或MQ搜索任务。
