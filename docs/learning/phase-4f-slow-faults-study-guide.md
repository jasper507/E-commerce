# Phase 4F：从实验边界理解缓存故障

本段是 Track B 的 Depth / Learning Mode。业务闭环已经能够浏览、下单和
模拟支付；现在补强“Redis缓存一致性与故障降级”的面试故事。代码只增加
实验，没有实施新的故障策略。

## 这一步完成什么

上一步的故障名额解决“Redis坏了后，不让此进程的详情回源同时无限增加”。
本段继续检查三个问题：请求是不是还要等Redis？请求合并遇到慢加载是否
还有效？Redis恢复后能不能读到正确的展示价格？

三组真实结果：

1. 每轮6并发，Redis慢故障两轮都出现6次超时；每轮2成功、4拒绝、4 SQL。
   被拒绝请求虽然零业务SQL，也先付出约100ms等待。
2. Redis正常而加载者被暂停，4个等待者在200ms后各自加载，最终5请求
   全部成功、5次详情加载、10 SQL，故障名额没有被申请。
3. 缓存旧价129 → 故障期MySQL提交169并回源显示169 → Redis恢复显示129。
   旧代号没换掉，原Key尚未过期；再次成功save换代才显示169。

这些是隔离服务实验的观察，不是生产容量或性能成绩。方法和原始记录见
[验证文档](../verification/phase-4f-slow-faults-and-recovery.md)。

## 完整请求怎么走

正常业务从前端商品页发起HTTP详情请求，经过Django路由进入公开详情视图。
此接口允许游客浏览，不读取其他用户的私人数据。以下实验用APIClient直接
走后端流程，未经过浏览器和HTTP服务器。

```text
请求 → Redis取得本次代号（必须在详情首条SQL前）
├─ 代号读取失败 → 标记故障 → 申请本地回源名额
│  ├─ 满员 → 503（此前可能已经等了Redis 100ms）
│  └─ 获得 → MySQL上架检查 → SKU/库存详情 → 返回 → 归还名额
└─ 代号正常 → MySQL上架检查 → Redis读同代详情
   ├─ 命中 → 返回公开JSON（仍有1次上架SQL）
   ├─ 读取失败 → 申请故障名额（此前已有1次上架SQL）
   │  ├─ 满员 → 503
   │  └─ 获得 → 独立加载SKU/库存 → 返回 → 归还名额
   └─ 未命中 → 加入同进程、同代、同商品进行中的加载
      ├─ 原加载者 → 再查同代缓存 → 必要时查SKU并回填 → 通知等待者
      └─ 等待者 → 最多等待200ms
         ├─ 获得共享结果 → 返回
         └─ 超时 → 独立再查缓存；仍未命中则自行加载
```

加载者或超时等待者复查缓存时若GET失败，也会进入故障名额保护；此前的
上架SQL无法撤回。不能把所有503都说成零SQL。

这说明两个“超时”含义不同。Redis timeout（依赖超时）表示Redis操作没
在预算内得到回复；Future wait timeout（共享结果等待超时）表示另一个
加载者还没有完成。后者不能直接推断Redis坏了。

100ms是Redis socket连接/读取超时配置，不是整个Redis命令或请求的严格
总截止时间；200ms是等待共享结果预算，也不是请求完成期限。等待结束后
还有查询、回填、序列化；总耗时可能超过它们。

## 三种保护各负责什么

| 机制 | 通俗作用 | 本项目的边界 |
| --- | --- | --- |
| SingleFlight（请求合并） | 相同任务让一个人做，其余共享结果 | 本进程同代同商品；等待超时可再次做，不是数据库总上限 |
| Admission control（准入控制） | 工作开始前发有限通行证，满员拒绝 | 本进程指定故障入口；不是每秒限速，也不消除Redis等待 |
| Circuit breaker（熔断） | 连续失败后暂时少尝试，过一段时间试探恢复 | 当前未实现；即使实现，也不自动修复旧缓存 |

读熔断一般需要Closed（正常尝试）、Open（暂时绕过）、Half-open（少量
探测）三个状态。它可能减少持续故障期间的等待，但也可能延迟使用已经
恢复的缓存。探测如果人人都做，又会产生集中尝试，所以必须定义探测名额。
本段尚没有实现或验证这些状态。

## 为什么故障期间新价，恢复反而旧价

假设G1缓存价格129。管理员正常保存169，MySQL提交成功；提交后的回调
尝试把Redis代号改成G2，但连接失败，Redis继续保留G1和129。

故障期间浏览无法读Redis，所以查MySQL得到169。恢复后请求又成功读到
G1，找到仍未过期的129，于是展示回退到旧价。它没有重新读取SKU价格，
只有商品上架检查，所以这次是1 SQL。

这不是请求合并出错，也不是MySQL丢数据。关键是MySQL提交与Redis换代
没有一个共同的原子提交。先捕获代号防止旧请求污染新代，不能保证每次
数据库修改都一定成功生成新代。

商品展示可以允许有限陈旧，而下单必须读取MySQL权威价格和库存，两者
业务要求不同。本段没有重新定义“允许陈旧多久”，TTL从缓存回填计算，
不能说从数据库提交时严格开始倒计时。

## 练到什么工程能力

- 区分故障类型：连接拒绝、连接后超时、加载者慢、恢复旧副本，各有不同
  的可观察结果，不能用一种假异常覆盖所有结论。
- 设计实验：使用真实服务，明确暂停位置、等待预算、SQL计数和正确性
  判定；让证据证明一个问题，避免把人为暂停的耗时当性能。
- 定位保护范围：说明名额保护从哪里开始、覆盖哪条查询、是否跨进程，
  不能把一个semaphore说成“保护全站数据库”。
- 解释设计取舍：减少重复工作、减少等待、允许多少拒绝、如何恢复正确性，
  是不同目标，需分别决定和验证。

## 可以独立讲出的面试回答

“我先用真实MySQL和Redis测了冷缓存重复加载，再用进程内请求合并减少
同代同商品的重复工作。Redis故障时另加2个回源名额，满员返回503。
然后测试慢故障，发现限并发仍让每个请求先等Redis超时；健康Redis的
加载者超过等待预算，也会出现重复回源。最后复现提交后换代失败，故障
期读新价，恢复后读旧价。因此我把吞吐保护、等待成本和恢复一致性分开
设计，没有宣称请求合并解决所有故障或当前缓存强一致。”

这里的2个名额是实验值；多进程各有一份。人工负载证明实现边界，不能
称为真实用户流量或生产容量。

常见追问及回答要点：

| 追问 | 应说明的关键 |
| --- | --- |
| 503不是立即拒绝吗，为什么还有100ms？ | 先发现Redis故障，再申请名额；满员不排队，但故障发现已耗时 |
| 为什么有2个名额，仍出现5个加载者？ | Redis正常的等待超时未标记降级，走的是另一条独立加载路径 |
| 等待超时能否取消原加载者？ | 当前Future等待超时不取消正在运行的查询；强行删登记会让更多人重复加载 |
| 怎么证明发生了重复回源？ | 4个真实等待超时、5次load_detail、5条SKU SQL和5条上架SQL，相互印证 |
| 熔断能解决恢复旧价吗？ | 减少失败尝试不改变缓存代号，恢复一致性需要另一套失效/补偿规则 |
| Redis写超时是否证明没写成功？ | 不能，回复可能没收到而命令已执行；本次旧价实验单独使用连接拒绝 |
| 为什么不直接增加200ms？ | 更长等待可能少重复SQL，但占请求资源且仍不保证完成，要有业务预算与实测 |
| 如何选择回源名额？ | 必须结合真实部署进程数、数据库预算和其他入口负载测量，本段未选生产值 |

下一段前先自己复述：三组实验各控制了什么、证明了什么、没有证明什么；
以及若优先减少持续故障等待，为什么读熔断仍需配合现有回源名额。健康
缓存也返回503或恢复后先换代都可能改变业务行为，需分别讨论后实施。
