# Phase 4C：热点冷启动与 Redis 连接失败回源基线

本文件保留 2026-09-26 的历史基线。Phase 4D 已在同一实验代码中加入未合并
与请求合并对照，现在运行会执行两个方案并输出带方案后缀的 JSON；后续
结果见 [Phase 4D](phase-4d-detail-singleflight.md)，本页历史数据未覆盖。

## 本步任务与业务位置

2026-09-26，本段属于 Track B / Depth / Learning Mode。公开商品详情分代已
处理成功换代后的旧回填污染；这次测量相同商品的并发浏览是否重复加载详情，
以及缓存连接失败后增加多少数据库查询。没有实现请求合并，没有改业务代码。

要保留的规则：每个成功请求返回相同的公开详情；每次仍在 MySQL 检查商品及
分类是否上架；价格、库存和交易始终以 MySQL 为准。商品是合成数据，但
MySQL、Redis、并发请求、连接错误和下列测量都是真实运行结果。

## 实验方法

- Python 3.11.9、Django 5.2.17、Windows；MySQL 8.4.10、Redis 8.10.1。
- 隔离数据库 `test_project_one`；独立测试 Redis 端口 6381；每次测试随机
  UUID 前缀，清理仅删除该前缀，不使用 FLUSHDB。
- 一个上架商品，一个上架 SKU，单价 129.00、可用库存 10；本实验只浏览。
- 三种场景，每种 10 线程同时开始请求，重复 3 轮，共 90 个被计量请求。
  10 小于现有 Redis 连接池上限 16，避免池耗尽混淆本次问题。
- 使用 DRF APIClient 执行 Django 请求链、真实 ORM/Redis 调用，**没有经过
  HTTP 服务、浏览器、Gunicorn 或网络入口**。不能视为线上压测。
- 每线程先建立 MySQL 连接，再在开始屏障汇合；计时覆盖请求至 JSON 解析，
  排除建数据库连接和开始屏障等待，包含查询、序列化、日志及线程调度。
- SQL 由线程各自的 `connection.execute_wrapper` 直接计数，区分
  Product/Category 检查和 SKU/Inventory 加载；不使用会切换全局信号的
  CaptureQueriesContext 并发计数。主线程预热仍复用原单请求工具。
- 包装缓存 `get` 仅观察原方法返回值和可用性，记录 hit/miss/unavailable，
  不替换 Redis 行为，不在 miss 后加同步屏障，不人工强迫所有请求未命中。
- 热缓存：每轮预热后请求。冷缓存：每轮真实切换全局代号，确认新代详情为空
  后请求；保留自然调度竞争。故障：只将测试进程中的 Redis 地址指向本机
  已 bind 但没有 listen 的 TCP 端口，产生真实连接失败，不停止健康 Redis。
- 准备请求、建连接、换代及 fixture SQL 不计入 90 个请求。三轮冷热场景
  不发生商品修改，不能用此测试证明改价并发正确性。

## 能证明什么

1. 缓存命中仍然每请求查询一次 MySQL 检查上架状态，不能声称零数据库查询。
2. 同一个商品新代建立时确有重复详情加载，三轮分别为 6、4、6 次。这是
   Cache Stampede（多个请求同时遇到空缓存，一起读取数据库）的局部证据。
   未命中的个数依赖调度；再次运行不需要复现完全相同的数字。
3. Redis 连接失败下 30 个请求仍然返回正确详情，但每请求变成 2 SQL。
   这证明该场景下能降级，不证明 MySQL 在大量流量下仍能承受。
4. 分代解决旧回填污染与限制重复回源是两个问题。目前每个未命中请求独立
   加载，没有负责加载的唯一请求，也没有等待该请求的队列。

不能声称强一致、生产容量、最大 QPS、性能提升倍数，也不能声称已验证
“唯一加载者失败后的接管”和“等待者超时”：当前没有这种合并机制。

## 下一步的最小候选与面试能力

证据已足够支持比较同 Key 请求合并：让同时未命中的请求共享一次详情加载。
最小候选是进程内 singleflight（同一个进程内相同 Key 共用一次加载），
替代方案是 Redis 租约锁协调多个进程。前者简单且不依赖 Redis 锁，但不能
合并不同进程；后者跨进程，但要处理锁过期、释放所有权和 Redis 自身故障。
这里尚未选定或实现方案。

下一段先确定合并键是否包含 generation、共享加载失败的处理、等待时限、
异常清理，再用同样查询口径比较。Redis 故障时无法依靠 Redis 锁，数据库
整体保护需要另行比较本地限并发或快速拒绝；不能说一把锁解决全部故障。

这一步训练实验设计、SQL 观察、并发调度理解、故障注入和结论边界。
面试可独立讲述：为什么命中还有 SQL？如何证明重复回源？为何未命中数不是
固定 10？成功降级为什么还可能拖垮数据库？为何分代不等于请求合并？
