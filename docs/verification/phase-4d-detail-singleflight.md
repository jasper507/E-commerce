## 问题、最小方案与取舍

本段为 Track B / Depth / Learning Mode。Phase 4C 已观察到同一商品冷缓存
重复加载；这次只合并本进程内、同一环境前缀、同一代号、同一商品的公开详情。
不合并上架检查，也不进入订单、库存或支付路径。

选择 singleflight（相同 Key 的进行中加载共用一个结果）：短 Lock 保护
Key → Future 注册表，Redis/SQL/等待都在锁外。Future 是供等待者取得结果
的线程同步对象。另一候选是 Redis 租约锁：可跨进程，但增加过期、所有权、
释放和 Redis 自身故障处理。本段未实现分布式锁，不宣称跨进程合并。

协议规则：

1. 在任何详情 SQL 前捕获代号。每个请求独立检查 MySQL 上架状态，之后
   初查捕获代号的详情 Key。命中直接返回。
2. 初查可用但未命中，以完整详情 Key 注册/加入进行中的加载。新加载者
   再查一次同代 Redis，避免上一轮刚回填就结束，当前请求仍重复读 SQL。
3. 加载者读取 SKU/库存、序列化公开 JSON、尽力回填，通知等待者共享结果。
   顶层转普通 dict，去掉 DRF ReturnDict 隐含的 Serializer/Request 引用；
   不共享 ORM 对象、Request 或 Response。共享公开数据仅用于只读响应。
4. 等待预算 200ms，是本地候选参数。超时者独立复查同代 Redis，必要时
   自己读取数据库；不能取消 Future 或删除仍在工作的加载者。
5. 加载者抛异常时，发布失败标记，保留其请求的原始异常，再在 finally
   中清理登记。等待者收到失败后独立复查/加载，不跨线程重抛同一个异常对象。
6. 初次缓存不可用、缓存禁用或事务内直接走原查询。二次 Redis 检查或回填
   失败时，已经加入的请求仍可共享加载者成功读取的公开数据库结果。
7. 完成后清理注册表，不把它变成第二个长期内存缓存。G1/G2 的完整 Key
   不同，换代后的请求不能加入旧代加载。

失败、等待超时后的独立回源是可用性取舍，不能保证任何场景始终只有一次
数据库加载。等待预算不等于整个请求时限；卡住的加载者也不会自动取消。

## 真实对照实验

2026-09-27，在真实隔离 MySQL 8.4.10、Redis 8.10.1 上，复用 Phase 4C
查询口径：每场景 10 并发 × 3 轮，两个方案共 180 个被计量请求。
比较基线在测试内替换 `get_or_load` 为原 get/load/set 路径，其余 API、
分代和存储相同；不是在两台不同服务上测量。所有请求均 200、完整 JSON
一致。自然调度，无强制 miss 屏障。历史 Phase 4C 数据保留，未覆盖。

| 场景 | 未合并：三轮详情加载 | 合并：三轮详情加载 | 未合并：三轮 SQL | 合并：三轮 SQL |
|---|---|---|---|---|
| 热缓存 | 0 / 0 / 0 | 0 / 0 / 0 | 10 / 10 / 10 | 10 / 10 / 10 |
| 新代冷缓存 | 9 / 10 / 7 | **1 / 1 / 1** | 19 / 20 / 17 | **11 / 11 / 11** |
| Redis 连接失败 | 10 / 10 / 10 | 10 / 10 / 10 | 20 / 20 / 20 | 20 / 20 / 20 |

冷缓存三轮 SQL 合计 56 → 33；减少的是详情加载（26 → 3），30 次上架
检查仍然存在。合并场景每轮初查全部 10 次 miss，却只有 1 次详情加载；
其余 9 次没有 SKU SQL。初查 miss 与数据库回源是两种不同指标。

## 正确性证据与复现

`test_singleflight.py` 用事件同步验证共享、不同 Key 并行、失败通知及再次
加载、超时不删除 owner、二次检查命中不回源。超时测试覆盖 0 与实际 0.2s
预算，不断言响应时间；owner 保持阻塞直到独立 fallback 完成。

真实 API 受控测试中，4 请求各执行一次上架 SQL，总共只执行 1 次 SKU SQL，
共 5 SQL。为精确编排事件，受控成功测试临时把等待预算设为 5s，它验证协议
正确性，不冒充默认 200ms 的性能实验。换代测试禁止新代请求进入 Future
等待，避免把“等超时后独立回源”误判为“新代没有加入旧代”。

禁用、事务内和非法代号不可用测试要求不调用合并器；原有下架、陈旧库存
不能授权下单、缓存价不能决定金额、真实 Redis 连接失败、回填错误和旧代
隔离测试继续保留。

测量代码错误，不是合并方案的故障反例。

最终商品目录整体回归实际通过：`57 passed, 6 subtests passed in 20.39s`，
包括原目录/缓存分代测试、11 个请求合并用例及两方案对照。Django check

## 尚存限制与下一步

- 同进程有效，多个服务进程仍可能各加载一次；没有跨机器容量结论。
- Redis 整体连接失败仍然集中回源，singleflight 不等于数据库限流或熔断。
- 超时/加载失败可能再次集中回源；长期卡住的 owner 持续占一个登记，需
  另行处理底层查询时限，不能说 200ms 会取消数据库查询。
- 缓存分代的提交回调窗口、崩溃、换代失败、批量更新和库存 TTL 陈旧不变，
  仍不是强一致缓存。
- 本轮无新依赖、配置、模型、迁移、接口契约变更，不改前端和交易路径，
  不修改开发数据库、不执行 commit/push。

下一步先由项目拥有者独立解释 Key 分代、失败和超时的区别；之后单独比较
Redis 故障时的本地限并发与快速拒绝，先确认拒绝策略和可用性代价，再实现。
