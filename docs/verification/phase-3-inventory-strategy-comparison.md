# Phase 3：行锁与原子条件更新对照

## 要回答的问题

库存 1 件、两个请求竞争同一 SKU 时，两种预占办法能否避免超卖？
第一个请求尚未提交时，第二个请求会立即返回，还是等待最终结果？

本实验只比较 **MySQL 库存预占这一步**：

- 当前正式下单使用的行锁策略：`SELECT ... FOR UPDATE NOWAIT`，拿到锁后检查库存并更新。
- 实验候选：`UPDATE ... SET available=available-1, reserved=reserved+1 WHERE available>=1`，
  检查实际更新的行数。

候选方法只写在 `test_inventory_strategy_comparison.py`，没有替换正式下单，
也没有复制订单、地址、购物车及库存流水的完整事务流程。

## 运行方式与条件

```powershell
.\.venv\Scripts\python.exe -m pytest backend/apps/ordering/tests/test_inventory_strategy_comparison.py -q -s
```

- 2026-09-26；Windows；Python 3.11.9、Django 5.2.17、pytest 9.1.1；MySQL 镜像 `mysql:8.4.10`。
- 隔离测试数据库 `test_project_one`；每个场景新建库存 `available=1, reserved=0`。
- 两个线程、各自的 MySQL 连接。第一个线程在事务中完成预占后持有锁；
  第二个线程发出库存 SQL 时，测试保持第一笔事务打开约 0.2 秒。
- 分别让第一笔事务提交或回滚；观察第二笔操作及最终库存。
- Git 基线 `418b022`，工作区还包含尚未提交的库存快速失败改动和前一组对照实验。

## 观察结果

| 第一笔事务 | 行锁 NOWAIT：第二笔 | 条件 UPDATE：第二笔 | 最终库存（行锁 / 条件更新） |
| --- | --- | --- | --- |
| 提交 | 锁占用，立即返回 `busy` | 等待后返回 `sold_out` | `0/1`、`0/1` |
| 回滚 | 锁占用，立即返回 `busy` | 等待后成功预占 | `1/0`、`0/1` |

最后一次运行结果：`4 passed in 6.98s`。第二笔操作在这次运行中的观察耗时：
行锁分别约 7.0、7.0 毫秒；条件更新分别约 216.8、224.9 毫秒。
**这些数字主要反映测试故意持锁约 0.2 秒**，不能当作两种方案的吞吐量或真实顾客延迟对比。

## 目前可以下的结论

两种方法在上述库存竞争场景里都守住了“不超卖”。
原子条件更新在数据库内一次完成“库存足够才扣减”，但 `UPDATE` 也要取得库存行的写锁；
热点行被占用时，它仍然可能等待。当前行锁方案使用 `NOWAIT`，可以快速回复“繁忙”，
代价是第一个人即使随后回滚，第二个人本次请求也已经被拒绝，需要主动重试。

因此，不能仅凭“条件更新少一次应用层检查”就认定它更快，也不能仅凭本实验决定替换正式代码。
下一步若要选最终方案，应在相同的完整下单事务和负载条件下比较成功率、忙/售罄比例、
延迟分布、吞吐、数据库连接占用与死锁，并保留订单、库存、预占和购物车的一致性检查。
