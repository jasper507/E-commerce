# Phase 3：完整下单 API 的库存竞争验证

## 目标与当前状态

服务于库存并发主线：验证不同顾客竞争同一个 SKU 时，现有悲观锁及
`NOWAIT` 策略在完整下单流程中的行为。库存行被锁住应返回
`409 stock_busy`；首单提交后重试应返回 `409 insufficient_stock`；
首单回滚后重试应能创建订单。失败者购物车保留，成功者购物车清理，
订单、地址快照、明细、预占、流水与库存必须一致。

**当前目标验证通过：`3 passed in 11.70s`。** 已在隔离 MySQL 上先复现
锁范围问题（`2 failed, 1 passed in 14.76s`），再收窄购物车锁范围并验证。
相关回归结果见下方“验证结果”。

## 测试路径

新增 `backend/apps/ordering/tests/test_checkout_contention.py`：

1. 两个不同顾客，首单事务暂不提交：第二个请求必须在库存仍被锁住时
   返回 `stock_busy`。首单提交后，第二个顾客用原 Key 重试应得到库存不足。
   第一位顾客同 Key 重放应返回同一个订单且不重复预占。
2. 首单完整写入后注入回滚：第二个顾客仍应先得到 `stock_busy`。
   首单回滚后，订单、快照、预占和流水都应不存在，两个购物车均保留；
   第二位顾客重试后才能产生一套完整订单事实。
3. 10 个不同顾客同时请求，库存 1 件：恰好一笔 `201`，其他为
   `409 stock_busy/insufficient_stock`；失败顾客不得留下订单或丢失购物车。

各顾客使用独立 APIClient、Session、CSRF、线程与数据库连接。测试走
`POST /api/orders/ → OrderCollectionView → create_order_from_cart → MySQL`，
没有复制库存算法或替换业务处理函数。连接仅指向 pytest 的 `test_` 数据库。
这是一组进程内 API 集成测试，不包含浏览器、实际 HTTP 网络或部署服务器。

测试只在前两个场景加外层事务和事件同步，以稳定制造未提交窗口，
并记录第二个请求是否在释放锁前返回。1 秒是测试观察预算，不是顾客
等待承诺，也不是生产响应时间指标。10 人场景输出各请求耗时与结果数，
只用于本机实验观察；不得据此声称支持千人秒杀或给出线上吞吐量。

## 实际复现的锁范围问题与修复

当前购物车读取组合了 `select_for_update()` 和
`select_related("sku__product__category")`。实际 SQL 为多表 JOIN 后的
`FOR UPDATE`，没有指定锁的表。第一笔完整订单事务未提交时，第二个
不同顾客阻塞在这条查询，尚未到达库存 `NOWAIT`：

| 首单结局 | 修复前第二人 | 修复后第二人 |
| --- | --- | --- |
| 提交 | 等到释放锁后返回库存不足，约 1030.57 ms | 释放锁前返回 `stock_busy`，约 16.36 ms；随后重试库存不足 |
| 回滚 | 等到释放锁后直接成功，约 1033.86 ms | 释放锁前返回 `stock_busy`，约 15.85 ms；随后重试成功 |

修复仅将购物车查询改为 `select_for_update(of=("self",))`。记录到的
SQL 变为 `FOR UPDATE OF ordering_cartitem`，联查的目录行不再被这条
语句加排他锁。库存仍使用 `select_for_update(nowait=True)`，User/Cart
锁、幂等约束、库存预占和整单事务回滚规则继续保留。

这些耗时反映测试故意延长的未提交窗口，以及一次本机调用，不能把差值
当成线上性能提升倍数或顾客响应时间保证。关键证据是“是否在首单仍持锁
时返回”，不是某个毫秒阈值。

取舍：价格、规格和可售状态以服务器本次目录读取时观察到的值生成订单
快照，不冻结到事务提交；管理员在该读取之后改价或下架，已在执行中的
订单可能仍使用此前观察到的值。它们不来自前端报价或缓存。若未来要求
下架操作与在途下单严格互斥，必须另行明确规则和协调目录写入路径。
另一种方案是让联查目录锁也使用 NOWAIT，但会把共享商品/分类锁竞争
变成业务拒绝，影响不必要的请求；本切片选择限制锁范围。

## 验证结果

- 环境：Windows、Django 5.2.17、原有 MySQL 8.4 容器，pytest 隔离
  `test_project_one` 数据库。正式业务数据未改动。
- 修复前：`2 failed, 1 passed in 14.76s`，两条“持锁期间应返回繁忙”断言
  失败，记录到没有限定表范围的购物车 JOIN 行锁 SQL。
- 修复后：`3 passed in 11.70s`。首单提交/回滚两种情况均在释放锁前
  返回繁忙；提交后重试库存不足，回滚后重试成功。
- 10 人竞争：修复前 1 成功、9 库存不足；修复后本轮 1 成功、9 繁忙。
  失败原因的比例随调度变化，不断言固定比例。成功数固定为 1，
  最终 `available=0, reserved=1`，一套订单/快照/预占/流水，
  成功者购物车清空，其余 9 个购物车各保留 1 件。
- 相关订单/支付/取消回归：`56 passed, 8 subtests passed in 53.04s`，
  包含普通下单 API、同 Key 并发、订单生命周期、支付 API 与支付模型约束。
- Django 系统检查：`0 issues`。

结论边界：本切片证明的是限定场景内不超卖、无残留订单、失败保留购物车，
以及不同顾客对同一 SKU 的库存锁竞争能返回繁忙；并不保证整个请求全程
无等待。同一顾客的 User/Cart 锁、管理更新及其他数据库操作仍可能等待。
尚未测得生产吞吐量、千人负载或数据库连接容量，也未引入 Redis 秒杀。

## 复现命令

Docker 和原有本地 MySQL 服务运行时执行：

```powershell
.\.venv\Scripts\python.exe -m pytest backend\apps\ordering\tests\test_checkout_contention.py -q -s --tb=short
```

此命令创建、使用并清理隔离测试数据库，不迁移开发库。
预期成功结果为 `3 passed`，同时打印 `CHECKOUT_HELD` 与
`CHECKOUT_BURST` 证据行。若返回 `stock_busy` 前发生等待或出现非预期异常，
应保留失败结果，定位实际阻塞位置，不放宽断言伪装成通过。
